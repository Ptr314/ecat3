## Window (Qt)

- **`MainWindow::e` is null once `closeEvent()` has run**: the emulator is deleted there, and the window still receives events afterwards - `ActivationChange` (which releases the host keys), the release of the key that closed it, a paint. Before the pointer was cleared, a click on the close button of the active window crashed the process with 0xC0000005 whenever the freed memory had been reused, which is rare enough to look random. A new window event handler that touches `e` checks it for null first. Under MCP the emulator is not deleted at all: `McpSession` holds the same pointer (its destructor runs after the window's and clears the script sink through it, and the stdin reader thread may be mid-request), so `closeEvent()` only stops it and the process exit frees it. Deleting it there crashed an MCP session closed after a long run, once the freed memory had been reused
- **A window changes a device only through `e->invoke()`**: a device is not locked, it belongs to the emulation thread. `Emulator::invoke(fn)` runs `fn` there, between two time slices, and returns when it has run; with no emulation thread (nothing loaded, the machine stopped) and on that thread itself it runs `fn` at once, so a script verb and the reset in `run()` go straight through. `Emulator::reset()` goes through it by itself; the drive menu, the option boxes, the debugger (mode, breakpoints, PC, a byte typed into the dump) and the tape window call it explicitly - before that a disk swapped under a spinning drive replaced the buffer the controller was indexing, and a reset from the menu cleared the memory the processor was executing. Three things to keep in mind: `fn` must not wait for the calling thread, which is waiting for `fn`; what it captures by reference lives on the caller's stack, which is fine precisely because the call is synchronous; and reads for display (registers, the tape counter, the drive led) still go direct - a stale value there is a wrong number on the screen for one refresh, not a fault. The debugger reads memory with `CPU::peek_mem()` (the mapper's `get_direct()`), never `read_mem()`: that one is a bus cycle, with the strobes, the read-to-clear registers, the page cache fill and - on a 1801 - the timeout flag the instruction being executed is about to test. Left outside the queue: the hard disk (its own mutex), host keys ("Keyboards and input" in `core.md`) and the other device calls of `wasm_main.cpp` (options, tape). Waiting on the browser's main thread works: the page's Reset and Power (`wasm_reset` -> `Emulator::reset()`) go through the queue and return in under a millisecond
- **Remembered disks are a third step after `.cfg` and `.ext`**: with «Запоминать выбор дисков» on (`[Core] remember_disks`), what the GUI puts into a drive of class `fdd` or `hdd` - an image, nothing, write protection - goes to `[Disks]` of the ini as `<machine file relative to the root>|<device> = <image>|<protect>`, keyed by `sd.system_file` (the file opened, so an `.ext` never touches its base). `build_machine()` takes a snapshot of the configuration's drives first (`m_disk_defaults`, through the device fields `loaded`/`attached`, `path`/`file`, `protected`, and the commands `load`/`eject`/`protect`, so a new drive class needs no code here) and then restores the entries; an entry equal to the default is removed, not written. The restore is off unless the windowed frontend sets `set_restore_disks()`, and it does not for a command line script, a replay or MCP; a `.ecats` is never touched. A new recording starts with `record_disk_changes()`, since its replay restores nothing. `FDD::image_path` is the whole path (`file_name` is the bare name). The web page keeps the entries itself (localStorage `disk.<key>`, the floppy bytes in IndexedDB, since a visitor's file cannot be reopened by name; hard disk images are not kept): `prepareRememberedDisks()` hands them to the core before `wasm_load_machine` (`wasm_disks_prepare`, `wasm_disk_set_entry`, the images written back to their MEMFS paths `/tmp/<drive>/<name>`), and `wasm_disk_remember` / `wasm_disk_default` let the core decide the entry after a change
- **Every copy of the ini writes the whole file as it holds it**: `MainWindow::m_settings` was read before the emulator wrote anything, so the language is saved through `e->write_setup()` - a save from the stale copy dropped `[DeviceOptions]` and `[Disks]` written since start-up

- **Frame blending is the window's, not the surface's**: «Смешивать кадры» (`[Video] blend_frames`, `Emulator::set_frame_blending()`) makes `render()` show every point mixed with the last different value it had, while that one is at most `BLEND_AGE` (2) frames old; that value weighs `BLEND_WEIGHT` (122/256, 95% of a half; 85% flickered too much), so a little of the alternation stays, as on a monitor. The mix is one of light, at the gamma of 2.2 (two tables, `BlendGamma`), not of the values: half a frame of full red is 186, not 128. Checked on the 10-colour palette Manwe drew for Lion (`docs-external/BK/manwe-lion-2025/real-colors`): the mean error went from 27 to 7 ΔE; what is left is the author's taste (mixes with black darker, 149..181, mixes of two colours lighter, 196) and his own error: `T1` of `lion11.mac` has 6 (green/blue) for colour 3 instead of 14, so on odd lines the dark red of the picture is cyan on the machine (`FrameBlender`, `frame_blender.h`, used by `VideoRenderer::blend_frame()`: the same code for OpenGL, SDL2, Qt and the web page; a renderer that skips it while blending is off calls `blend_off()`). The page has it as the «Смешивать кадры» box of the Screen block (localStorage `ecat3.blendFrames`, sent with `wasm_set_frame_blending`, which also writes the core's ini in memory, read again by `init_video()` at every load). The surface the display draws into is not touched, so `get_screenshot()`, the scripts' `SCREEN`, MCP and the video recorder keep the real frames - except a video "as on screen" at the rate of the machine with blending on, see Video recording. It is for programs that alternate a picture every frame to mix two colours (the 4k intro of the БК toggles a 40/56-cycle instruction before its palette writes): the host's screen holds a frame whole and a 60 Hz one breaks the 50 Hz alternation, so without it the mix flickers. A plain mean of two neighbouring frames is not enough: Lion (Manwe, БК0010) waits for the timer (480 counts = 61440 clocks = a frame) and then copies 102 x 14 words with MOV (R1)+,(R2)+; at the 44 clocks the real БК0010 takes for it (`tools/bk-timing/measured.tsv`) the copy lasts ~66700 clocks, misses the next timer window, and the pictures go A A B B - two frames each, on the machine as in the emulator (on the БК0011М it fits: 562 of 640 counts). The mean of neighbours turns that into A, mix, B, mix; the mean with the last different value is steady for both rhythms, and a picture changed once keeps the old one for two frames. Known gap: on the line where the copy meets the beam the points go A A A B (the second picture is copied one instruction later, after `MOV #Lion2,R1`), the third A comes out clean and a few points there still flicker; where that line falls depends on the moment of the start (the author: "hit a key to fix the frame tearing"). `BLEND_AGE` 3 makes them steady at the cost of a three-frame trail; it was tried and taken back for now. A display that stops changing no longer sets `was_updated`, so `render_screen()` draws once more while `blend_settling()` says the last mix still holds the frame before; without it the previous picture stayed half visible
- **I/O ports window** (`dialogs/serialwindow.*`, Emulation / I/O ports, or a `dl11`/`printer` entry of the Devices menu, which opens the same window on that tab; the class and the ini section `[Serial]` kept their old names): one tab per device that is a `ByteTap` (`devices/common/byte_tap.*`: `DL11` and `Printer`), found by `dynamic_cast`, since those classes set no `device_class`. A tab is named by the device's `title` (as written in the config: «Терминал», «Стык С2», «Принтер»), the device name and type are its tooltip; files and ini keys use the device name, which does not change with the title. `ByteTap::put()` is called by the device for every byte that leaves it (a DL11 in `transmit_done()`, loopback and plug included; a printer when it takes a byte on its strobe): it feeds the ring of the `output`/`text` fields and, while `set_tap(true)` is on, a mutex-guarded buffer (at most 1 MB) that the window takes with `take_tap()` every 50 ms on the GUI thread - no per-byte callback, no `invoke()`. Neither is state. The file gets the bytes untouched; the field shows them as Latin-1, recoded, or as numbers in `view_base()`. Recoding goes through the encoding chosen in the tab's list: first the machine's `charmap` (`translate_char()`; the ДВК and УК-НЦ configs name `koi8` for it), then the tables of `dsk_tools::init_charmap()` (`charmaps.cpp` was moved into `dsk_tools_core` for it; KOI-7 N0/N1 switches on SO/SI). A tab keeps the last 256 KB it received; a new encoding or mode redraws the field from them (SO/SI counted from the start of that buffer), and «Очистить» empties both. Ini: `[Serial] folder` (default `<work>/serial`), `mode` = original/recoded/bytes, `to_file_<settings_key>_<device>`, `charset_<settings_key>_<device>` (`machine` or a `dsk_tools` id). Logging lives with the window: closing it while a file is written asks first, and so do `load_config()` and `MainWindow::closeEvent()` before they close every `GenericDbgWnd` (a refusal cancels the switch or the exit; under MCP the load returns an error)

- **Paste text** (Emulation > «Вставка текста», `MainWindow::on_actionPasteText_triggered()`): a plain text of the clipboard (not files, not a picture) goes to `Emulator::paste_text()`, which types it as `TYPE` does: `text_to_keys()` (`keyboard.cpp`) is shared with the verb, here without the script escapes (a line break is Return, CR dropped; a character with no key, Cyrillic included, is skipped). The typer is the emulator's own, not the script buffer, which recording, replay and MCP own; its state belongs to the emulation thread, `paste_step()` runs once a slice, timed in emulated cycles, and `run()` clears it for a new machine. «Быстрая вставка» (Settings > Keyboard, after the remap modes; `[Keyboard] fast_paste`, on by default) is 50/50 ms, off 100/100. Ignored while a script is active (replay, a command line script, MCP); while recording, the paste is written as `TYPE "...", _ms, _ms`

## GUI record / replay

**GUI record / replay** (toolbar block, menu Emulation > Action recording) uses the same `ScriptEngine`: it owns the command buffer, and `ScriptRecorder` (`emulator/script/script_recorder.h`, Qt-free) appends commands built from GUI events, timed by `Emulator::clock_counter`. A press/release pair becomes `KEY delay,hold,name`; overlapping presses become `KEYDOWN` / `KEYUP`. `format_script_command()` is the serializer; arguments are stored in file syntax (escapes included), so a value built from scratch goes through `escape_script_text()` first. Threading rule: the emulation thread only calls `tick()`, which has a lock-free fast path and takes the engine mutex only when a command actually runs; the GUI edits the buffer (`append`/`truncate`/`seek`) only while the engine is not active. New GUI actions that should be replayable call `e->record_command()` / `e->record_verb()` right after performing the action (see `fdd_open`, the device-option combo lambda, `TapeRecorderWindow`).

## Video recording

- **Video recording (`emulator/video_recorder.*`, Qt-free) times frames by `clock_counter`, not by the wall clock**: frame N is the picture shown at start + N/fps of emulated time, and `render_screen()` hands over a picture only when one was rendered - the recorder writes the last one again for every frame that came due (the queue holds a picture and a repeat count). The sound is a second capture of every `GenericSound` (`begin_video_capture()`, taken before the mute, so a muted window still records sound - but after the volume, which scales the level itself), summed by `Emulator::collect_video_audio()` as far as every output has got, into a temporary WAV at `produced_rate()` (the rounded `m_counts_per_sample` makes a few more samples a second than the nominal rate: written as nominal, the sound drifted 0.6 s an hour on a 1 MHz machine; the mux resamples to 48 kHz) that a second ffmpeg run adds with `-c:v copy`. Start and stop go through `invoke()`, so frame 0 and the first sample are one moment. The capture is ended by `stop_video_recording()` also after ffmpeg failed on its own (`m_video_capturing`, not `recording()`), or the outputs fill buffers nobody empties. "As on screen" frames come from the GUI: `GLWidget::setFrameHook()` reads back the frame `paintGL()` just drew, the Qt and SDL2 renderers use a timer. ffmpeg runs through `CreateProcessW` with `CREATE_NO_WINDOW` (a `_popen` from a windowed program flashes a console), its stderr goes to `%TEMP%/ecat3-ffmpeg.log`, and the last lines of that file are the error shown to the user
- **"As the machine" (`video_fps = native`) records frame by frame**: a display that knows its rate answers `GenericDisplay::native_frame_rate(num, den)` (a reduced fraction, so ffmpeg gets `-framerate 3125/64`) and calls `frame_complete()` at the end of each picture, on the emulation thread and outside the surface lock. `start_video_recording()` sets the hook there inside `invoke()`; the hook copies the surface under `lock_surface()` into `VideoRecorder::push_frame()`, which never waits (an unchanged picture is a repeat, a queue far behind repeats the last one, so the count stays in step with the sound) - and nothing is then queued by the clock. Rates: БК 3125/64 = 48.828125 (320 lines of 64 us, at 3 and 4 MHz alike), УК-НЦ 15625/312 ≈ 50.08 (312 x 64 us - the machine's own, not 50), Агат 50/1 (a picture per field). A display without a rate falls back to 50 fps on the clock grid; "as on screen" takes only the exact rate, the window's frames cannot be locked. Except with frame blending on: then "as on screen" at the machine's rate records the machine's frames from the hook, blended by a `FrameBlender` of its own on the emulation thread (`m_video_blended`; turning blending off in the window during the recording turns it off in the video), and the window is not read back at all (`video_from_window()` false). The read-back came when the GUI thread painted, later than the frame and not for every one, so the slots of the clock grid got frames twice or not at all, and the residual flicker of the mix jerked in the file; `glReadPixels` and the copy of a window-sized picture held the GUI thread up, `GLWidget::updateTexture()` keeps one pending picture, and the window lost frames and jerked as well, only while recording. Such a video has no CRT shader; the window's pixel aspect is put into the pixels instead of `setsar` (`VideoSettings::scale_x/scale_y`, `scale=...:flags=neighbor`): each axis is enlarged a whole number of times, the height at least the window's scale (auto: 480 lines), and an aspect that is a fraction p/q with q up to 4 is exact (the БК: 256x256 at 4:3 is x4/x3, 512x256 x2/x3, both 1024x768); any other takes the nearest whole width and leaves the rest to `setsar`. Players that ignore `setsar` or smooth it showed uneven points. A frame-locked video starts ffmpeg in `VideoRecorder::start()` with the surface's size (`VideoSettings::width/height`), on the GUI thread: started by the first picture it ran on the emulation thread of the hook, the process start held the machine up for tens of milliseconds, and its catching up jerked the window once at the start. `raster_frame_rate(num, den, pictures)` of `RasterDisplay` is the helper, `display.frame_clocks` the field

## Web page

- **The web page can start an extension it downloads**: `index.html?load=<url>` (`startUrlMachine()` in `src/wasm/ecat_wasm.js`) fetches the file into `/tmp/load/` of MEMFS and loads it like any machine. The base `.cfg` and its ROMs live in the bundle of *their* machine, which the page fetches first, so it needs the base before the load: `wasm_machine_base()` answers with `machine_base_file()` (`config_ext.h`), which parses the extension alone and resolves `@extends` without loading anything. A base that is not a machine of the build, and a server that does not allow the download (the page is cross-origin isolated, so a cross-origin file needs CORS), are the two ways this fails; `wasm_last_error()` carries the core's message to the status line, since `wasm_load_machine()` returns only a code. The same path takes a machine file picked on the visitor's own computer: the "Open file" button hands the bytes to `startMachineFile()`, the half of `startUrlMachine()` that does not care where they came from. That button is shown for every machine, not only for one whose `system` section names `files` - without it a snapshot of the УК-НЦ, which names none, could be opened in the browser by a link and by nothing else. `setupOpenFile()` lives outside the closure that holds the machine list, so `startMachineFile` is a module-level holder that `initEcat()` fills.
- **A hard disk image picked on the page is not copied into MEMFS** (hundreds of MB would be the tab's memory): `HddImage::source_factory` (set by `wasm_main.cpp`) turns a name `/host/<id>/<file>` into an `HddSource`, and a plain worker of the page (`HOST_FILE_WORKER` in `ecat_wasm.js`) holds the `File` and reads what is asked with `FileReaderSync`, straight into the wasm memory, through a mailbox of 8 words in it (`HostFile`, 64 KB blocks cached). The asker waits with `emscripten_futex_wait` - the emulation thread, or the main thread when a controller reads the image while attaching it (spinning there is allowed); the worker needs nobody's event loop, so neither can deadlock. A WORKERFS mount would not do: with pthreads the FS calls are proxied to the main thread, where `FileReaderSync` does not exist. Such an image is never written: `HddImage` keeps the writes in memory, and Save (`wasm_hdd_save`, `HddImage::contents()`) hands out the image with them. The mailbox is freed only after the worker has answered its stop, or it would read reused memory as a request. Controllers expose the image through `HddImageOwner`

## MCP server

- **The MCP server runs behind `.build/mcp_reload.py`**, and that is not decoration: an `eCat3.exe --mcp`
  started directly outlives every rebuild, so it holds the exe open (`cannot open output file eCat3.exe:
  Permission denied`) and keeps answering from the core it was launched with - plausible answers from a
  stale build. The wrapper runs the emulator from a temporary copy and restarts it whenever the built exe
  gets newer, so a rebuild is picked up by the next tool call; it says so in the answer, and the emulated
  machine has to be loaded again. `ECAT3_MCP_NO_RELOAD=1` keeps only the copy. See `docs/MCP.md`
- **The wrapper also survives the emulator dying**: before, it exited with it, and the server stayed gone for the rest of the client session - no client restarts it by itself. Now a hung request gets an error, the next tool call starts the emulator again, and every start, restart and exit code (a crash is `0xC0000005`) goes to `%TEMP%/ecat3-mcp-reload.log`, since the client hides the wrapper's stderr. A copy of the build is taken before the old process is stopped, waiting for the linker to finish, so a call in the middle of a build does not leave the server empty
