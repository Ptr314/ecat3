## К1801ВМ1 bus timing (`timing = vm1`)

The БК machines time every bus cycle of the processor; the ДВК-3 keeps the old formulas (`timing = legacy`, `reply_delay`), and nothing of the new path runs for it - `k1801vm1::m_timing` is null. `tools/bk-timing/README.md` has how the numbers were obtained and how to rebuild them.

- **The microprogram fixes the gaps, the memory fixes the replies.** The next SYNC comes a fixed number of half clocks after the previous strobe was released, whatever the memory; the strobe is released 3 half clocks after RPLY. `vm1_timing_table.inc` holds these gaps for every form (operation x source x destination addressing, PC modes apart, interrupt entries), taken from a simulation of the reverse engineered chip. It is generated - edit `tools/bk-timing`, not the file.
- **A template runs from the release of the instruction's own opcode fetch to the prefetch of the next opcode**, which is its last step. The emulator does not perform that prefetch: `MemoryMapper::peek_read_device()` answers which memory it would reach, without side effects. The tail of a form (the microprogram still busy after the prefetch) is **added** to the prefetch release, not overlapped - a model that overlapped them made register instructions two windows long on the БК0011М instead of three.
- **Accesses are matched to steps by role, in order**: the instruction stream (opcode, index, `#n`, `@#a` - `pdp11core::m_stream`, set by `read_stream()`) and data separately; the chip and the emulator agree on the order within each, not on how they interleave. Whether a read and the following write of one address are one read-modify-write cycle is the template's call, not the address's: `MOV (R1),@0(R1)` reads its pointer from where it then writes, in two cycles.
- **A memory answers through a `bus-timing` device** its `bus_timing` parameter names; one per controller, and every device the processor can see answering must name it - on the БК0011М that includes the `page-mapper` windows, since `MemoryMapper::last_device` is the window, not the page behind it. The parameter is not called `bus`: `ay8910` already has one.
- **Time is absolute, in 1/12 of a clock** (so the 037 period is 48/64/96 ticks at 3/4/6 MHz), and the phase against the 037 is part of the saved state (`timing_now/start/release`). On the БК0011М the same instruction takes different times by phase, and the measured averages are fractional; a per-form average would lose exactly that.
- **PC as a register operand throws a prefetch away**: OP1 PC, OP2 Rs,Rd and ss,PC with PC among the registers read the word after the instruction (`R_PREFETCH`, answered by the memory the instruction lies in) and then fetch the next opcode anew; OP2 PC,memory does not. These forms are simulated (`gen_all.py`, every copy writes the next address into PC) - borrowed from the Rn form, MOV (SP)+,PC ran a quarter faster than RTS PC, while on the machine the two are equal (`timing-bk0011m-smk-pc`, the POP_vs_RET test). The ВМ2 pays the extra fetch only for a write into PC (MOV (R)+,PC = RTS PC there), not for reading it (`tools/vm2-timing/README.md`)
- **Anything without a template** - an instruction that ended in a trap, JMP/JSR to a register, WAIT, RESET - keeps the legacy count and only moves the chain along (`Vm1BusTiming::idle()`), as does time without the bus (`hold()`, a processor held by `~dclo`).
- **The Verilog bench is exact on static memory only.** With the ВП1-037 it needs the flip-flop both БК put on the RPLY input (`RSYNC = 1` in `tools/bk-timing/tb_bk.v`), and even then it stays 1-3 windows fast on part of the forms at 3 and 4 MHz. That is why the `bus-timing` numbers are fitted to the measurements of real machines, not taken from the bench: they are a chain-model equivalent that includes the flip-flop, not a description of the chip.
- `tests/scripts/timing-bk0010.ecat` / `timing-bk0011m.ecat` run Manwe's speed tests (`tests/files/bk-timing`) and must show the numbers of the real machines; `eCat3-headless --selftest` checks the table and a few forms against the measurements.

## КМ1801ВМ2 bus timing (`timing = vm2`)

The КЦГД processor and both УК-НЦ processors are timed like the БК (`Vm1BusTiming` with `CHIP_VM2`, table `vm2_timing_table.inc` from `tools/vm2-timing`, whose README has the method and the numbers). The ДВК-3 stays `legacy`: its memory needs a reply model of its own first.

- **The ВМ2 halves CLC** (`vm2/hdl/org`: `f1 <= ~f2` on the falling CLC); the synchronous model is clocked by f1 itself, so its half clock is one CLC and the table is in CLC clocks. CLCO is `~f1`. A bench fed CLC instead of f1 runs twice too fast - that is how the first measurement went wrong.
- **It fetches the word after its opcode before its data**: a template runs from the fetch of A+2 to the same fetch of the next executed instruction, and fetches beyond the instruction's own words are steps of role `R_PREFETCH`, placed wherever the chip puts them (device by `peek_read_device(pc)`). An interrupt entry replaces the next-opcode fetch instead of following it; the model does not tell, ~8 clocks per interrupt.
- **RPLY is noticed only on the edges the strobes come on** (every other CLC): a memory answering on the others (the КЦГД window) releases a clock later. `m_start` stays on an odd clock (`align_vm2()`), the КЦГД slot ends are even.
- **Two queues, bus and microprogram**: the tables are measured where the bus waits for nothing (after SEC, static memory); three rules take the rest - the instruction starts (s0) at the previous tail's end, counted from the previous release, or for a form without data cycles (SEC, MUL R, branches) from where a static memory would have released it; the first SYNC is not before the bus allows (3 after a read, 4 after a write); a write before any data read is not before s0 + its anchor (`r2w` of a write step). Validated against the chip on all forms: 3986/3986 in КЦГД video memory, 3976 with only the data there (firmware in ROM), 3968 on static memory, 3946 with only the code slow - the misses are 2 clocks an instruction where the microprogram starts during the previous instruction's last cycle, which templates taken after SEC cannot show
- **The 12-clock window of the КЦГД hides 2-clock errors**: validate a ВМ2 rule with mixed memories (`WINDOW=2/3` of `tb_vm2.v`), not only with everything slow
- **Validate on random mixes, not only on the forms**: repeats and "form; SEC" pairs never put a form that starts early after one that ends with a data read, and the model was right on all of them while 65 clocks off per 300-instruction mix (`gen_mix.py`). Two boundary rules came out of the mixes and are in `vm1_timing.cpp`: 7 clocks after a data read that ended the previous instruction, and a form with a first gap under 3 gets it only after a form without data cycles (else the whole instruction moves). With them: 16 clocks off on average. A per-step reference model (`fit.py`) fits the forms but does not generalise better: the instruction boundary carries hidden microprogram state - the exact way is the chip's own microprogram
- **RPLY on the bench comes 2 ns after the edge that made it**, as on the board (D30 and D19 after the slot end): a reply exactly on the f1 edge is taken a clock earlier and made the KC.SAV loop 96 clocks instead of 132
- **A request that comes up during an instruction is taken after the next one** (`pdp11core::m_irq_seen`, ВМ2 only, IRQ2/IRQ3/VIRQ): on the chip model a write that raises VIRQ or EVNT lets exactly one more instruction run before the entry. Patron's JSR test switches the channel transmitter interrupt on and expects the SOB after that write to run; taking it at once made the loop nest into itself with no count («Overrun», on the old timing as well) - now 797 loops a field against 853 and 848 on two boards
- **SOB that loops fetches its target 15 clocks after the DIN of its prefetch** (`VM2_SOB_TARGET`), not the table's 11 after its release: the microprogram decrements and works out the target while the prefetch waits. On static memory the two are the same; with the УК-НЦ ЦП memory the chip runs SOB R3,. in 28.5 clocks and the gap after the release gave 34 (the machines: 30-31.5). Found by putting the chip and `emu_model.py` side by side on the same memory: every TSSPD form, BR, Bxx and SEC agree within a clock, SOB was the one form that did not
- **RESET holds INIT for 1042 clocks on the ВМ2** (chip model; IRQ.SAV on the УК-НЦ: 153 RESETs in 20 ms, about 1060 clocks, UKNCBTL 1073): `C_RESET_VM2`, the form has no template. It was 30 for every 1801, 25 times too fast
- MUL and DIV take constant time (DIV with V set is its own form, `m_last_div_v`), ASH/ASHC 4 clocks a shift step on top (`m_last_shift`: left n - n, right n - n-1). `eCat3-headless --selftest` checks five loops against the chip, static and КЦГД memory.

## УК-НЦ memory timing (`uknc-ram-timing`)

Both УК-НЦ processors run `timing = vm2`; their RAM answers through a `uknc-ram-timing` device named by `wait` (`ppu-mem` on `plane0`, `cpu-mem` on `cpu-ram`). There is no netlist of the 1515ХМ1-031: the model is fitted to the times measured on a real литера 7 machine (TSSPD by Titus, Patron's tables; `tools/uknc-timing/README.md` has the data, the bench and the fit, `slow-uknc-tsspd` and `slow-uknc-patron-*` the check - their references are the emulator's screens, which catch a silent change, not the machine's numbers).

- **A memory cycle starts on a point of the controller's grid**, at or after the strobe and after the previous cycle of the same processor has let the memory go; RPLY comes `reply` after that point, and the cycle keeps the memory for `read` / `write` / `write_byte` / `rmw_write` / `rmw_write_byte` ns. The ПП (plane 0 is 8 bits wide, a word is two accesses) is synchronous to the 640 ns grid and matches TSSPD to half a clock on average: every read 20 clocks, a word write 16, a byte write 12. The ЦП is about a clock on average (TSSPD 0.97, OP1 1.06, Patron's MOV table 1.67), worst on the forms with two reads (2.8 fast). A fit to all 137 forms (`fit_cpu.py`) finds better averages (160 ns grid, `setup = 80`: 1.05 / 1.37 / 1.32) but MOV R0,R0 then takes 13.7 clocks and SPEED shows 576 thousand register adds a second against 624-672 on the machines - register instructions are the commonest, so the TSSPD fit stays. The two-read forms cannot be raised by the memory at all: on the machine a data read and a data write in one instruction cost less than apart (MOV (R1),R0 33, R1,(R0) 35, (R1),(R0) 50), while the model and the chip model with the same memory have (R1),(R0) 3-4 long and (R1),R0 1-3 short - the chip, not the memory No contention between the processors, the raster or refresh: the measurements show none
- **A WaitSource may tell cycles apart** (`wait_cycle()`, flags `WAIT_WRITE`, `WAIT_BYTE`, `WAIT_RMW`; the default calls `wait_states()`). Only `timing = vm2` passes the byte and RMW flags: `Vm1BusTiming::record()` keeps a byte flag, `write_byte()` of the core sets it. Every byte write of the ВМ2 is the write half of a read-modify-write, and on the ЦП that half keeps the memory a third of a separate write (the row is open)
- **The ЦП's own crystal is not locked to the grid, and an exact ratio is a trap**: 8 MHz against 640 or 320 ns repeats exactly, and a loop of equal instructions sits at one phase for good - MOV (R0),R1 ran 28.5 or 32 clocks by where the program began (the machine: 33.1). `drift = 100` lengthens the grid by 100 millionths so the phase walks through it every few milliseconds, as the two crystals do on the machine. The chip model on the bench shows the same: with the memory clock 0.3% off one way or the other, a form changes by up to 4 clocks, so a ЦП model better than a couple of clocks is not to be had this way
- **`late` is the rounding of RPLY against the ВМ2's edges** (0: a reply exactly on an edge is seen on it). The bench gives 0; with 1 a ЦП read released two clocks later and MOV R0,R0 took 15.4 clocks against 12.3
- **A cheap copy of the emulator's chain is in `tools/uknc-timing/emu_model.py`**, reading `vm2_timing_table.inc`: fitting on it took minutes against hours on the bench, and it reproduces the emulator's TSSPD screens to the hundredth. Change `release_vm2()`/`finish()` and it goes stale
- **JMP/JSR through a register have their own templates**: (PC), (R), (R)+, -(R) are measured with R3 pointing at the next instruction (MOV #,R3; SEC before each copy). JMP (PC) had none and ran the old formulas (17 clocks against 44 in the ПП); (R)+ used to be measured by a jump onto itself in `gen_x.py`, which put a data read into the template - JSR PC,(R0) 62.5 against 51-53 on the machines, the same as JSR PC,(PC) there
- **A (PC)+ destination has its own templates** (170 forms, `gen_all.py` used to skip them and `emit_inc.py` lent them (R)+, which lacks the fetch of the next opcode after the written word - Patron's (PC)+ column ran 12 clocks fast). The chip reads the word as a word of the instruction (`R_STREAM`) and then writes it; the emulator only writes it, so a stream step with no access recorded takes the memory of the next opcode (`finish()`)
- **A write into the prefetched next opcode is fetched again** (`Vm1BusTiming`, every ВМ2, the КЦГД too): through a (PC) destination the microprogram reads the opcode again right after the write (MOV R0,(PC); MOV R0,R0: 38 clocks static, 76 in the ПП as on the machine); through another register it finds out late - the next instruction runs its first cycle, waits 17 clocks, reads its opcode and the word after it again (`F2_REFETCH`, +30 static, TSSPD «пропуск» 144 against 148 in the ПП). Found on the chip model (`tb_uknc.v`); a write into the word after a 1-word instruction's next opcode (A+4) costs nothing
- **Not modelled**: the (PC)-source forms. Not a latch in the 031 (checked: MOVB (PC)+,R0 reads one word twice in a row on the chip and the machine charges three full reads, 59.99 ПП clocks): the real ВМ2 executes MOV (PC),Rn wrongly, by turns reading the next word and running the next instruction twice, or reading the word after it and skipping the next instruction (Patron's TSTPC photos: MOV (PC),R0; INC R0; MOV (PC),R1; INC R1 ... leaves R0 = 005202, R1 = 011702), so TSSPD's 30 clocks a copy is a buffer walked with gaps. The cpu11 model differs from the silicon there; emulating it would change what the instruction does, not its time; ROM and the registers of the ПП (answer at once - nothing measured)

## КМ1801ВМ3 timing (`timing = vm3`)

The ДВК-4 processor takes the time of each instruction from a table of forms (`vm3_timing_table.inc`, generated by `tools/vm3-timing`, whose README has the method): the steady-state period of each form repeated back to back on the chip model (cpu11 `vm3`), with memory replying `reply_clocks` CLC after DIN/DOUT. No cycle chain as on ВМ1/ВМ2: all ДВК-4 memory is one DRAM behind КР1801ВП1-119.

- **The ВМ3 does not halve CLC** (unlike the ВМ2): the model runs on both edges, the table is in CLC clocks
- **Time is not linear in the reply delay**: at a small one the bus hides behind the microprogram, at a large one the bus waits alone (MOV (R),@(R)+: 36, 43, 51 clocks at 2, 4, 6). The table holds the time at `VM3_REF_REPLY` (4) and what 2 more clocks add; another `reply_clocks` is corrected along that slope
- **Fetch-to-fetch is not an instruction's time**: the chip fetches the next word ahead, so with other instructions between the copies (DIV reloads its dividend) the fetch of the next one comes long before the DIV ends. The bench takes the period of the copies and subtracts the fillers (`FILL_FORMS` in `measure.py`); everywhere else the copies follow each other
- **The form programs were written for the ВМ2**, which has no odd-address trap: they store `#1` where later forms take pointers, and the ВМ3 trapped through 4. `tb_vm3.v` keeps the data area 060000-075777 read-only (pointers 070000) and sets no vector 250, which would overwrite form code at 000250
- **ВП1-119 (D14) has no model**: its ERPLY reaches the processor through D38/D40 with no extra synchroniser, and `reply_clocks = _4` is calibrated to the published 800 thousand register-register ops/s (MOV R,R is 7 clocks at 5.5 MHz, 786 thousand)
- ASH/ASHC add 3 clocks a shift step (left n: 3n - 3, right n: 3n + 3), MUL is 60 clocks, DIV 96; traps, interrupts, WAIT, RESET and unmeasured forms keep the legacy count

## 8088/8086 bus timing

`i8086core` (`devices/cpu/i8086core.*`, Qt-free) is one core for both chips; they differ in the bus only (8088: 8-bit, 4-byte queue, a word is two cycles; 8086: 16-bit, 6 bytes). `tools/x86-tests/README.md` has the test runner and where it stands.

- **The bus is timed clock by clock, the inside of an instruction is not.** A bus cycle is T1-T4 plus wait states; the BIU prefetches into the queue whenever the bus is free and the queue has room, and is simulated lazily up to the moment the EU next needs the bus. The EU's own clocks are the Intel table numbers less 4 per transfer the table counts, and a jump subtracts 4 more for the refetch. No microcode: results match SingleStepTests in every case except the flags pushed on a divide error; clocks match about half the time.
- **A REP string instruction runs one iteration per `execute()`**, its decoded form kept in `i8086bus_state`; an interrupt between iterations returns to the prefix right before the opcode, so a second prefix is lost, as on the chip.
- **Wait states come from the memory, not from the address**: `AddressableDevice::wait_source`, set by `wait = <device>`, is a `WaitSource` the core asks after every memory cycle (through `mm->last_device`), with the cycle's T1 as an offset from the point the devices have been clocked to. The Поиск-1 board RAM names the display, a cartridge RAM names nothing and runs at full speed - which is what games relied on.
- **The 8259 hands the 8086 its vector on `~vector`**, a line of its own: `~data` is MODE_R and `change()` on it drives nothing. The CPU drives `~inta` low in `reset()` (after every `load_config`), or the first acknowledge is not an edge and the vector never comes.
- **A far transfer goes through `i8086core::far_jump()`**: the prefetch cycles the BIU began before the jump belong to the old CS and are run to the current clock before CS changes. Setting CS and then calling `flush()` ran them from the new segment - the wrong memory's wait states and a read at a bogus address. `reset()` drops the queue without running them at all
