## Configuration extensions (`.ext`, `.ext.zip`)

**Configuration extensions (`.ext`, `.ext.zip`)** are variants written as edits to a base `.cfg` (`@extends`, `@version`, `dev:prop = value`, `-dev:key [= value]`, `name : type { ... }`, `@before`, `@script`); `docs/CONFIG.md` has the rules. Every machine file goes through one function, `load_machine_description()` (`emulator/config_ext.h`): a `.cfg` as is, an extension parsed by `ConfigExtension` and applied to the parsed `EmulatorConfig` before any device exists, a `.ext.zip` unpacked into `Emulator::cache_path` first. Both formats share the tokenizer (`ConfigReader`) and `parse_parameter()` in `config.cpp`, so a value means the same thing in either. Things to know:
- `@protected` marks a shipped variant: the chooser's Edit and Delete are greyed out for it (`MachineSource::is_protected`, `Qt::UserRole + 3` of the item), Copy is not, and the copy drops the flag. **A Copy of an extension is a new extension standing on it** (`ExtEditModel::open(path, paths, derive)`, `@extends <the copied .ext>`, no edits of its own), not its edits repeated on the bottom `.cfg`: the web page fetches the bundle of the machine `@extends` names, and the plain base's lacks the variant's files (ЯЗС: "File not found flop140.boot.v2.bin"). The copy carries the `@script` of the file copied (only the top file's script runs). A copy of an unprotected extension whose edits are all editor fields (`ExtEditModel::only_field_edits()`: no device blocks, removals, ranges, `@before`) is not stood on: it takes that file's `@extends` and repeats its edits, so a copy of a copy does not grow the chain. **The editor saves every new extension as an `.ext.zip`** (`unique_ext_file()`, the text alone as `<stem>.ext` inside) and edits an archive in place: `write_extension_file()` (`config_ext.h`) replaces the text under its old name and keeps the other members. Since `@extends` takes no archive, an archive is copied only when it is field-only and carries no other files (`ExtEditModel::other_files`); otherwise Copy is refused. **In an archive an embedded file is a member, not base64 in the text**: `write_extension_file()` takes every inline `{base64: ...}` of a Set edit out into a top-level member named after the value (made unique, never `*.ext`; two edits with the same bytes share one) and leaves the plain name in the text; `read_extension_file()` puts the members the Set edits name back inline, so the editor, `other_files` and the Copy rules see them exactly as in a plain .ext. A rewrite drops the members the old text named unless the new text still names them. The point is the chooser: it reads only the system section, and a 2.3 MB text with a disk image inline took 26 ms to inflate and parse per file. `--selftest` (`check_ext_editor_copy`, `check_ext_editor_zip`, `check_ext_editor_inline_zip`) checks it.
- **A device block** (`name : type { ... }`, as in a `.cfg`) adds a device: `ExtEdit::AddDevice`, read by `parse_device_parameters()` - the same code as `load_from_text()`, on the extension's text padded with a line break. A line is a block when a lone word follows the colon and a brace follows it on the same line; every `device:property` line has `=` before any brace. A name the base already has is an error. **`@before`** places the run of edits after it, each in front of the same place so the run keeps its order: `@before dev` for new devices (the order is the clocking and reset order), `@before dev:key [= value]` for range lines of that same device. The first edit of another kind ends the run; an `@before` that placed nothing is an error, and so is a placed line the base already has - a change of options to an existing line written right after a run would otherwise be swallowed by it and moved (that happened while converting `BK-0011M-smk512`: write such a change before the `@before`). A new line written after a run joins it as well, with no error to say so - `Agat-9-pp` put its last range in front of `boot840` that way until `--print-config` showed it. Lines the extension itself added above are not the base's, so one range can go to one device twice (read and write, `Orion-128-m3`). Another part of an interface wired in parts (`~config[3]` beside `~config[0-1]`) is added, not refused as "other modifiers". `ExtEditModel::build()` writes a field of an added device into its block, since it has no base to differ from. `eCat3-headless --selftest` checks the order, the round trip through `serialize()` and the editor; `tests/scripts/ext-add-device.ext` checks a placed range on a running machine
- **An extension may stand on an extension**: `@extends` names a `.cfg` or a plain `.ext` (not `.ext.zip`, not a state), and `load_extension_chain()` builds the chain from the `.cfg` at the bottom, refusing a loop. `MachineSource::base_cfg` is that bottom `.cfg`; the files of an extension in the middle of a chain are found only if they lie by the base or the file opened (`ext_path` is one directory). **`cfg_or_ext()`**: a machine file named `X.cfg` that is missing while `X.ext` exists means `X.ext` - in `@extends`, `MACHINE`, the command line, the ini default - which is what let the variants become extensions of their bases - БК (`BK-0011M-fdd`, `-smk512`, `-mstd` on `BK-0011M.cfg`; `BK-0010-01-fdd`, `-smk512` on `BK-0010-01.cfg`), Агат (`Agat-7-840-pp`, `Agat-7-max` on `Agat-7-840.cfg`, `Agat-9-pp` on `Agat-9.cfg`), Орион (`Orion-128-m3` on `-m1`, `-tZ80` and `-Z80-zexall` on `-Z80`), `Spektr001` on `Radio-86rk.cfg` - without breaking the extensions, recordings and `?load=` links written against their old names (`tests/files/ext-bk-fdd-empty.ext` still says `@extends bk/BK-0011M-fdd.cfg` on purpose). The page does the same in `startMachineFile()`; `package_machines.py` skips an extension built on another one (the bundle would need the chain). The editor compares against `load_extension_base()`. A `.cfg` rewritten as an extension is checked with `eCat3-headless --print-config <file>` before and after: devices in the same order, and inside a device the same lines once sorted stably by name (a changed plain property moves to the end of its device, lines of one name keep their order)
- `-device` (no colon) removes a whole device before any exists. Nothing follows its references: the mapper ranges, links and `mix` entries naming it must be removed by the same extension, or the load stops at the first one (`UKNC-basic.ext` drops the hard disk and the sound module this way - they live in `ppu-mapper`, not `mapper`).
- A key (`name + left_range`) is **not unique** in a base: the БК mapper sends `@memory[177714-177715]` to three devices and `port-ppi` takes `~data[0-7]` from two. A removal picks one by value (`-mapper:@memory[177714-177715] = ay`); replacing an ambiguous key is an error.
- `{base64: ...}` after a file name is decoded by `materialize_inline_data()` into `cache_path/inline/` and the parameter gets the absolute path, so no device loader knows about inline data. `find_file_location()` therefore takes absolute names as they are, and searches `SystemData::ext_path` (the extension's own directory) right after the script's.
- **The cache (`cache_path`: `ext/` unpacked archives, `inline/` base64 data) is cleaned by age** - `cache_cleanup()` (`emulator/cache.*`, plain system calls since the core is C++11) runs at start-up of the window and of the console build and removes what was not touched for 30 days; `unpack_archive()` and `materialize_inline_data()` `cache_touch()` what they reuse, since a reuse that finds the same bytes writes nothing. Not by "mine, now that I exit": a parallel test run loads one archive in several processes at once. **An archive is bounded before anything is written**: 1 GB unpacked (256 MB in the browser, where MEMFS is the tab's memory), 4096 files, 64 MB a file (`ZipReader::max_entry_size`). The sizes in the central directory can be trusted for the sum because `ZipReader::read()` refuses an entry whose data comes out of another size; `tests/files/ext-errors/archive-too-large.ext.zip` (made by `make_archive_limit.py`) claims 2 GB in a 435-byte file, and the runner reads the `// @error` of an `.ext.zip` from the `.ext` inside it
- `sd.system_file` is the file asked for (the `.ext`), which keys `[DeviceOptions]` and `MACHINE` of a recording; `sd.system_path` is the base's directory.
- The `@script` is started by the frontend (`has_embedded_script()` / `load_embedded_script()`), and only when nothing else drives the machine: an explicit `--script`, a replay and an MCP client win.
- `ConfigReader::next()` drops the last character of a text that ends without a line break. A `.cfg` always ends on `}`; the extension parser appends `\n` to each property it tokenizes.
- **The editor** (`dialogs/exteditorwindow.*`, opened from the machine chooser) shows what `ComputerDevice::get_config_fields()` returns. `collect_config_fields()` (`emulator/config_fields.h`) constructs the machine's devices through `register_all_devices()` on a private `DeviceManager` and never calls `load_config`, so `get_config_fields()` must read `cd` only, and a constructor must stay free of side effects (and leaks: the editor builds a machine every time it opens). `ExtEditModel` is the Qt-free part: base and current values per field, `build()` rewrites only the edits of known fields and keeps the rest and `@script`. A new editable parameter is one override in the device, no GUI change.
- Tests: `tests/scripts/*.ext` run as their own script, `tests/files/ext-errors/*.ext` must fail to load with the `// @error` text on stderr (headless only, see `tests/README.md`).

## Saved state (`.ecats`, `.ecats.zip`)

A snapshot of a running machine, accurate enough that the guest cannot tell it was restarted. Written by `SAVESTATE` (script) or File > Save state, opened like any other machine file — `is_machine_file()` accepts it, so every frontend including `index.html?load=` works with no code of its own. `docs/CONFIG.md` has the format.

**It is self-contained.** The file carries the machine's *resolved* configuration (`@config`, written by `serialize_config()`), and the archive carries every file that configuration names — ROMs, key tables, the keyboard drawing, the charmap — plus the media. So a snapshot does not break when a ROM or an image elsewhere changes. `docs/CONFIG.md` describes the two forms: `.ecats.zip`, and a bare `.ecats` with a `<stem>.files/` directory beside it, whose member names carry that prefix so both resolve through `MachineSource::ext_path`.

- **Both sections are `.cfg` syntax**, read by `EmulatorConfig::load_from_text()` — the tokenizer, ranges, `{extended}` blocks and comments come for free. A large buffer is `key = {hex: ...}`, an addressed dump where `*` means "the line above repeats to the next stated address", so untouched RAM is three lines.
- **`StateWriter::num()` always writes a base prefix**, decimal included (`_123`), unlike `format_number()`. A state of a decimal-radix machine would otherwise read differently from one of a БК.
- **A line is `~name = <value> {old = …, edge = …, mode = …}`**, and `off` means `_FFFF`, "nobody is driving this". Written as a number it would either be an unreadable row of ones or, masked to the line width, something else entirely.
- **Save is on the emulation thread.** From a script it is synchronous inside `tick()` (between two instructions, so the same script saves the same state); from the GUI it is a request flag consumed at the top of `timer_proc()`, the `m_screenshot_requested` pattern.
- **Restore is inside `Emulator::run()`**, between `reset(true)` and the loop: everything is built, nothing has been clocked, and that thread owns all of it. Five passes — device options (a `connector` plugs whole devices, so it must be first), `load_state()` per device, then `state_restored()`, then `clock_counter` and the domain positions. Because it is in `run()`, no frontend needs a line for loading.
- **`ClockDomain::norm` is rebased on save** (`base = min(norm)`). Restored raw, the first `timer_proc()` finds every domain past its target and runs `norm -= target` on a `uint64_t`, which wraps and freezes the machine for good.
- **`CPU::reset_mode` must be cleared in `load_state()`**: a reset is deferred to the first `execute()`, which would throw the restored registers away.
- **A device's `load_state()` must not drive a line.** The base class restores the device's interfaces first (through `Interface::restore()`, which assigns without cascading); anything driven afterwards would reach devices that have not been restored yet. Work that needs every device restored goes in `state_restored()` — `MemoryMapper` invalidates its page cache there, `GenericSound` refreshes its mix, `GenericDisplay` marks the surface for a full repaint (the Орион and the Ириша paint on every write to video memory and would otherwise show the picture of the run that took the snapshot).
- **Whatever a device derived from a line, it must derive again in `state_restored()`.** `Interface::restore()` assigns without firing `interface_callback()`, so anything a device computed *from* an interface and cached keeps whatever the reset left in it. This is invisible to every field a script can read — the bug is in the cached copy, not in the line. `UKNCSound` cached "does my level move on its own" there (`m_self_volatile`, from the grid bits of 177716) and the mixer held a stale level after a restore: the tone came back coarse and aliased until the program next wrote the register. `tests/scripts/state-uknc-sound.ecat` and the `sound.moving` field are the guard.
- **Media are state, not configuration.** A device whose `state_owns_file()` claims a parameter (`fdd:image`, `uknc-hdd:image`, the tape) has it dropped from the `@config` it carries, and writes its live contents into the bundle instead — raw, not through `save_image()`, which converts by extension. A snapshot taken right after a sector was written holds it in the `BKFDC` track cache and the `FDD` buffer and nowhere on disk; `BKFDC::save_state()` calls `flush_all()` first for that reason. `tests/scripts/state-bk-0011m-disk.ecat` is the test.
- **Host-side input is never restored** — held keys, pending mouse motion. Nobody is holding anything when a snapshot is opened, and a key that came back down would stay down forever. The machine side (the code register, the ready trigger) is restored, so a program waiting for a keystroke sees what it saw. Debugger breakpoints and the step mode are left out too: a state that opens already stopped is not what "continue from here" means.
- **A missing key keeps what the reset gave**, an unknown key is ignored and collected in `Emulator::state_report()`. Diagnostics never reach stderr — any output there fails every regression test.
- **A `.ecats` cannot carry `@script`**: a file fetched from a link must not run anything.
- Tests: `tests/scripts/state-*.ecat` load a committed fixture from `tests/files/*.ecats.zip`, made by hand with the `tests/files/make-state-*.ecat` generators. The snapshot itself is *not* a byte-comparable artifact — the instruction a `WAIT` lands on is host-timing dependent — so the tests compare the screen and memory that come back.
- `eCat3-headless --selftest` checks the invariants this rests on: `serialize_config()` round-trips every `.cfg` of the installation, `ZipWriter` round-trips through `ZipReader`, and the hex dump round-trips with its folding.
