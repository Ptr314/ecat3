## Device-based architecture

The emulator uses a device-based architecture where computers are built from interconnected components:

- **CPU Layer** (`emulator/devices/cpu/`): i8080, Z80, 6502, 65C02, К1801ВМ1 (PDP-11), 8088/8086 - independent instruction execution engines
- **Memory Mapper** (`emulator/devices/common/page_mapper.h`): Central address-space manager that routes memory access to correct devices
- **Device Types**:
  - **Common Devices** (`emulator/devices/common/`): Generic peripherals (RAM, ROM, i8255, i8253, WD1793 and GMD70 disk controllers, etc.)
  - **Machine-Specific Devices** (`emulator/devices/specific/`): Agat/Orion/Irisha/БК display controllers, БК timer, FDC variants
- **Interface System**: Devices connect via interfaces (analogous to real hardware buses). Interfaces support bit-range connections and inversion.

Computer configurations live in **`.cfg` files** (text format, see docs/CONFIG.md for syntax). During startup:
1. Config parser reads device definitions and their parameter values
2. Devices are instantiated and registered in device list
3. Interface connections are established
4. System runs with defined architecture

This means most hardware behavior is **not hardcoded** - it's defined via config files. New machines can be added by creating `.cfg` files without code changes.

## Interfaces

Interfaces are declared as `Interface` member variables in device classes. The `Interface` constructor auto-registers with `InterfaceManager` (see `core.h` for its arguments: size, name, mode, `callback_id`).

The `callback_id` is the key reactive mechanism: when a connected interface changes value, `device->interface_callback(callback_id, new_value, old_value)` fires. A `callback_id` of 0 means no callback.

Interface wiring happens in `ComputerDevice::load_config()`, not constructors. Config parameters prefixed with `~` are parsed as connections. The `!` prefix inverts the signal. Bit-range syntax `[lo-hi]` handles width differences via mask/shift.

Propagation is **synchronous**: calling `interface.change(value)` immediately cascades through all linked interfaces and triggers callbacks. No event queue.

Config example:
```
memory_mapper: page-mapper {
  ~address = cpu.address
  ~data_read = cpu.data_read
}
ram1: ram {
  size = 64k
  ~address[0-15] = memory_mapper.address[0-15]
  ~data = memory_mapper.data
}
```

- **An interface line has no wired-AND: two writers overwrite each other**, so a second interrupt source on a line cannot simply be linked to it. The Агат ЯЗС (`agat-yazs`) takes the rest of the machine's IRQ on `~irq_in` and drives `cpu.~irq` with both (`Agat-9-yazs.ext`); a new open-collector source does the same
- **Two links between the same pair of interfaces with different bits are two links**: `Interface::connect()` used to treat any second link between two interfaces as the reverse half of the first and drop it, so `~ir[6] = pit.output[1]` after `~ir[0] = pit.output[0]` silently never reached the 8259 (the Поиск-1 keyboard is polled on IRQ6). The duplicate check now compares the bits too; the regression suite passed unchanged after the fix, so no earlier machine depended on the dropped links
- **`Interface::mask` is set by the constructor now**, not only by `set_size()`. An interface whose size never changed used to carry whatever was on the stack; nothing read it until a saved state needed the width of a line, and then the same machine wrote two different files on two runs.
- **Port access strobe**: `Port::get_value()`/`set_value()` toggle `i_access` (0→1 pulse) on every access. Devices connected to `port_name.access` receive this as a trigger. Used for keyboard reset, sound toggle, etc.
- **`PortAddress` stores address, not data**: `PortAddress::set_value(addr, val)` drives `i_data` with the *address*, not the value. Models Apple II / Agat soft-switches where the accessed address encodes the command.
- **`force` parameter**: `set_value(addr, val, force=true)` comes from the memory editor and `COMMAND dev.set`; the editor (the debugger's dumps, `MemoryMapper::poke()`) writes only where `debug_writable(address)` is true - `Memory`, the windows into it (`PageMapper`, `PlanePair`, the Агат-9 mapper outside C0xx, the memory of `smk512`/`a16m` outside 177130-177133, the КЦГД window), so a register is shown and never acted on from there; a new memory-like device overrides it. Its meaning is the device's: i8255 and `PoiskFdcControl` update internal state without driving interfaces, ay8910 writes even when unplugged, and most register devices (DL11, 1801ВП1-033, УК-НЦ channels) ignore it and act as on a bus write, which tests rely on (see `testing-and-debugging.md`).
- **ROM has `auto_output = true`, RAM does not**: ROM responds to address bus changes by outputting data on `i_data` automatically (combinatorial lookup). RAM requires explicit `get_value()` calls through the mapper.
- **The bits of the i8255 upper half `CH` are numbered by direction**. An input (another device drives the port) is numbered by its place in the whole port: `~CH[4]` is PC4, `~CH[0]` names nothing and silently drives nothing - which is how the tape first never reached port 62h (`interface_callback()` takes `new_value & 0xF0`). An output is numbered within the half, since the port drives `registers[2] >> 4`: `dev.CH[3]` is PC7, as in the УК-НЦ printer strobe `~strobe = !pp-printer.CH[3]` and the `port-user.CH[3]` examples of `docs/CONFIG.md`. "Fixing" such a line to `CH[7]` makes it drive nothing. `CL` is bits 0-3 both ways

## Initialization

1. **Constructor**: Creates `Interface` members (auto-registered), sets defaults. Must NOT reference other devices (they may not exist yet).
2. **`load_config(SystemData *sd)`**: Base class processes `~` interface connections. Subclasses load ROM images, resolve cross-device references by name, call `init_sound()`, etc.

- **`Emulator`'s constructor takes work, *data*, software, ini** - not the order the members are declared in. Swapping the middle two is silent until a machine whose images live under `software/` reports "Disk image file not found".

## Emulation loop, clock domains, speed

Emulation runs in a dedicated high-priority thread (not QTimer). `Emulator::run()` spawns two raw threads: `emulationThread` (TIME_CRITICAL priority on Windows, SCHED_FIFO on POSIX) and `renderThread`. The emulation loop polls wall-clock time with microsecond resolution, converts elapsed time to cycles of the master processor, and calls `cpu->execute()` which returns cycle count. `DeviceManager::clock(domain, counter)` then clocks the devices of that domain whose `clock()` does something — the per-domain `clocked_devices` lists built by `load_devices_config()` from the `m_clocked` flag every such class sets in its constructor. Processors are not in those lists: each is clocked by its own `execute()`.

**The render thread shows a frame when the display reports it whole** (`GenericDisplay::frame_complete()` moves `frames_done()` and raises `Emulator::m_frame_event`, a `compat_event` the render thread waits on; not more often than every 8 ms), and falls back to a fixed 50 Hz tick only for a stopped machine. Every display reports frames: a raster one where its picture ends (БК, УК-НЦ, Агат, ВГ75, Поиск-1, the КЦГД at its last visible line), a terminal on its 50 Hz blink counter (КСМ, 15ИЭ), and one with no raster in the model (Орион, Ириша; `own_frames()` false) gets them from `Emulator::timer_proc()`, every 20 ms of `clock_counter`, checked once a slice - those two displays were taken off the clocked list on purpose and must stay off it. A new display either calls `frame_complete()` and answers `own_frames()` true, or does nothing and is covered by the emulator. A free 50 Hz tick against the machine's 50.08 Hz dropped 18% of the УК-НЦ frames and added 12 ms on average to what the mouse moved - measured by timestamps along the whole path, from the host event to `frameSwapped`. **Never wait for something short with a sleep on Windows**: Windows 11 may end `Sleep(1)` / `sleep_for(1ms)` on its 15.6 ms tick despite `timeBeginPeriod(1)` - it does not promise a fine timer to a process without a visible window, or with a covered one (measured: 15.6 ms a call in a console test, and in one of two windowed runs) - so a 1 ms poll showed the frame 8 ms late on average; the event wakes the thread when the frame is done. Measured with the fix, the host's share from the event to the swap fell from ~37 ms to ~10 ms, of ~40 in all (the УК-НЦ MOUTST: ~29 of it is the program polling once a frame and drawing into the next one). A display with its own `frame_complete()` (the ВГ75 sink) calls the base one too. The page runs the same loop: its tick came out at 15.7 / 31.2 ms in Chrome too, and with the event `putImageData` follows the machine's frames (20.0 ms on the УК-НЦ, 20.5 on the БК; measured with a hook on the canvas over CDP). `GenericDisplay::set_renderer()` marks the picture invalid: a display that redraws only changed lines (the Поиск-1) otherwise left a new surface black for up to a second after a resolution change, which the early tick used to hide. The OpenGL window does not wait for the retrace on the frame swap (`setSwapInterval(0)` on Windows and macOS, where the compositor syncs anyway): the wait held the GUI thread 12 ms on average, and the mouse with it. The host mouse steps go to the machine with each host event; the 10 ms timer only writes the recording's `MOUSE` lines.

**Clock domains.** `Emulator` keeps one `ClockDomain` per processor: the CPU, a `scale` and a position `norm`. `scale` is `LCM(all frequencies) / this frequency`, computed once in `run()`, so positions of different processors are comparable as whole numbers — 8 MHz and 6.25 MHz give scales 25 and 32, the true 32:25 interleave of the УК-НЦ. Each pass `timer_proc()` runs whichever domain is furthest behind, adds `cycles * scale` to it and clocks that domain's devices; what a domain overshoots the slice by is carried into the next one. With a single processor the LCM is its own clock, every scale is 1, and the arithmetic is exactly the old `local_counter` loop — which is why the whole regression suite has to pass unchanged after touching this. A device joins a domain through `clock_source` (`ComputerDevice::load_config`), which also sets its `m_system_clock`, so anything converting real units into cycles uses the frequency of its own side of the machine. `clock_counter` — emulated time for scripts, `WAIT` and recordings — counts the master only. `deploy/computers/bk/2cpu-test.cfg` + `tests/scripts/boot-2cpu.ecat` is the test that the ratio really holds.

**Emulation > Speed** (`Emulator::set_speed()`, quarters: 1 = 0.25x ... 40 = 10x, up to 4000 from a script, 0 = as fast as possible - no wall clock, a fixed 20 ms slice, the elapsed wait skipped, silent to the device; script verb `SPEED`, `--speed` of both builds, `run_tests.py` runs at max by default (`--speed 1` for real time), parsed by `Emulator::parse_speed()`; ini `[Core] speed` (the choice of the menu) and `[Core] turbo` in the window - the Turbo button right of Stop applies that speed while pressed and 1x while released, and a choice in the menu presses it unless it is 1x (`MainWindow::apply_speed()`); localStorage `speed` and `wasm_set_speed` on the page; the console build only by --speed and SPEED) scales the wall time of a slice in `slice_ticks()`, nothing else: every processor and device keeps its clock, so the whole machine runs faster. Raising a processor's `clock` instead is not a speed control - the devices and the bus timing stay behind (the БК floppy stops working). At 4 the formula is the old one byte for byte; at any other speed the remainder is carried and a slice is capped at 50 ms of emulated time (a host that cannot keep up would otherwise make every slice longer, and `invoke()` waits for the slice). The audio device's stream is resampled by `GenericSound::s_speed_q` (averaged or repeated, so the pitch follows the speed); a WAV and a video take every sample. At any speed but 1x a pending `SCREEN` holds emulated time (`m_shot_hold`) until the render thread has taken it, or MAX would run a second past the moment asked for; 1x keeps running meanwhile, which is how the references were taken. A field a script reads must not come from the render thread for the same reason: `I8275Display` answers `resolution` from the last whole frame, not from the surface. Nor may a change of the screen size wait for the render thread: `I8275Display::frame_complete()` declares the size of the frame (sx/sy) itself, so the surface is resized and drawn on one pass - left to `follow_resolution()` in `render_all()`, the first pass only declared it, and a `SCREEN` on that pass saved the picture of the old size (`work-argo-zx`); `BKDisplay` applies a colour/mono switch at the end of the picture on the emulation thread (`apply_mode_switch()`, also from `get_screen_constraints()` for a stopped machine, both under the surface lock), not only when the render thread asks for the size (`work-bk-0011m-screen` read the old width). The size changes through `change_resolution()`, which stops drawing until the render thread has replaced the surface. With both, the suite passes at `--speed max` in under a minute (533 s at 1x, `-j 8`).

**The high precision mode of a display** (`GenericDisplay::precise_available()` / `precise()` / `set_precise()`, field and command `precise`, menu Display > High precision, ini `[Display] precise_<config>`, on when absent, applied by `Emulator::apply_saved_device_options()`; `<config>` is `Emulator::settings_key()`, the machine file name up to its first dot, shared with the device options so the window and the core write and read the same key): a raster display that has it sets `m_precise_available` in its constructor and overrides `RasterDisplay::BEAM(line, clocks)`, called after every `clock()` of a line that started with the mode on (`m_beam`, taken at the line start so no line is drawn half one way). Off, the cost is that one flag test an instruction - keep it so: no virtual call on the path. Only `BKDisplay` has it (see machines.md). Not saved state: a setting, like the speed.

Two properties of that loop are deliberate and easy to "fix" into a regression:
- **The loop spins.** Between slices it calls `yield()` rather than sleeping, so the thread holds a core even while the CPU is stopped. A `sleep_for` needs `timeBeginPeriod()` on Windows (the default timer granularity is ~15 ms, and 15 ms chunks of emulated time cost audio quality), which is what the removed `Core/TimerResolution` and `Core/TimerDelay` settings were once for. The regression suite cannot see the difference — it measures emulated time, not smoothness — so this is a change to make by ear, not by test.
- **The catch-up is not capped.** The whole interval since the previous slice is replayed, however long. A ceiling makes emulated time fall behind the wall clock whenever the host is busy, which breaks a parallel test run (`-j4`) in a way that looks like random screenshot and timeout failures. What a 32-bit counter used to break — a slice longer than 2^32 cycles never ending — is fixed by the domain positions being 64-bit, not by a cap.

- **A device is clocked in the order it is declared, and for a device that reads another's fast-moving state that order is part of the wiring**: the slice is one instruction (a dozen ticks), and anything moving faster than that — the УК-НЦ tone grid steps every 12 ticks — cannot be sampled at the slice boundary, it has to be integrated over the slice. `UKNCSound` does that from the timer's step log, so it is declared *after* `pp-timer`: declared before, it would average the previous instruction's slice and weight it by this one's, which is audible in the pauses of a melody. There is no mechanism that enforces this; the config says why.
- **The debugger pauses the machine with a flag, not with the processors' modes** (`Emulator::debug_pause()`, `m_debug_paused`): `timer_proc()` moves every domain to the end of the slice unclocked (`debug_hold_domains()`), so a К1801ВМ1 held by ~dclo, whose `execute()` spends cycles even when stopped, stands still too, and the modes a script gave the processors survive. A step (`debug_step()`) is made in time by `debug_step_slice()`: the domain furthest behind runs, as in the loop, until the chosen processor has executed one instruction (`waiting()`: past WAIT/HLT to the interrupt) and is the one furthest behind again; a processor stopped on its own moves along for the step. While the debugger is attached (`debug_attach()`), a processor that stops in `DEBUG_BRAKES` sets `break_hit`, and the machine pauses in the `counter == 0` branch - when the others have caught up with it, so nothing is added to the per-instruction path. Nothing stops a processor that is `waiting()`: after WAIT/HLT its PC already shows the next instruction, which a breakpoint there must meet after the interrupt, not on every idle step (`waiting()` is asked only on a hit). `TEMP_RETURN` at the address after the call counts only with the stack at the call's level: a recursive call comes back there deeper. A script's `cpu.pause` pauses at the instruction it runs at: the flag is checked after `script->tick()` inside the loop. Step over (`TEMP_RETURN`: the address after the call, or the stack back at its level after a return instruction - `JSR R5` returning past its arguments, recursion, an interrupt taken before the call, a routine popping its own data) and step out (`TEMP_OUT`: the stack above its level after a return instruction, `CPU::returned()` decodes it only then) are `CPU::set_temp_break()`; a repeated instruction (8086 `rep`, Z80 `LDIR`...) is stepped over to the next one. A processor's breakpoint list is a vector with its room reserved (`MAX_BREAKPOINTS`): the window reads it from its thread. `tests/scripts/work-uknc-debugger.ecat` holds the interleaving of the two processors
- **`DeviceManager::clock(domain, counter)` skips processors by class, not by index**: devices are stored in declaration order, and a CPU is recognised by `device_class == "cpu"` (set in `CPU::CPU`). Clocking a processor here would double-count the cycles its own `execute()` already returned. Slots 0 and 1 used to be reserved for the names `cpu` and `mapper`, which is what made a second processor impossible.
- **`clock` parameter has dual meaning**: For a processor it's the absolute frequency in Hz. For all other devices, `clock = 1/2` sets a multiplier/divider ratio relative to that device's clock domain. Both constructors read the parameter, so `CPU::CPU` resets `clock_miltiplier`/`clock_divider` back to 1 after the base class has taken the frequency for a multiplier.
- **A bus master stops the CPU with `cpu->hold(cycles)`**: `CPU::hold()` (`core.h`) banks cycles that `execute()` hands straight back to `Emulator::timer_proc()` instead of running an instruction, so emulated time and every clocked device move on while the processor stands still — HOLD/HLDA, and no change to the emulation loop. `i8275` is the only user: it charges four system clocks per ВТ57 cycle, 2340 of them a frame, which is the 26% of a Радио-86РК the screen refresh really costs. `cpu.hold` reports the running total to scripts. Not to be confused with the wd1793 trick below, which does not spend emulated time at all.
- **Wait states are modelled by running the device forward, not by stalling the CPU**: `wd1793` `sync = <address mask>` marks a data-register copy whose access (Irisha KNGMD port 37) advances the controller state machine until DRQ/INTRQ before returning. Use the same trick for any device whose READY line holds the CPU.

## Memory mapper

CPU holds a direct pointer `mm` to `MemoryMapper` (set in `CPU::load_config()`). All memory/port access goes through this pointer, **not** through the interface system:
- `read_mem(addr)` → `mm->read(addr)` → `MemoryMapper::map()` finds matching `AddressableDevice` → `device->get_value(addr)`
- `write_mem(addr, val)` → `mm->write(addr, val)` → `device->set_value(addr, val, false)`
- Port I/O: `read_port()`/`write_port()` → `mm->read_port()`/`mm->write_port()` (same dispatch via separate port map)

`MemoryMapper::map()` does linear scan of ranges checking: config mask match, address in range, address mask filter, and read/write mode. Returns `_FFFF` (all bits set) when no range matches. The four emulation entry points go through a page cache first, see below; everything else (the debugger, `mmwindow`, scripts) keeps using the scan.

**Word access**: CPUs with a 16-bit bus (the К1801ВМ1 family) use `mm->read_word()` / `write_word()`, which map once and call `AddressableDevice::get_value_word()` / `set_value_word()`. The default implementation composes the word from two little-endian byte accesses, so byte-oriented devices need no changes; `Port` and `MemoryMapper` override it to stay atomic. A `port` with `size > 8` is a true two-byte register: byte accesses pick a lane by address bit 0, word accesses see the whole thing.

- **`cancelinit`**: MemoryMapper feature where range index 0 (marked `[*]` in config) is active only after reset. Flips off when CPU reads an address matching the cancelinit mask. Models Agat boot-ROM-only-at-reset behavior.
- **A 1801 word cycle at an odd address reaches a byte-wide device at that address**: the processor puts the address on the bus as it is, a memory ignores A0 and moves the word at the even address (the БК0011М БЕЙСИК tests a byte variable with a word TST of its odd address). `pdp11core::read_word_checked()`/`write_word_checked()` no longer mask the address; `k1801vm1::read_mem_word()`/`write_mem_word()` send an odd one to `MemoryMapper::read_word_odd()`/`write_word_odd()`, which give a device whose `byte_wide()` is true (the `i8255`) the odd register on the low byte (high byte 0) and everything else the even word through `read_word()`/`write_word()`. The bus cycle is timed and a timeout reported at the even address. `MemoryMapper::read_word()` is untouched: an x86 reads an unaligned word with it. The `i8255` also answers a word at an even address with that one register (`get_value_word()`/`set_value_word()`): RBTRON.SAV on the УК-НЦ drops the printer strobe with `BIC #200,@#177102`, and as two bytes the second wrote the control word back and cleared the ports. The ВМ3 (`vm3_read()`) is not affected
- **`portstomemory = 1`**: Routes port I/O to the memory address map instead of the port map. Used by Agat-9 (6502 has no separate I/O space).
- **The mapper resolves a whole 512-byte page at once, and the config value is part of the tag**: `MemoryMapper::find_page()` / `fill_page()` (`core.h`, `core.cpp`) answer `read`/`write`/`read_word`/`write_word` in O(1) when, of the ranges matching the current config, at most one intersects the page — and that one covers it entirely, filters no addresses of its own (`address_mask`) and does not continue a read (`or_read`) or a write (`through`). Anything else marks the page `uncached` and it goes the old way, which is what the I/O page of every 1801 machine does. Because the config value sits in the tag, **a configuration change invalidates nothing** — that matters, since `interface_callback` fires on every write to the config line, not only on a real change. Anything that ever changes `ranges[]` or `first_range` must call `invalidate_pages()`; today that is `load_config`, `reset()` and the `cancelinit` flip. 512 bytes is not arbitrary: it is the largest page that keeps the УК-НЦ ROM window (ending at 176777) whole and leaves 177000-177777 in one page
- **A `routed = 1` range asks its device, address by address** (`AddressableDevice::route()`): answer, pass the address on to the ranges after it as if the range were not there, hold the bus with no reply, answer a write and pass it on (like `through`), or answer a read OR-ed with the ranges after it (like `or_read`). `route()` must be side-effect free - `map()`, `map_read()` (which then skips its read-modify-write memo), `responds()`, `fill_page()`, `peek_read_device()` and the debugger all ask it. The page cache asks it once per 512-byte page (at both ends, both ways) and keeps an ANSWER / TIMEOUT / PASS-both-ways answer, so the device must answer uniformly within a page except where it answers THROUGH or OR (those pages stay uncached), and must call `MemoryMapper::routing_changed()` whenever its answers change - the СМК does on a mode change. `map()` reports the route through its optional last argument, so the read and write loops do not ask twice. The СМК-512 of the БК (`smk512`) is the user: one range over 100000-177777 placed before the machine's own memory, which by its mode covers, switches off or leaves alone. Its spec is the gid АльтПро test v4.77F (tables `CODS`/`CODSR11`), run by `tests/scripts/smk-altpro-*.ecat`; the replica's RAM beats ROM and machine RAM on a read but is OR-ed with the I/O registers (the test polls 177716 in mode All, where its own sync word lies underneath), and the machine starts at 166400 because in SYS the ROM covers 177716 too
- **A write reaches only the first matching range, unless it is `through = 1`**: `@memory[177714-177715] = ay {mode = w, through = 1}` followed by `port-ppi-out {mode = w}` delivers the write to both. Reads are unaffected; `LOG mapper.map` marks such ranges with `through`
- **Bus timeout is a feature, not an error**: `k1801vm1` aborts the current instruction and traps through vector 004 when an address matches no range. The БК0011М ROM probes for installed memory blocks exactly this way, and without the trap it never starts БЕЙСИК. `MemoryMapper::responds()` answers whether anything is mapped.
- **A register whose read does something must override `get_direct()`**: the dump window, `LOG dev.value` and `MemoryMapper::get_direct()` (which the debugger's dump goes through) read with it, and the default forwards to `get_value()`. Without an override, looking at a channel data register takes the byte, a timer read reloads the counter. `value16` still reads the way the processor does (`get_value_word`), side effects included

## Devices

**Reserved device names:** Every config MUST have a device named `"cpu"` and one named `"mapper"`. The emulator also looks up `"display"` and `"keyboard"` by name. These four names are hardcoded in `Emulator`; everything else is found by class (`find_devices_by_class()`): the drives (`fdd`), the tape (`tape`), the audio outputs the volume control reaches (`sound`, set by `GenericSound`). `"cpu"` is the *master* processor — its frequency is the machine's time base (`clock_counter`, script delays, `WAIT`) — and `"mapper"` is the default address space a processor gets. A machine may declare more processors; see Clock domains below.

- **`_FFFF`** (`(unsigned int)(-1)` from `utils.h`): Represents "all bits set / no device responded / high-impedance". Returned by `MemoryMapper::read()` on miss; initial value of all interfaces; broadcast by `MODE_OFF` interfaces.
- **What the guest may do and a device does not model is counted, not fatal**: `ComputerDevice::note_unsupported(what)` bumps the `unsupported` field and keeps the text in `unsupported_last`, and the device carries on as close to the chip as it can (the ВТ57 answers a missing register with nothing, the ВВ55 treats port A in mode 1/2 as mode 0, the ВГ93 answers Read Address/Track with not-ready). `DeviceManager::error()`, which stops the machine, is for faults of the emulator itself - a drive asked for a byte outside its sector. A real machine never freezes because a program touched a register, so neither should the emulator; the counter keeps the inaccuracy visible to a script or an MCP client
- **Device lookup is O(N)**: `DeviceManager::get_device_by_name()` does linear scan. Use `required=false` for optional devices to get `nullptr` instead of exception.
- **`-N` entries in `get_registers()` / `get_flags()`**: pairs whose name starts with a dash carry no value — they are blank separators between register groups, drawn (skipped) by `KeyValueArea::paintEvent` and filtered out by the script engine's `pairs_to_string`. Anything else consuming those lists must skip them too.
- **`fdd` `layout` picks the track order by file extension** (`cpm:sides|dsk:cylinders`); `save` to an extension with the other order reshuffles tracks on the way out, so the drive doubles as an image converter. Only the sector (`logical`) path honours it; MFM/whole-track paths index `track_indexes[track*sides+side]` directly.
- **Input devices sharing one port go through a `connector`**: interface links are last-writer-wins, so a joystick and a mouse on the same `~data` lines are both `PluggableDevice`s and the `connector` (`devices = joystick|mouse`, `default = none`, `COMMAND up.plug(name|none)`) plugs one. An unplugged device must drive 0 when it leaves, or the port keeps its last value. On the БК the socket is empty by default: a joystick always on the host arrows made programs that poll 0177714 (the TDR demo) run the cursor into the edge
- **Sound uses `AudioDriver` abstraction**: `GenericSound` uses a pluggable `AudioDriver` (`emulator/audio/audio_driver.h`). Default backend is **miniaudio** (`audio_driver_miniaudio`); SDL2 audio is optional via `USE_SDL_AUDIO` CMake flag. Sound devices inherit from `GenericSound` and override `calc_sound_value()`.
- **Latency is the period of the audio device** (`[Sound] period` of the ini, ms; 10, and 40 in the XP build and on the web page, whose ScriptProcessorNode runs on the busy main thread; a power of two of samples there and under SDL): miniaudio holds three periods, `GenericSound`'s buffer one more, but no more than 15 ms. It was 2048 samples at 22050 Hz (93 ms) and the sound came a third of a second late. The data callback gets one whole period; the level the buffer is left at is kept near `m_target` (one period, at most 15 ms: the reserve is against a late slice of the emulation, which runs in 1 ms slices whatever the period, while a late device only makes the buffer grow; on the web page it was 46 ms and is 15, measured on the page with a probe of `buffered`/`underruns`: no underrun in 20 s, also with the main thread blocked 40 ms of every 100): above twice the target or below half of it, `push_frame()` drops or doubles one frame in 64 until it is back (the producer's steady_clock and the sound card drift apart by up to 0.2%). A period the buffer cannot fill takes nothing and plays the last frame fading out, so what has arrived becomes the reserve (the old code played the part it had and ran dry again on the next period - an underrun a second). Only a burst past the capacity (five periods + 50 ms) drops everything but the target at once. Check by `buffered`/`underruns`/`overflows` of the output from a script run with sound (the headless exe without `--no-sound`, at 1x): the suite runs silent and cannot see any of it.
- **`GenericSound` opens the device at `sample_rate` (default 22050 Hz) with a low-pass `lpf` (default 5000 Hz, 0 = off)**: everything above 11 kHz is gone in the window, which a beeper does not miss and the Агат ЯЗС does (`Agat-9-yazs.ext` sets 44100). A cutoff at or above half the rate disables the filter (`m_lpf_on`): `ButterworthLowPassFilter::setup()` leaves its coefficients unset for it, and the machine went silent. `lpf_editable = 1` offers the cutoff in the configuration editor (only the ЯЗС machine). **A source may be stereo** (`SoundSource::sound_stereo()` / `sound_sample_left()`): the output then opens two channels and every mono source sounds in both; `sound_sample()` stays the channel a mono output takes, so it must sound right alone - the ЯЗС's two line outputs are opposite in the treble, and summed they cancel it (why the ЯЗС defaults to mono, `stereo = 0`). Video capture stays mono
- **`VideoRenderer::fill()` invalidates `render_pixels` under the OpenGL back end**: it reaches `QImage::fill()`, which detaches the implicitly shared image the widget still holds, so the renderer carries on with a fresh buffer while the pointer `GenericDisplay::set_renderer()` captured keeps addressing the copy the widget is about to free. `I8275Display` blacks the screen out by writing `render_pixels` itself for that reason. The symptom is heap corruption reported in an unrelated thread, minutes later — and only in the windowed MCP build, because there the window (and the surface) is created when a machine is asked for, while `--script` builds it up front.
- **A renderer's `get_screenshot()` must return raw RGBA**, `sx*sy*4` bytes: `Emulator::store_screenshot()` encodes the PNG itself and drops a buffer of any other size (with a line in `cerr`). The contract is written next to the declaration in `renderer.h`; `WasmRenderer` used to return an encoded PNG, which is why it is written down at all. Nothing in the web frontend requests a screenshot yet - there is no C API for scripts there - so `SCREEN` in the browser is correct but unreachable.

## Numbers and radix

- Hex prefix: `$` (e.g., `$FF`), Octal: `&` (e.g., `&177714`), Binary: `#` (e.g., `#1010`), Multiplier: `k` (e.g., `64k`). The same prefixes `format_number()` writes, so a value from a `LOG` line can be typed back in. Octal is what every К1801ВМ1 (БК) document uses; note that the `#` of a PDP-11 listing means an immediate operand, not binary
- **`radix` in the `system` section sets the base of every unprefixed number of that machine** (`radix = 8` in every BK config), and `_` marks the decimals — `clock = _4000000` next to `start_address = 140000`. It is ambient state: `set_default_radix()` (`utils.cpp`) is called by `Emulator::load_config()` from `EmulatorConfigDevice::radix`, and by the script verb `RADIX`. `parse_numeric_value(s)` therefore reads it everywhere; pass `10` explicitly for a number that is **not** the machine's — ini settings, tape format strings, the base of `RADIX` itself, and interface bit ranges in `convert_range()`. Converting a machine to a non-decimal radix means marking every count, size, frequency and delay in its configs **and its scripts** with `_`; the regression suite is what catches a missed one
- **The arguments of a script verb are read in the machine's radix too**, which is easiest to forget when typing commands by hand into an MCP session rather than into a `.ecat` file. On a БК `LOGDEFS 16,8` fails outright (`Invalid numeric value: 8` — an octal number has no digit 8), and `WAIT 1000` silently waits 512 ms; write `LOGDEFS _16,_8` and `WAIT _1000`. The base of `LOGDEFS` is itself such a number, so the octal output of a БК is asked for with `_8`
- **`parse_numeric_value()` parses unsigned**: it used `strtol`, which stops at `LONG_MAX` — 0x7FFFFFFF where `long` is 32 bits — so everything above 2^31 came back as that one wrong number. A bus line nobody drives carries `_FFFF`, and one driven in part carries most of it, so a saved state writes such values routinely.

## Keyboards and input

- **The on-screen keyboard presses machine keys, not host keys**: `Emulator::key_event_id(id, press)` goes straight to `Keyboard::key_event_id()` and skips `rus_translate()`, because the drawing shows the machine's own layout — pressing Й on an Орион picture is already `EmuKey::Key_J`, and the ordinary `key_event()` would remap it a second time into О. The names come from the machine's native key table (`keys = <file>`, `picture = <file>.svg`), all start with `key_` so they never collide with a host key name, and `KEYDOWN`/`KEYUP` accept them. That table is what expresses things the host `.map` cannot: on the БК `key_1` sends $31 or $21 depending on the register latch, while `bk.map` has `!/S` and no `1/S` at all
- **Host key events arrive on the GUI thread**: `Emulator::key_event()` and `key_event_id()` call straight into the keyboard device from the window, while the machine runs on the emulation thread. A keyboard that only updates its own key matrix, which the machine polls, gets away with it; one that writes a register and drives an interrupt line from `key_down()` races the processor taking or clearing that same request. `UKNCKeyboard` therefore only queues codes in `key_down()` and hands them to the machine from `clock()`. Scripts and MCP press keys on the emulation thread, so they cannot show such a race - but do not blame every lost key on it: the УК-НЦ menu that skipped every fifth arrow was an interrupt fault, see "УК-НЦ" in `machines.md`
- **Settings > Keyboard moves host keys onto other host keys** (keypad on the arrows or on U I O / J K L / M , .): a `KeyRemapMode` set by the frontend (`Emulator::set_key_remap()`, ini `[Keyboard] remap`, page `wasm_set_key_remap`), with one table per mode named by the keyboard's own `remap_arrows` / `remap_letters` (`deploy/data/*_ms7004.remap`, `deploy/computers/agat/*_agat.remap`, `host: target` by script names; a target is a host key, so on the Агат `up: kp8` lands on функц 2 through `agat.map` - by position, as the user wanted), applied in `Keyboard::key_event()` before `rus_translate()` and kept in `m_host_down` so the release matches. Only host input is remapped (`host_key()`, `wasm_key_event` pass `host = true`); scripts, MCP and the drawing are not, so the tests do not depend on the setting, and `record_key()` writes the remapped key
- **Key groups block a scan line** (`groups = <file>` of any keyboard, a line per group of the machine's key names; `ms7007.grp` holds the 11 columns of the УК-НЦ matrix, column = (number & 017) - 5): a host key held in a group swallows the press and the release of every other key of that group, and a key swallowed stays swallowed until its own release (`Keyboard::group_filter_locked()`, under `m_host_mutex`). Host input only - `release_host_keys()` therefore lets keys go as host keys, and `record_key()` skips a swallowed key (`last_host_swallowed()`), since a replay is not host input. A keyboard takes part by answering `host_key_id()` (host code -> machine key name): `uknc-keyboard` and `map-keyboard` (its `id_of_code()`). `@hold` in a file: the key that took a group stays down for the machine until the last key swallowed in it is up (`m_group_deferred`; `host_release()` lifts it then, and `record_key()` writes that release through `last_host_released()`). The БК (`bk.grp`, `bk10.grp`) is one `@hold` group over the whole К1801ВП1-014 matrix, not a group per scan line: the chip does not scan - a pressed key resets its column trigger, the column then pulls the key's X line low, and the chip waits for every X to go high, so no second key gives a code on any line and the first is released only when all are up. That came from running the chip's reverse-engineered netlist (github.com/1801BM1/k1801, `014`) in iverilog with a resistive matrix (the bench there has a simplified one); a second key on the same X in another column, held after the first is let go, makes the model chatter with no code. Key places: `docs-external/BK/keybk.pdf`; the chip's code is the place, 8*X + Y for X0-X3, 060 + 8*(X-4) + Y for X4-X9; ПРОБЕЛ is not among the 80 places. ЗАП and СТИР of `bk10.keys` share their 7-bit codes with сдвижка/раздвижка and are left out. `COMMAND keyboard.host("j",1)` presses as the host would, `keyboard.blocked` counts; `work-uknc-kbd-groups` and `work-bk-kbd-groups` are the tests
- **Lamps of a keyboard drawing**: only `led_rus`/`led_lat` come from the base `Keyboard::indicators()`; a `led_*` nobody reports is drawn as drawn, i.e. lit (the Апогей's `led_power` relies on it). A drawing shared by machines that wire the lamps differently is fixed by keyboard parameters: `led_off = a|b` (always dark - the Ириша darkens the six 15ВВВ lamps only the 15ИЭ drives) and `led_case_lower = led_nr`. The `leds` field of every keyboard lists the lit lamps
- **A Russian Windows layout makes Qt report a letter as its Cyrillic character** (Й = 0x419), which no map knows; `host_layout_key()` (`qt_utils.cpp`) takes such a key from `nativeVirtualKey()` instead, for the main window and the keyboard window
- **The machine mouse measures a step on the screen widget, not with `get_scale()`**: auto scale (`scale=0`, the shipped default) returns 0 there. The pointer is put back to the middle only when it strays past a quarter of the widget: doing it on every event loops under a fractional Windows scale. Capture lives in `MainWindow::eventFilter`, speed is `[Mouse] speed` in the Settings menu
- **`MOUSE dx,dy[,buttons]` hands its steps out over time**: wait with `WAITFOR mouse.pending == 0`. A recorded movement is written as `_12` / `-_12`, because a БК reads unprefixed numbers as octal
- **TYPE and paste type Cyrillic through the keyboard device, which must say how**: `text_to_keys()` (`keyboard.cpp`) asks `key_for_char(codepoint, key, shift)` for a letter outside ASCII; false means the device does not know, and the letter is an "unknown character". The default is the КОИ-7 rule of the Soviet machines (in РУС a Russian letter is the Latin key of its code, Й - J, Ю - @), only for a keyboard with a РУС/ЛАТ key; a map with `/R` lines (15ВВВ) is searched for the code instead, and a machine of its own layout overrides it (ScanKeyboard: `rus_layout = jcuken` of the Поиск, `koi7-shift` of the Правец-8Д). Around the letters TYPE presses `rus_on_key()` / `rus_off_key()` (default `rus_switch_key()`, `_FFFF` = the keyboard cannot switch) and reads `rus_now()`, so it switches only when needed and puts the register back. The key goes out with `KEY_NO_REMAP` (past the host ЙЦУКЕН remap) and, for a switch that is a chord, `KEY_WITH_CTRL` (`Emulator::key_event()` holds Ctrl around it: УПР+N of the УК-НЦ). `needs_shift_char(ch, key)` decides Shift for a character whose case the key code lost (capitals of the Правец-8А 8-bit table). A new keyboard gets Cyrillic by overriding `rus_switch_key()` (and `key_for_char()` when its letters are not the КОИ-7 keys); `KEY_NO_REMAP` gets the key to the machine even where the device does not track РУС (the Орион takes it from a lamp)

## Adding a CPU, a device, a machine

**Add a new CPU type:**
1. Create `emulator/devices/cpu/newcpu.cpp/h` inheriting from `CPU`
2. Implement instruction decode/execute cycle
3. Add to `src/emulator_sources.cmake`, the one core list every build includes (desktop, console, web)
4. Register the factory in `Emulator::register_devices()`. The debugger asks the processor for its disassembler: override `disasm_table()` to name a table in `deploy/data/*.dis`, or `create_disasm()` to return a `DisAsm` subclass when the instruction set does not fit the table format (see `k1801vm1::create_disasm()` and `disasm_pdp11.cpp`). A decoder fills `DisasmLine` in `decode()`: the length, `valid` (false for an opcode the processor does not have - the backward disassembly trusts only real instructions), the flow (`FLOW_JUMP`/`CALL`/`RET`, `conditional`) and the target when the instruction names it; a table marks the flow in a column after the length (`J`, `JC`, `C`, `CC`, `R`, `RC`, `JI`/`CI` for a jump or call through a register or cell, `@hex` for an implied target such as `RST 38H`), the 6502 tables have their addressing mode before it. The debugger and the step over use it; `over_commands` is gone. Also for the debugger: `register_radix()` when `get_registers()` is not hex, `set_flag()`, `get_sp()` / `stack_address()` / `stack_entry_bytes()`, `waiting()` (WAIT/HLT: a step goes on to the interrupt), `get_history()` for a processor that keeps one, `poke_mem()` with the processor's own address translation. `execute()` calls `debug_before()` before the instruction and `debug_after()` after it, both only when `m_debug != DEBUG_OFF`. A processor that counts the bus cycles of the instruction it executes answers `bus_time()` with the moment of the access in progress (the 6502 does, with its dummy reads): a device clocked in batches after the instruction but tied to the processor's clock (the Disk II sequencer, `apple2-disk2`) runs itself up to that moment on an access, so the timed loops of DOS see it at the right clock
5. Reference in `.cfg` files via `device_id: newcpu {}`

**Add a new device:**

A card that must know which chip sits in a ROM socket (an inverted image, a revision) asks `ROM::image_name()`: the image as the configuration names it (`image` or `image_1`), not the resolved path (`apple2_cards.cpp`).

1. Create `emulator/devices/common/newdevice.cpp/h` (or `specific/` for machine-specific)
2. Inherit from `ComputerDevice` (generic) or `AddressableDevice` (memory-mapped/port-mapped)
3. Declare `Interface` members in the class body; they self-register on construction
4. Implement `get_value(addr)` / `set_value(addr, val, force)` for addressable devices, `clock(counter)` for clocked devices, and `interface_callback(id, new_val, old_val)` for reactive devices
5. Add a `create_xxx(InterfaceManager*, EmulatorConfigDevice*)` factory function in the `.h`, implement it in the `.cpp`
6. Register the factory in `Emulator::register_devices()` in `emulator.cpp`
7. Add source files to `src/emulator_sources.cmake`
8. Optional: override `get_device_fields()` / `get_field()` and `get_device_commands()` / `send_command()` to expose state and actions to scripts
9. Override `save_state()` / `load_state()` for anything a cold start does not reproduce — the base class already carries the device's interfaces and its fractional clock, so most devices need only their own registers. See "Saved state" above for what must not go in and what belongs in `state_restored()` instead

**Add a new computer configuration:**
1. Create `.cfg` file in `deploy/computers/` subdirectory (e.g., `my_machine/config.cfg`)
2. Define system, CPU, memory, devices, and interface connections
3. Place ROM/disk images in same directory
4. Create matching `.md` file with user-facing description
5. No code recompilation needed

## Build structure

Three rendering backends controlled by compile flags:
- `RENDERER_QT`: Software rendering via Qt painter
- `RENDERER_SDL2`: Hardware-accelerated via SDL2 (preferred for Windows 7)
- `RENDERER_OPENGL` (default for Qt6 debug): OpenGL rendering (best performance)

Selected at build time with `-DRENDERER_OPENGL=1` / `-DRENDERER_SDL2=1` / `-DRENDERER_QT=1`. A windowed build needs exactly one, and configuration stops otherwise. A Debug build that names none gets OpenGL with Qt 6 and SDL2 with Qt 5. OpenGL needs Qt 6.

**Build variants** (`src/CMakeLists.txt`):
- `ENABLE_GUI` (ON): the windowed `eCat3`. With `OFF` no `find_package(Qt)` runs at all, so a console-only build configures on a machine without Qt.
- `ENABLE_HEADLESS` (OFF): a second target `eCat3-headless` built from the same `EMULATOR_SOURCES` plus `src/headless/`. Console subsystem, links no Qt, draws into `NullRenderer`. Needs a C++17 toolchain, so the XP/Win7 kits refuse it. It reproduces the regression suite byte for byte, references included.
- `ENABLE_MCP` (OFF): the MCP server (`src/mcp/`, `src/mcp_bridge.*`, vendored `libs/picojson`). Without the option not one of those files is compiled. A windowed MCP build requires `RENDERER_OPENGL` and fails configuration otherwise; see `docs/MCP.md`.
- The release scripts of Windows 10+, macOS and Linux build every variant in one run: `OPENGL`, `OPENGL-mcp` and `HEADLESS` (console, always with MCP; a `.tar.gz` of `bin/` + `share/ecat/` on macOS and Linux), see `.build/README.md`. The Qt-renderer variant (`QT`, and `QT` next to `SDL2` on the XP/Win7 kits) is built only with the `all` argument.
- **One core source list**: `src/emulator_sources.cmake` defines `ECAT_CORE_SOURCES`, included by `src/CMakeLists.txt` (as `EMULATOR_SOURCES`, shared by the windowed and the console targets) and by `src/wasm/CMakeLists.txt`. A core file goes there and nowhere else; `GUI_SOURCES` is for files that need Qt. A source of one build's library (SDL audio) stays in the list and compiles to nothing without its define.
- **Only `dsk_tools_core` of the `dsk_tools` submodule is built**: helpers, `Result`, the Agat track decoders (`include/dsk_tools/core.h`). The submodule is added `EXCLUDE_FROM_ALL`, so its loaders, file systems and viewers (some 75 files) are never compiled; a file of eCat3 includes `dsk_tools/core.h`, and `dsk_tools/dsk_tools.h` does not even compile here (its headers are not on the include path). Something more from the library means moving it into the core there, not linking the full `dsk_tools`
- **`globals.h` is generated**: Produced by `configure_file(globals.h.in ...)` at CMake configure time into the build directory, one per build directory. Do NOT edit it; edit `globals.h.in` or CMake variables instead. It used to be written into `src/`, where every build directory overwrote the others' copy; the configure step deletes a `src/globals.h` left from then, since it would be found first.

**Update translations:**
```bash
cd .build
./update_translations.bat  # Or update_translations.sh on Unix
# Edit .ts files in Qt Linguist
```
Without the IDE: `cmake --build <build dir> --target update_translations` (on Windows with `__COMPAT_LAYER=RunAsInvoker` in the environment) adds new strings to `src/translations/*.ts` as unfinished; the Russian and Bulgarian texts go into `ru_ru.ts` and `bg_bg.ts` by hand. A new language is a `.ts` in `TS_FILES` and `SUPPORTED_LANGUAGES` (`src/CMakeLists.txt`), a flag in `resources.qrc` and an item in `MainWindow::add_languages()`. The `.qm` files are generated on the next build and are not in git.

- **C++11 baseline** (`CMAKE_CXX_STANDARD 11`): The emulator core targets C++11 for MinGW 4.9.2 (Windows XP) compatibility. Modern compilers (MSVC, MinGW 13+) build with C++17 features enabled selectively (e.g., `USE_MINI_INI` requires `<filesystem>`).
- **Threading**: `thread_compat.h` provides `compat_mutex` (use it instead of `std::mutex`) and, in the QThread variant only, `EmuThread`; the std variant uses `std::thread` behind `#if USE_QT_THREADING` (see `emulator.cpp`). On MinGW < 5 the Qt classes are used; `FORCE_QT_THREADING` / `FORCE_STD_THREADING` override auto-detection.
- **Qt-free core boundary**: Code under `src/emulator/` must not include Qt headers directly. The only exception is `thread_compat.h`, which uses Qt threading behind `#if USE_QT_THREADING`. Qt-dependent utilities live in `src/qt_utils.h/cpp` (outside the core).
- **Keyboard codes**: `EmuKey` namespace in `keyboard.h` defines key constants with values matching `Qt::Key`, so Qt frontends pass `event->key()` directly. Non-Qt frontends (Wasm, SDL) use the same `EmuKey::` constants.
- **Some files are committed with CRLF** (`git ls-files --eol` shows `i/crlf`: `i8255.cpp`, `i8257.*`, `6502.*`, `i8080.*`, `z80.*`, `globals.h.in`). A script that rewrites such a file with LF turns the diff into the whole file; preserve the existing line endings.
