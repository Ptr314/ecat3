## Поиск-1 (IBM PC clone)

- **The Поиск-1 follows MAME (`src/mame/pc/poisk1.cpp`) except for the video memory**: it is the top 32 KB of the board RAM (shared with the processor, hence the wait states), not a separate buffer - but seen by the processor only through the B8000 window (`poisk-vram`), never at its own address. The 1991 BIOS sizes the RAM by probing 16 KB blocks up to the first gap; with the top 32 KB mapped it reported them as free and DOS put COMMAND.COM into the screen. CGA ports and writes to B8000-BBFFF trap through NMI (`poisk-trap`), and the BIOS draws text itself. The floppy cartridge B504 is a КР1818ВГ93 at C0h-C3h plus `poisk-fdc-control` at C4h (drive/motor/side, MR on D6 - a Restore when it goes high, which the ROM waits for; a read of C4h runs the controller to DRQ/INTRQ; a write to C6h restarts the motor one-shot, bit 0 of C6h reads 1 once it has run out). The factory driver ROM waits ~0.25 s for the motor before every operation on A: (its "motor already on" test compares with the drive number, 0 for A:), which is why DOS boots in about a minute; `Poisk-1-fdd302.ext` carries the Moscow v3.02 ROM, which waits only after the one-shot ran out. The factory BIOS INT 16h decrements AH in place and returns it changed for an unknown function, so a program probing for the AT keyboard with `AX=11FFh` (Volkov Commander 4.99) decides it is there and then polls functions 10h/11h that do nothing - an incompatibility of the real BIOS, not of the emulator. `LOG cpu.history` lists the last 256 linear addresses on the 8088 too.
- **A 20-bit address space needs `address_bits = _20` on the mapper**: the page table is sized from it, and an address above it takes the linear scan.
- **The cassette is the IBM PC one** (`encoding = ibmpc`, `tape_ibmpc.h`): a bit is one period of the square wave of PIT channel 2 (1184 counts for a 1, 592 for a 0), written to tape from `pit.output[2]` and read back on port 62h bit 4. The BIOS times the halves with channel 0, which is what found two faults of the shared `i8253`: a latch command kept only the low byte (the high byte read was stale), and a count written to a running mode 2/3 channel restarted it and flipped OUT, so every bit got a spurious edge (the write path rewrites channel 2 after each edge). Both are fixed for every machine; the regression suite passed unchanged. A `.cas` is the PCE format - the record's bytes with the leader as FFh and the sync bit as FEh. The BIOS writes records back to back with no pause, so the decoder recognises the next record by its leader: a run of 2080 ones (32 of the trailer + 2048), longer than any block of FFh bytes can give. A `.cas` that does not start with a leader is a bare file (digitised cassettes are often kept so, `TETRIS.CAS`): the loader wraps it into a header (A5h, the file name as is - the BIOS compares it byte for byte, capitals included) and a data record. The BIOS menu runs a loaded file on Enter only; any other key returns to the menu
- **`wd1793` has one slot for a delayed register write**, and a 16-bit OUT of the 8088 writes two registers within one instruction, before the devices are clocked: `set_value()` applies a waiting write before it takes the slot, or the first of the two (a command, a sector number) was lost
- Tests: `boot-poisk*`, `work-poisk-*` (`work-poisk-tape*`: read, write + read back, bare file) and `state-poisk-tape` / `state-poisk-tape-write` / `state-poisk-disk` (a snapshot in the middle of a tape read and of a tape write - a restored recording must set the decoder up again; graphics plus a sector that lives only in the drive buffer). `Poisk-1-cart-ram.ext` stands on `Poisk-1.cfg` itself and repeats the 128 KB edits: an extension on another extension is not packed for the web

## ДВК (`deploy/computers/dvk`)

ДВК-1/2 are the МС1201.01 board (К1801ВМ1, monitor ПЗУ 000) with the 15ИЭ terminal, ДВК-3 the МС1201.02 (КМ1801ВМ2, monitor 279 or 055, КСМ, КГД, MX, MY, DW), ДВК-4 the МС1201.04 (КМ1801ВМ3, monitor 134, КЦГД, MX, MY, DW). **Four shipped machines, one per model**: what was a separate variant is a switch or a test machine. A ROM that was a replaceable chip is a `rom` with `image_1`, `image_2`, ... (`title_N`, `label`): not a toolbar option but a choice field of the configuration editor (`ROM::get_config_fields()`), written into an extension as `image` - БЕЙСИК/ФОКАЛ on the ДВК-1, monitor 279/055 on the ДВК-3, monitor 134/377 and КЦГД firmware 181 / 182 / 182 + KeyGP on the ДВК-4 (181 first: most КЦГД software is written for it - 182 points every empty screen row at one shared video line, which FIGHTR draws into, and LOAD.SAV, the firmware extension COLUMN, MINE and others need, patches 181 and breaks 182's output; KeyGP breaks the games that load code at 040000, see below). Without `image` the first one is used. Tests pick a variant with a small extension in `tests/files` (`dvk3-055.ext`, `dvk1-focal.ext`, `dvk4-kcgd181.ext`, `dvk4-keygp.ext`, `dvk4-ksm-377.ext` - the last stands on `dvk4-ksm.ext`). Two-position options (the panel's «Пульт» and «Прерывания») are `DEVICE_OPTION_TOGGLE`: a checkable button on the toolbar and on the page (`wasm_device_options()` carries the type), values 0/1 as before, so the ini, `COMMAND panel.option(id,v)` and recordings are unchanged. The ДВК-4 with the КСМ (`tests/files/dvk4-ksm.ext`; `display.text` cannot read the 182 font) and the ДВК-3 with the КЦГД (`tests/files/dvk3-kcgd.ext`, monitor 055) live in the tests only. `kcgd-display` reads the firmware font when the text is asked for, not at reset: the switch changes the firmware after the reset. The documentation and the ROMs are in `docs-external/DVK/`; register maps follow the FPGA replica github.com/forth32/dvk-fpga and MAME (`dvk_ksm.cpp`, `dvk_mx.cpp`, `dvk_kgd.cpp`).
- **The terminal КСМ is a second machine**, not a display controller: its own i8080 (`ksm-cpu`, own mapper and clock domain) runs the real firmware (ksm_04/05) with an 8259, two 8251 and an 8255; `ksm-display` only scans its video RAM. It talks to the ДВК through `dl11` `~txd`/`~rxd` (byte-wide links) and nothing else. The КСМ firmware needs ~0.35 s after power-on before it takes characters from the line, while the ДВК monitor prints its first prompt at once. On the real machine the start is given by the power panel, modelled by `dvk-panel` (the author's Arduino replica `DVK_Control`): POWER GOOD after `power_good` (500 ms), АИП (`~dclo`) 13 ms later, АСП (`~aclo`) 10 ms after that. Without it the first prompt was lost. Do not put such a delay into the processor. Its two switches are device options (toolbar drop-downs, `COMMAND panel.option(id,v)`): «Пульт» drives ОСТ (`~halt`, a level - the CPU cannot leave the console while it is on) and «Прерывания» the 50 Hz ПРТ square wave, which is the line clock everywhere: `~irq2 = !panel.prt` on all three processors. The МС1201.04 has no LKS register (netlist: XS1 BA14 -> D7 -> S7 -> VM3 EVNT, nothing gates it; `dvk-lks` is the FPGA replica's and stays only in `vm3-test.cfg`), so nothing masks the line: the 134 monitor runs its memory test with interrupts open and fails with the switch on, which is why the ДВК-4 starts with «Прерывания» off and `boot-dvk4-xm` turns it on after the prompt. Without LKS, RT-11 reports no system clock in SHOW CONFIG (`cpu.irq2_requests` counts what reaches the processor). The 055 monitor's `P` is the ВМ2 STEP, which proceeds (RTT-like: the first instruction is fetched without an interrupt poll, and nothing returns to the console after it - an earlier model returned at once and executed nothing, so `P` looked like a dead single step). `k1801vm1` starts only when both lines are released: ACLO released after DCLO is the power-up, not the interrupt through 024. The tests still press ВК first
- **The 15ИЭ-00-013 terminal of the ДВК-1/2 runs its own firmware** (`ie15-cpu` + `ie15-io` + `ie15-display` + `ie15-keyboard`; `cpu/ie15.*`, `specific/dvk_ie15.*`), like the КСМ of the ДВК-3: a second processor in its own clock domain, 3.08 MHz, one instruction a tick (ТО 15ИЭ 5.2: 324.6 ns a cycle). The processor is MAME's `src/devices/cpu/ie15` except the ALU buffer (БАЛУ): the emuverse ТО (6.1.1) confirms what MAME marks XXX - ZF is the «A=B» trigger, all ALU outputs 1 = result 377 - and puts the ALU buffer, not the accumulator, on the data channel. Alex_K's command table (zx-pk.ru thread 36791, «СПИСОК КОМАНД 15ИЭ-00-013.docx»): ADD, RAL, RAR, DSR, 05x, LLA, AND, XOR, LDA and CS (A - R - 1) write БАЛУ (and ZF with it), LDC/LCA, jumps, flags, STA and OTA do not; STA and OTA output БАЛУ, condition 5 is its bit 7. A probe over the DVK-1/2 tests (both firmwares) found no STA, no OTA with a meaningful byte (00, 02, 03, 06, 14) and no SFC/SFS 5 where БАЛУ differed from A, so MAME's accumulator model and this one run the firmware the same; a snapshot without `B` takes БАЛУ = A. Firmware `ie15.rom` = MAME `dump1.bin` (5 chips, CRC 14b82284), `ie15_6chip.rom` = `dump5.bin` (older board; per Alex_K's disassembly the dump is corrupt on pages 8 and 9, 0x800-0x9FF); DUMP3 differs by one byte at 3B6 and is a bad read. Commented disassembly of the 5-chip firmware, port/flag/memory/register maps: `docs-external/DVK/15ИЭ/Alex_K&Tutus`. All ports 00-17 and flags 20-27 go to one device, `ie15-io` (an `AddressableDevice`; a `GenericDisplay` cannot also sit on a bus): the port map is MAME's, the port semantics were checked against the firmware. Speed (port 14, bits 0-2): 0 = 9600 ... 7 = 75, read from the jump table at 0460 that prints the status line. Flag 7 is ФЛ7, КОИ-7 Н2 (setup group II bit 3, bit 5 of r11): the character generator gets bit 5 of the code in place of bit 7, so Latin small letters show as Russian capitals; `display.text` reads them so too. Input flag 3 is the ФЛ7 output: the routine at 0x5F3 (octal 2763) reads it before setting or clearing flag 7, and with flag 3 read as 0 (MAME) the bit never came off once set. A control code is any code with bits 5 and 6 zero (ГС D21, so 200-237 too): the generator gets bit 6 as well and the cell blinks, in phase with the cursor marker (yursav's reading of the schematic in thread 20744; Titus there first read the opposite phase). The bell (port 10 write) is 2400 Hz on `ie15-io.beep` to a `speaker`: flag 2 at the moment of the write picks 0.15 s (1) or 0.4 s (0), measured on a machine (thread 20744; the schematic values give 23 ms / 300 ms, one resistor reads 7.5 kΩ in the parts list). Port 07 write (line break) is not modelled. «Snow» (Titus, EmuStudio thread): the firmware turns video off (flag 0) while it works with the memory, and when that outlasts the three marker lines the start of the next text row stays dark - normal on the machine. The raster is counted in CPU ticks (line 200, blank 40, 28 x 11 lines, visible rows 2-26): a line is drawn on the emulation thread cell by cell, as the beam meets it: cell x is taken at tick 40 + 2x, from the one memory address counter, which the memory itself advances per cell while video (РИН, flag 0) is on - so the firmware reloads the line start in every horizontal blank (0x092-0x095, then it waits for the blank to end). Before anything that changes the picture (flags 0, 1, 3, 7, ports 00-05) `IE15IO::video_sync()` brings the beam up to the current tick; the 80 cells go to `IE15Display::draw_line()` when the line ends. With video off a cell is dark and the counter stands; video switched on again without a reload shows the cells from where the firmware wrote. MAME draws the whole line at the end of the blank, so a line whose video came on a few cells late was dark entirely; here (field `snow`, test `work-dvk1-ie15-snow`) such lines are line 0 of a row with the first 3-4 cells dark, a few per second of scrolling output, and every reference of the old model stayed pixel-identical. The marker flag belongs to the next line, as MAME. The firmware polls flags 0-2, so this timing is load-bearing. Memory writes take a pair of OTA 00 (the second writes), as MAME. `IE15CPU::execute()` runs a batch (up to 64) of instructions that touch no port and stops before the next one that does, which then opens the next batch: the terminal devices change only through ports, so every port access sees them exactly as with one pass per instruction; only the moment the ДВК processor sees the line moves, by at most a batch. Off under the debugger. With one read of the opcode per instruction this cut the terminal's cost by a quarter (10 s of ДВК-1 at MAX: 545 -> 440 ms, 145 with the terminal stopped); the rest is the per-batch pass of the emulation loop and `IE15IO::clock()`. **After power-on the terminal is in its own mode, not VT52**: control codes go through one of two jump tables (3010 or 3110), picked by setup bit 1 of r11; the default table ignores ESC and drives the cursor by single codes (034 up, 035 down, 031 right, 032 left, 010 home, 014 clear). VT52 is set in setup (СДВ, seven times right, «Уст. след.» = code 002, СДВ); there is no NVRAM, setup bits are 0 at every power-on - the user chose this hardware behaviour over a convenience default, so `disk-dvk2-dx` (its RT-11 runs SL, which edits by VT52 codes) sets the bit first. The status line (speed, 16 setup bits, clock) shows unless setup bit 0 of r10 is set. In local mode (ЛИН off) the firmware does not read the line at all, so bytes fed then overrun. Switch ports: 12/16/17 = 200 when РЕД/ДУП/ЛИН are on, 14 = 200 in setup. **РЕД is on in normal work** (as MAME's RED default): released, the firmware stores control codes in video RAM instead of acting on them, and the video shows stored codes blinking only while РЕД is released - the status line keeps its markers there as such codes (cursor stops for the arrows, parameter numbers; in setup right jumps by parameter, left by one character). The polarity once was inverted (РЕД off at power-on meant normal work); a 4.4.0 snapshot has no `red_on` in the keyboard state, and `IE15Keyboard::load_state()` flips its РЕД (`state-dvk1-ie15` opens such a snapshot). MAME blinks them with RED on and the status line off; the blink here follows a user's account of the hardware. the ДК line (port 15) is set for the whole cursor block and the keypad, as in the MAME matrix - by it the firmware turns arrows into ESC A/B/C/D and 026/002/022 into ESC P/Q/R in VT52 mode. The keyboard is the Ириша's 15ВВВ (`15vvv.keys`, `15vvv.map`, `15vvv_keyboard.svg` in `deploy/data`), a `map-keyboard` whose codes go to `ie15-io` (`send_key()` virtual); the keyboard is hold-based, as the hardware (ТО 6.1.5.2, Alex_K): the ready flag (port 13) is set on a press and, while the key stays down past 1 s, at 15 Hz; a port 15 write and the key's release clear it. The firmware itself turns autorepeat on and off (setup group II bit 2, 0 = on): with it on it clears the flag on taking the code (routine 0x401), with it off it waits for the release (0x201 clears r9 bit 2 when the flag is down) - so without release clearing, as in MAME, a terminal with autorepeat off took one key and no more. Press and release reach `ie15-io` with a token (host key or drawing id) and are applied in `clock()`; the first held key is the one the matrix counter stops on, a second one is seen after the first is released and the counter has gone round the matrix (6.4 ms, 64 positions at 10 kHz - without that pause a key pressed the instant the last one was released vanished with autorepeat off). A press shorter than 40 ms (a tap on the drawing, a script key with no hold) is held 40 ms: the firmware polls the keyboard once a frame. Held keys are host input, not state: a snapshot loads with none held and the flag down. Test: `work-dvk1-ie15-kbd`. The host Backspace sends ЗБ (DEL): RT-11 and BASIC erase by DEL. The five mode switches have no codes, so no place in `15vvv.map`; `IE15Keyboard` puts them on host F6-F10 itself (СДВ, РЕД, ЛИН, ДУП, ПЧ; a press flips, a release does nothing): role `toggle` (`KEY_ROLE_TOGGLE`, saved in a snapshot); ЛИН, ДУП and РЕД on at power-on, a machine reset leaves them, as it leaves the whole terminal (`IE15CPU::reset()` and `IE15IO::reset()` act on a cold reset only). The character generator (`ie15_cg.rom`, KOI-8, bit 7 = left pixel) repeats 040-077 at 240-277: in the second set the firmware stores codes with bit 7. `COMMAND ie15-io.receive("...")` feeds bytes through the receiver, one a character time; `display.text` reads each row from where the beam took it. A skipping instruction (DSR, ISN, DSN, ISE, DSE, SFC/SFS/SKP, CS) steps over a whole 2-byte slot when the next opcode is in group 03x (`IE15CPU::skip()`, as MAME `SKIP_OP`), so a skipped RAL/RAR (033/035) would take the byte after it too; the ТО does not say what the hardware does, and it does not matter: neither firmware ever has RAL/RAR right after such an instruction, in reached code or anywhere in the ROM (`tools/ie15/ie15_skip.py`, which also finds two unknown 03x bytes, 077 at 3425 and 071 at 4455 / 5055 - table bytes reached through LDC constants taken as JMI entries; `ie15-cpu.unsupported` stays 0 through `work-dvk1-ie15`). Tests: `work-dvk1-ie15`, `state-dvk1-ie15` (snapshot in the middle of an ESC Y)
- **The МС7004 drawing** (`ms7004_keyboard.svg`, source `src/pics/ms7004_keyboard_font.svg` - keep the ids of both the same) works through `ms7004.keys` (`id: LK201 code`; `MS7004::parse_key_table()`/`send_key_id()` press the key through the same `press()` as a host key). Codes come from the keyboard firmware's matrix table (`ms7004.lst` 0380-03FF); the keys LK201 lacks are placed by matrix column: `key_lcurl` $FC, `key_rcurl` $F5, `key_tilda` $C9, `key_lf` $C4 (the КСМ gives LF), `key_hard` (Ъ) $F1, `key_under` $FD. LEDs follow the firmware (0531/05FF): $13 + `1000abcd` lights, $11 darkens (d wait, c compose, b lock/ФКС, a hold/СТОП КАДР); `1001xxxx` is ЛАТ on P1.5, inverted ($11 lights it); $89/$8B light/darken wait; $FD and reset darken all. The КЦГД 181 sends $11 $90, $13 $90, $11 $90 at start (ЛАТ lit) and lights СТОП КАДР; the КСМ ROM never writes the keyboard channel's data port (only 8251 control words to 6F), so on the ДВК-3 the lamps stay dark - `keyboard.~rxd = ksm-kbd.txd` is wired anyway. `command_log` shows the last 16 bytes from the terminal; `work-dvk4-ms7004-leds` is the test
- **The КСМ 8259 answers the 8080 with CALL** (8080 mode, ICW1 D6h / ICW2 0Bh, level n -> 0BC0h + 4n): `i8080` `int_opcode = $CD` takes the address from `~int_address` = `i8259` `~call`, and drives `~inta` low in `reset()` so the first acknowledge is an edge.
- **`ms7004` sends LK201 key codes as they are**; the КСМ firmware turns a code into a character through its table at 0AFD + ~code (the `CMA` there belongs to the table index, not to the line). The МС7004 is ЙЦУКЕН with Latin letters on the same keys (J on the Q key); the host map gives Latin letters to keys with the same Latin label, `use_remap = 0`. **Both terminals change the case of the Ш Щ Э Ч Ю Ъ keys like letters** (Latin: 133-137 and 100): with ВР Ю is `` ` ``, Ч `~`, and Ъ on the КЦГД 181 is DEL (177). So every such sign is marked `-shift`/`+shift` plus `letter` (`[ ] \ ^ @ _` lower, `{ } | ~ `` ` `` upper; `` ` `` is host key `~`, `~` is `tilde`; `work-dvk4-ms7004-symbols`). ФКС inverts the letter group on both terminals and on the КСМ also the digits and signs (a true shift lock), so the keyboard inverts ВР for a marked sign while the terminal's ФКС is on, by `fks`: `lamp` (КЦГД: the ФКС lamp, which 181 drives from 11042 and which toggles only with ВР held; `letter` signs only, and only while the ЛАТ lamp is lit, since in РУС these keys are letters) or `toggle` (КСМ: it drives no lamps, but each ФКС press flips 20B4 bit 2 (05CD), so the keyboard counts the B0 codes it queued; every marked sign; `work-dvk3-ms7004-fks`). Unmarked letters still follow ФКС, which is how a user gets PC-like case. **B4 differs between the firmwares**: КСМ and КЦГД 182 resend the stored character (pressing ВР clears it), while КЦГД 181 (110410) re-translates the last stored key code under the current ВР and does not store ЗБ (177 bypasses 110200), so holding ЗБ repeats the character before it, and a character typed with ВР repeats without it once ВР is up. This is the firmware, not the model.
- **`ms7004` follows the keyboard's own firmware** (`docs-external/DVK/MC7004_keyboard_original.rom`, commented disassembly `ms7004.lst` in CP866), which is not LK201: every release of ВР or СУ sends B3 (0231), even with the other still held; a held key's release sends nothing; three ordinary keys at most. The КСМ firmware takes AE and AF as "down" only and B3 clears СУ first, ВР only when СУ is already clear (0587) - so ВР released under СУ leaves the terminal with ВР down and СУ up until СУ comes up, as on the real machine. An older model sent B3 only when no modifier was held and the code again otherwise, which left ВР latched after Windows' Ctrl+Shift. **Autorepeat is the keyboard's**: the last pressed key, while held, gives B4 after `repeat_delay` (360 ms) and every `repeat_period` (28 ms) - counted from the firmware's cycles: 46 cycles = 150 us by its comment, a matrix pass ~33 ms, 11 passes - except ВК (BD), the top row (< 80) and 80-8F; the terminal repeats its last character (КСМ 057A, unless its setup turned autorepeat off; КЦГД 181 the same, checked by sending B4). The window drops host autorepeat (`isAutoRepeat`), so before this the ДВК had none. **The host keypad is the МС7004 keypad** (92h-A0h, Enter = 95h; KCGD games like BABY play on keys 4/5/6 of it): a keypad digit or sign carries `EmuKey::Keypad` (= `Qt::KeypadModifier`, set by `host_layout_key()` and by the page for `Numpad*` codes; not the arrows, which macOS marks too), named `kp0`..`kp9`, `kpdot`, `kpplus`, `kpminus`, `kpmult`, `kpdiv`. `Emulator::key_event()` passes it on only to a keyboard whose `keypad_keys()` is true and gives every other machine and the joysticks the plain key, so nothing else changed; `MS7004::entry_of()` falls back to the plain key for a keypad key its map lacks. A `map-keyboard` has `keypad_keys()` true as soon as its map names a `kp*` key (`MapKeyboard::resolve_keypad()` falls back the same way): the Агат, whose right block is function keys ($90-$94, $9C-$9F, $81-$83 by Appendix 2 of the Агат-9 manual, agatcomp.ru `A9_K1`), not digits, and is taken by position - 1 2 3 on top, so host kp7 is функц 1 (`work-agat-9-keypad`) Commands: FD (01 00 00 00, repeat on), AB (01 00), 89 (B7, then silent until 8B), D3 (BA), E1/D9/E3 (repeat off/on). `work-dvk3-ctrl-shift` reads the КСМ flags (RAM 20B3/20B4) and `keyboard.repeats`
- **The ВМ2 board register SEL is one parameter, `sel`** (bkbtl-doc «1801vm1 vs 1801vm2»): its high byte is the start vector `SEL000` and the base of the console vectors, the whole of it is what RSEL (000020, unaddressed read) returns - 160000 on the УК-НЦ, 140001 on the ДВК-3, 100000 on the КЦГД. `start_address`/`start_vector`/`halt_sel`/`una_value` are the old split form, kept for test rigs and old snapshots. The start reads the vector in the console space and then takes HALT/USER from bit 8 of the PSW it got: the 055/279 monitors have 740 there and run in the console, the КЦГД firmware has 340 and runs as a normal program. **PSW bit 8 is the mode** on every word load of PSW (any vector, RUN/STEP from КРСП) and goes onto the stack with the PSW, except that RTI/RTT take it only when they return into 160000-177777 and otherwise load the low byte and keep the mode (the chip model's `dc_b7`, `ax[15:13] == 111`, fed to the microprogram as `br[7]`; UKNCBTL decides the same way): the УК-НЦ disk БЕЙСИК returns from user mode into the console by RTI (PSW 000401 to 166556), while FODOS boots on the ДВК-3 through an RTI with 052404 on the stack to 155654 and must stay in user mode. **КРСК/КРСП are not a separate pair on the ВМ2**: the chip writes them with PC and PSW unless the PSW has both bits 7 and 8 (cpu11 `vm2_wb.v`, `pc_wr`/`cpsw_stb`), so a console entry through a vector with 0600/0740 freezes them on the interrupted program, while in the console with priority 0 (PSW 0400) they track PC/PSW - MFPC reads the next address, START/STEP go nowhere (Alex_K's CHLT/PHLT run chains of console instructions that way). **On the УК-НЦ the console range of the CPU mapper must come before the registers**: the console sees 160000-177777 as RAM, and with the range after them 176560-177567 still answered as registers (the CHLT chain fetched from the СА register). Console instructions are decoded in ranges (START 10-13, STEP 14-17, RSEL 20, MFUS 21, RCPC 22-23, RCPS 24-27, 030 (a normalization step loop the cpu11 decoder calls «unknown»: action from the chip model, 24 clocks a step from Alex_K's C030), MTUS 31, WCPC 32-33, WCPS 34-37) and outside the console all of them are the reserved instruction, vector 010 Running the КЦГД in the console broke the RTI trace (no trace trap in the console). **The КЦГД ROM range is `strict = 1`**: КР1801РЕ2 does not answer a write, so a write into 100000-157777 is a bus timeout. The KCGD81/KCGD82 loaders (games disk, «графический протокол») rest on it and on STEP: a self-copying `MOV (SP)+,(PC)` crawls up memory until it writes into the ROM and traps through a vector 4 it set itself, a checksum of the 8 KB ROM is sent to the ДВК, an RTI into 160104 with PSW 000740 enters the console (bit 8 is taken because the return is into 160000-177777), and the console code MTPMs the payload into user memory, MTPCs its entry and STEPs into it. Without a printer XP2-5 floats high, so the first byte's strobe is never taken back; an unplugged `printer` instead drops `ready`, which reads TR = 0 at once. `COPY TT: LP:` from RT-11 on `rt11-dw.dsk` prints through it (`tests/scripts/work-dvk4-printer.ecat`)
- **The `*_mc1201.rom` dumps** (031, 054, 279 in `docs-external/DVK/`) are stored with the words in reverse order and inverted data, plus 2 trailing bytes; `deploy/computers/dvk/files/*.rom` hold them decoded (279 matches forth32's copy except their B RK patch).

## Floppy formats (HFE, Агат 140 KB)

- **HFE** (`.hfe`, HxC Floppy Emulator v1, what Gotek/FlashFloppy reads) is the bit-cell form of the same tracks for `mfm_ibm`, `fm_ibm` and `fm_dvk_mx`: `FDD::load_hfe`/`save_hfe`, with the container and the cell codecs in the `dsk_tools` core (`src/libs/dsk_tools/src/hfe.cpp`: `hfe_read`/`hfe_write`, `mfm_encode`/`decode`, `fm_encode`/`decode`; a flag per byte marks a sync byte without its clock - MFM A1 = 4489, FM FE/FB/F8 with clock C7, FC with D7). Decoding takes the byte grid anew at every mark, so a track not written from a byte boundary reads too. MFM decoding looks for 4489 only: the C2 sync 5224 also turns up, shifted, inside a 4E gap and broke the grid. MX words go high byte first (not checked against a real MX drive). `fdd.checksum` (a hash of the tracks and marks) shows a round trip is exact; `work-dvk2-dx-deleted`, `slow-dvk3-testmx` and `slow-dvk3-testmy` do one through `.hfe`, and a BK `.hfe` was checked once with an independent sector reader (all 1600 CRCs). The rate, rpm and encoding come from the library (`TrackLayout` of the drive mode, `track_hfe_params`, `track_bytes` - 3125 bytes a turn for MX, while the drive keeps 1562 whole words), and the header's write-allowed flag becomes `write_protect` on load and is written from it. The library's IBM sector reader (`ibm_track_fields`) skips what lies between fields - a write splice, junk after a rewritten sector - instead of giving up on the track; `fdd.deleted` counts through it (TESTMY leaves 128 deleted sectors, the old reader saw 110) The Агат 840 has `.hfe` too (`agat_840_to_cells`/`agat_840_from_cells` in `mfm_tools`): its MFM table is plain MFM (checked byte for byte against `encode_agat_MFM_byte`), the sync is A4 with the clock of its last bit dropped (cells 4490h, `dsk_tools` writes them as bytes 22 09), and the drive's DESYNC mark sits on the FF after it, as in the AIM dumps; the track keeps the file's length (6464 bytes from `dsk_tools`, 6381 from a .dsk). A `.hfe` of `fddconv` and one of eCat3 convert into each other and back to the same .dsk (`work-agat-9-hfe`); `dsk_tools` writes Агат images with write not allowed, so they open protected. The 140 KB GCR disk (`mfm_agat_140`) has `.hfe` too, with `gcr_encode()`/`gcr_decode()` of the `dsk_tools` core (`agat_140_to_cells()`/`agat_140_fit_track()` in `mfm_tools`): the drive keeps the bytes the controller reads, so each goes out as its 8 bits, top bit first, and every FF with two 0 bits more - the 10-bit sync bytes of the gaps, which the latch drops, so an FF inside a data field reads the same; a disk bit is two cells, a 1 a transition in the second. The header is the one `fddconv` writes for 140 KB disks: one side, 250 kbit/s, 300 rpm, encoding FF, interface 7, double step. Loading takes one side of 35 to 40 tracks whose header says Apple II GCR or no encoding (side 0 of two); `gcr_decode()` gives each track's nibbles of one turn as the latch reads them, counting bits by a clock where the transitions leave their cells (the HxC software puts them in the first cell of a pair, write splices and flux captures shift them), and every track then gets the length of the longest, the missing bytes going into its longest run of FF, a gap. A round trip keeps `fdd.checksum` (`work-agat-7-140-hfe`), and the `.hfe` of the IKP disk decodes to `IKP7_140.dsk` in `fddconv` too; 11 of the 13 GCR `.hfe` of an Agat collection (from the HxC software, Greaseweazle and FlashFloppy) save as the same .dsk as an independent converter makes of them, and the other two load but hold tracks `decode_agat_140_image()` refuses (unreadable sectors; address epilogues DE AA FF), so they don't save as .dsk. The track layouts themselves (IBM MFM, IBM 3740 FM, MX) are in the `dsk_tools` core too (`src/track_formats.cpp`; `mfm_tools` only wraps them), and the full library's `LoaderHXC_HFE`/`WriterHxCHFE` use the same functions for the `TYPE_RT11:*` disks, so an `.hfe` written by `fddconv` reads here with the same `checksum` as the flat image, and the other way round
- **The 140 KB drive takes 35 to 40 tracks and both sector orders.** `generate_mfm_agat_140()` counts the tracks of a sector image from its size (a tail shorter than a sector, as the 128-byte Agat label, is left out), `load_image()` those of a `.nib` or `.nic` from the file's, and `decode_agat_140_image()` of `dsk_tools` saves as many as the drive has; the controller steps the head up to track 39 (half-track 78). A `.po` keeps its sectors in ProDOS order, `.dsk` and `.do` in DOS 3.3 order, and a `.dsk` whose block 2 in ProDOS order starts as the key block of a ProDOS volume directory is read as a `.po` (`agat_140_prodos_order()`, `agat_140_dos_to_prodos()` in `mfm_tools`), the rule of FlashFloppy's Apple2 mode. `disk-agat-7-140-order` and `disk-agat-7-140-forty` check both through `fdd.checksum`

## БК, СМК-512, К1801ВМ1 start and console

- **The БК printer protocol is the one of the БОС ROM driver** (БК-0011М, `B11M_BOS.ROM` at 140000, routine 156752, byte in R0): it waits for bit 14 of 0177714 read (printer ready; R4 = how many 65536-turn SOB delays to wait, 0 = forever, then C = 1), writes the byte with bit 14 = 0, sets bit 14 (the strobe: a `printer` takes the byte on its rise), waits until bit 14 read drops and writes 0. So the printer is `~data = port-ppi-out.value[0-7]`, `~strobe = port-ppi-out.value[14]`, `port-ppi ~data[14] = printer.ready`, the third entry of the УП socket `up` (default none, so bit 14 reads 0 and the driver times out) (`tests/scripts/work-bk-printer.ecat`)
- **The К1801ВМ1 starts from its 177716** (+ 020 per processor number, `cpu_number`): PC = the high byte, PSW = 340, after ACLO is released - the description's start microcode. `start_address` means nothing to it; every machine already answers there (БК 100000/140000, СМК/А16М ROM, ДВК-1/2 jumpers 160000, КМД 010000), the test rigs got a read-only `port`
- **nIRQ1 of the К1801ВМ1 is a level** (description: "вход чувствителен к уровню"), masked only by PSW bits 10/11. A held СТОП straight on it re-enters on every instruction, and on a plain БК every entry is a trap through 004 with a push: 100 ms of the key ran the stack through all of memory. The real board makes a pulse instead (`docs-external/BK/BK0010_01.JPG`): contact ОСТ1 is the node of R5 180k from +5 V and C2 68n, ОСТ2 goes through VD1 to R1 75 Ω and inverter D1.1, then synchroniser D11 to nIRQ1 - pressing the key discharges C2 into R1, about 6 µs above the threshold, and a held key gives nothing more until C2 recharges (~12 ms, not modelled). The БК configs build it from a triggered `generator` (`stop-pulse`, `length` 18 clocks at 3 MHz, 24 at 4 MHz), and the core latches the IRQ1 request flag so a pulse shorter than an instruction is not lost (taken when PSW 10/11 allow, raised again while the line stays low)
- **The К1801ВМ1 console mode is external, and the БК's vector 4 on СТОП/HALT is a consequence of it**: entry is RMW 177716 |= 010, PSW to 177676, PC to 177674, new PC/PSW from 160002 (`pdp11core::vm1_console_entry`); START/STEP read them back. On a plain БК nothing answers 177676, the bus timeout becomes the ordinary trap through 4 - `halt_vector`/`halt_sel` do not apply to `1801vm1`. A timeout inside such an entry counts in `cpu.timeouts` (the БК0010 monitor executes a HALT at 120000 on start-up). PSW bits 10/11 come only from a console vector: RTI/RTT clear them (and drop `halt_mode`: a console handler may leave that way instead of START), MTPS keeps them, and while set a timeout goes to 160002 and nIRQ1 waits. `work-bk-smk-halt` is the test, with the СМК-512 Hlt modes providing the console memory
- **The БК 2xAY board is its own entry of the sound socket**, beside the single `ay`: `ts-ay1` (`chip = 1`, `title = 2xAY TurboSound`) and `ts-ay2` (`chip = 2`, `pair = ts-ay1`) sit on 177714 with `through = 1`, and each decodes the select word itself - TurboSound 0377/0376, GryphonSound bits 15/14, the protocol of the bk-catalog emulator. Not folded into `ay`: a word select with a zero high byte (after the port inversion both Gryphon bits) would send a single-AY program to both chips. `ts-ay2` joins the mix only once written. It is last in `devices = ay|covox|ts-ay1` so the indices saved in `[DeviceOptions]` do not shift. A device's `title` overrides its `plug_title()` in any `connector`, so a board name never goes into device code. `work-bk-ay-turbosound` is the test
- **The СМК-512 BIOS maps drive numbers differently from the КНГМД**: 0-1 are the floppies, 2 and up the logical disks of the hard disk, while the КНГМД driver folds the drive number to 0-3. A program asking for a drive the СМК does not have gets BIOS error 13 (in cell 052) after the ~10 s wait for an empty IDE channel - `andos330.img` used to keep its shell's right panel on E: for exactly this reason, see `disk-bk0011m-smk-shell`. The BIOS keeps its partition table copy and variables in board RAM segment 7 (176000-176777, 176770 = number of logical disks)
- **Hard disk images of the БК are stored as on the drive, so the CPU sees them inverted**: search an image for text only after inverting its bytes. A `*.hdi` starts with a 512-byte IDENTIFY header before sector 0 (`UKNCHDD::m_data_offset`); without it every sector reads one off and the BIOS finds no partition table
- **The БК0011М frame interrupt comes at the end of the horizontal sync pulse of the first service line** (`HSYNC(line, 2)` of `RasterDisplay`, 8 3/8 words into the line, line 257 of the model), not with the vertical sync pulse of the 037 (SYNC2, service lines 21-23) as it used to. The evidence is the demo Babylona: its palette program (256 blocks of six `MOV Rx,(R0)` 32 clocks apart, after a delay loop timed on a real machine) fits its reference picture to the byte with the block for line y+1 drawn on line y and the first write at byte -4; with the interrupt at the vertical sync it was 20 lines low. The MiSTer core has the same point (irq at vc 256, hc 649). With this and the mid-instruction write below the demo matches its reference at 97% (72% before); 3 bytes (~8 clocks) are left, the picture coming that much earlier on the reference. `work-bk-0011m-raster` and `-precise` count 20 lines longer for it
- **The high precision mode of `bk-display` lays a line out a byte at a time as the beam passes** (`BKDisplay::BEAM()`, `beam_draw()`, `beam_commit()`): a line is 48 words of the video clock, 16 of blanking and then 32 of the picture: by `va_037.v` of the reconstruction (github 1801BM1/k1801, 037/rtl) `TV51` at the last picture word steps the line counter, so a line of the model has its picture in the last two thirds, and the beam is past `clocks * line_bytes * 3 / (2 * line_length()) - line_bytes / 2` bytes of it. The line mode samples at 21 us, the start of that picture. The bytes go into `m_beam_buf` and onto the surface whole at the next line start (one surface lock a line, as without the mode); `HSYNC(line, 1)` then draws nothing. The registers are read once a call, that is once a processor instruction, and a register that changed takes effect from the middle of the instruction: the devices are clocked after `execute()`, and the vm1 timing knows when a cycle happened only in `finish()`; MOV R,(R) strobes its write 15.5 clocks into its 32 on the chip model. Taking it from the instruction's start put Babylona's palette 6 bytes early. Off, it costs one flag test in `RasterDisplay::clock()`; on, ~9% on a БК0011М running `BR .` at max speed. `work-bk-0011m-precise` is the test: the handler of `work-bk-0011m-raster` six SOB turns longer puts the palette change at dot 76 of line 171. The demo Babylona (`docs-external/BK/sands-and-bomb-babylona`; a plain БК .bin with 002000 in its header: load it there and start at 002000, or from tape by the monitor, `L` and `2000G`) is the check against a real machine

## Агат

- **The 625/50 raster (both Агат) is exactly 1/25 s**: 625 lines, 313 in the first field and 312 in the second (it counted 626, a frame 64 us long - the first visible line of no display depends on line 625: 512 lines are 102..613 on the Агат-7, 38..549 on the Агат-9), and a frame of `2 * clock / 50` clocks with the remainder spread over the lines (`m_line_rem`, `m_rem_acc`: at 1.021 MHz the Агат-9 line is 65.34 clocks, 65 and 66 in turn; it was 65, 50.26 Hz). The Агат draws the 256-line mode in both fields, as the machine shows it, so the picture changes 50 times a second; the regression suite passed unchanged after all three
- **An ВВ55 mode word resets the output registers**: a control word with bit 7 set clears ports A, B and C and drives the output ones to 0 (8255A datasheet, "Mode Definition Format"); a bit set/reset word (bit 7 clear) does not. It is the only thing the Агат-840 boot ROM does to put the controller into a known state, so without it a warm restart out of a program that left drive B selected steps forever waiting for a track 00 that drive cannot report. Школьница's «Конец работы» is exactly that case; `work-agat-9-restart` is the test
- **The Агат ЯЗС (`agat-yazs`) has the schematic's topology but not its values**: the drums, the envelope former and the drum/tone balance are fitted to recordings of two real cards - `docs-external/Agat/sound/YAZS_Test.wav` (SOUNDTEST automatic mode, `soundtest.DSK`) and the NCL demo (agatcomp.ru `SoundNCL/SoftNCL/DemoNCL/`, the song of `music-d.dsk`); the schematic's values stay in comments. By the schematic drum 7 buzzed at 100 Hz where the card hisses at 6-13 kHz. The SOUNDTEST card is faulty: D0 of drum 6 does nothing there, while the demo relies on it - do not fit drum 6 to that recording again. The emulator records sound in real time only (4 min for SOUNDTEST); fit on a bench that compiles a copy of `agat_yazs.cpp` (constants as variables) against the headless objects and replays the test's register writes. `tones`, `drum6`, `drum7` (percent) scale each source's share of the mix

## Правец-8 (`deploy/computers/pravetz`)

Sources: the book of P. Petrov «Персональный компьютер Правец-8А» (Sofia 1989, `docs-external/pravetz/petrov`, file number = printed page + 1), the Правец-8С service manual (`docs-external/pravetz/service-8c`), agatcomp.ru/Pravetz (pages saved in `docs-external/pravetz/agatcomp-pages`), MAME `prav8c`/`prav82`/`prav8m`, AppleWin `Pravets.cpp`. The 8А/8С system ROMs of agatcomp are byte for byte MAME's `prav8c`.

- **The core is three devices, not mapper ranges**: `apple2-mmu` (CM631 + language card + aux + slot ROMs, page tables of pointers into the RAM/ROM buffers, rebuilt only when a switch changes), `apple2-iou` (CM632: $C000-$C07F except the speaker) and `apple2-video`. The //e banking does not fit an 8-bit `~config` and 100 ranges. `get_direct()` of the MMU has no side effects; `LOG mmu.map` replaces `LOG mapper.map`, which shows three ranges.
- **The 8А runs on the PAL //e crystal, the 8С on the NTSC one**: 14250.45 kHz in the book (7.1.1), 14.31818 MHz in the 8С manual. The raster standards `apple-pal` (312 lines) and `apple-ntsc` (262) have a fixed line of 65 clocks; the CPU clock is the average with the long cycle (14250450*65/912 = 1015657). The 82/8М standard is unknown and taken as PAL.
- **$C060 is the keyboard's, not the tape's**: D7 = KD7, the eighth bit of the code latched with the strobe, D6 (of any $C06x) = SOFTSW, the 8-bit code table flip-flop, set from D0 by any write to $C06x. The ROM reads a key as `LDA $C000; STA $C010; BIT $C060; BMI; AND #$7F`, and `SETMOD n` is `STX $C060; STA $C00E,X`. The book's own sentence on the flag (p.21) contradicts its name; the ROM decides: 1 = 8-bit.
- **The 8-bit code of a letter is the 7-bit one less $80** (tables П8.2/П8.4): Latin small $40-$5F, Cyrillic small $60-$7F; capitals and controls keep the 7-bit codes. `pravetz-keyboard` applies that rule to every map entry without `S` with a code $C0-$FE; the maps hold the 7-bit codes. Book misprints fixed in `pravetz-8a-bds.map`: И -> С is $F3 (printed $E3, the code of Ц), / -> Б is $E2.
- **Character ROM (2764)**: two 4K halves (jumper X20), each 2K of glyphs indexed by the code + 2K the graphics go through. Half 0 is the Правец set, half 1 the //e one. A glyph is stored lit = 0 for the normal codes and lit = 1 for the inverse ones ($00-$3F, $80-$9F: Cyrillic capitals inverse, as the book prints), bit 0 the leftmost dot. The primary set flashes $40-$7F by turning the inverse glyph of $00-$3F over; the alternate set has the small letters there and no flash. ALTCHARSET switches on a read too (table 2.12). The 82 ROM is all normal glyphs, bit 6 the leftmost (`font_reverse`); its Ю Ш Щ Ч are on @ [ ] ^. The 8М ROM has four 2K sets.
- **Colour**: the stock monitor is monochrome; the stock Bulgarian RGB card (and the one built into the 8С, service manual fig. 5.8) latches four dots of the 74LS164 on the colour clock and sends them as G, B, R, intensity, which is why its colours are wrong. `rgb-stock` does that; `rgb` is the Apple palette (table 2.8). `rgb-variant` is the Tashkent «Вариант» card (`rgb_rom`, its КР556РТ4 `pravetz-rgb-variant.bin`, hand-drawn schematic in `docs-external/pravetz/cards/RGB_images`): the PROM gives CGA IRGB (D0 B, D1 G, D2 R, D3 I). The address order of the four dots (first dot A0, then A2, A3, A1) is fitted: with it table 0 gives each Apple colour its CGA match, except grey 5 which the PROM makes dark blue (as dumped, not corrected). Table 1 (A4) is table 0 for the window one dot earlier; the schematic does not show what drives A4, the device takes it as the half-dot delay of a hires byte. The mapping of the four dots to the outputs is read off the schematic and not checked against a photo.
- **MEGARAM takes its 64K page from a write to $C073**, like the RamWorks: the board has a 74LS173 (16 pages) and no ROM, X0 carries *PDL.RESET and the data bus; the ramdisk of the «Вариант» school disks sizes it by writing $0F..$00 there under ALTZP (`work-pravetz-8a-megaram`). It is not a Slinky (that one is a slot card with a port and a ROM). The video always shows page 0.
- **The Disk II boot PROM of the Правец card is four КР556РТ11** (256x4): 5H/5L the P5, 6H/6L the P6. Address lines A5 and A7 are swapped and the high nibble's bits reversed; undone, P5 is 341-0027 byte for byte (`files/fdc140-p5.bin`). The 8С has it in D38 at $600; D38 also holds the Centronics ($C100) and the 8250 ($C200, registers $C098-$C09F) firmware.
- **Liberty Drive (`liberty-fdc` + `wd1793`) is reverse-engineered from its ROM** (`docs-external/pravetz/cards/LIBERTY_Liberty_ROM_DSK/analysis/LIBERTY-SPEC.md`). The ROM needs what the other ВГ93 machines never asked for, all opt-in parameters of `wd1793`: BUSY at the first status read after a command (`register_delay = 0`; a seek to the same track still takes a step), heads apart from the track register (`physical_head`: TR00 from the head, a 40-track drive stops at 41, which is how the ROM tells it from an 80-track one), index pulses in the type I status (`index_period`), Read Address (now for every machine). Its NOT READY is the inverse of latch bit 6, cleared by reset, which makes the driver detect its drives again. A type II command now clears an RNF left by an earlier one. `disk-pravetz-8a-liberty` reads blocks 2, 15, 25 and 799 through the ROM's ProDOS driver; mind that `PR#5` leaves CSW at the card, so a program booted that way must print through COUT1. Write Track parses the byte stream into the sector image (ID after $FE, data after $FB/$F8; $F5-$F7 never open a field), `disk-pravetz-8a-liberty-format` formats cylinder 3 with its own routine (`tests/files/make-liberty-format.py`).
- **The 8С ports**: Centronics is configuration (`cent-data` port: a write latches the byte and its access strobes `printer`; `cent-status`: bits 6 and 7 = printer busy - the D38 firmware writes $C090 and waits for $C091 < $40, i.e. BUSY and "no ACK yet" both gone). RS-232 is the new `ins8250` (D24, 1.8432 MHz; the D38 firmware at $C200 is a split-screen terminal at 1200 baud that writes THR without looking at THRE); INTRPT goes to the CPU IRQ. `work-pravetz-8c-ports`.
- **Dummy cycles**: `dummy_reads = 1` on the Правец CPUs (NMOS only): the read at the uncarried address of an indexed access (reads on a page cross, writes and RMW always) and the write-back of RMW. `work-pravetz-8a-dummy`: `INC $C030` is three speaker accesses, `LDA $C0F3,Y` across a page is the second read of $C083.
- **Cards answering their own pages**: `slotN = device` in `apple2-mmu` sends every access of that $Cn page (and of $C800 when the slot owns it) to the device with the full address; a read of $CFFF returns the owner's byte before the release. `apple2-parallel` (Epson APL and copies) puts printer BUSY into bit 7 of $CnC0-$CnFF, which the firmware polls at $CnC1; its strobe is a 0-1-0 pulse because the printer ignores the first rise from an undriven line. `pravetz-ulan`: ACIA at $C0n3/$C0n7, RTS = ROM A11, station number read at $CFFF (DIP switches SA on the photos). Its line self-test sends a break and waits for an IRQ from a detector that is not known without a schematic: it stops at «ДЕФЕКТ #1».
- **COMport**: the protocol is from the card ROM (spec, with a 6502 simulation of PR#5, in `docs-external/pravetz/cards/COMPORT_src/COMPORT-SPEC.md`). The ROM uses the DOS command codes (1 read, 2 write), the older Pascal servers 0/1: follow the ROM. The PC is `comport-server`, the far end of the card's `ins8250` (`peer`). Image 1 must be the COMport-patched DOS (`files/comport-disk1.dsk` = DISK#1.PDS of the kit; a stock DOS has no `JMP` at $BD00 to hook). `disk-pravetz-8a-comport` boots it, saves to D2 and gets I/O ERROR from D9.
- **Shipped disks** (`software/pravetz`, from agatcomp.ru): the 8А/8С `fdd0` starts with `sptu20.dsk` (DOS 3.3 + menu), so every Pravetz test that wants an empty drive begins with `COMMAND fdd0.eject()` (`boot-pravetz-8a-disk` boots the menu). The Liberty `lfdd0` starts with `liberty-system.img`, the controller's own disk: `disk-pravetz-8a-liberty-system` formats it with the LIBERTY file manager (F1+F), which builds the track and calls the ROM's Write Track entry $CEFD. COMport: `disk_title_N` makes `disk_N` an editor field; `disk-pravetz-8a-comport-copy` copies a whole disk from slot 6 to image D3 with the kit's COPY (the result was checked byte for byte against the source image while writing the test).
- **Snapshots with cards**: `state-pravetz-8a-comport` (the server images travel in the device state; `comport-server::state_owns_file()` keeps the `disk_N` files out of the bundle, which had made the snapshot 224K instead of 77K) and `state-pravetz-8a-liberty` (latch, heads, the driver's drive types: the loader reruns from $0801 with `cpu.setreg`). PARIS (`disk-pravetz-8a-paris`) starts, asks the date itself (no Time RAM needed) and edits; printing to the Epson APL card hangs before the first byte (it waits in the internal $C800 firmware; its printer is «MULTIPRO T», not identified). TETA.OBJ of the СПТУ-20 menu needs `BLOAD RUNTIME` first (it starts with `JSR $0803`), on a real machine too.
- **Programs checked on the shipped disks**: COMport disk 1 - XONIX (`disk-pravetz-8a-comport-xonix`), FILES and COPY run; SPY HUNTER and RASTER are truncated in the image (13 of 136 and 21 of 144 data sectors in their only T/S list; DOS rereads it forever, on the Disk II as well), STARTCOLOR is a fragment of COPY's CHANGE BOOT PROGRAMM. Liberty disk: XONEX SHELL, LIBERTY.SYSTEM (with formatting), BASIC.SYSTEM (runs STARTUP, a file chooser), CONVERT.SYSTEM (Apple/PARIS text converter) and PARIS run. TYPE now asks `needs_shift_char()`: in the 8-bit table of the 8А a capital needs Shift (the key alone gives the small letter); before, TYPE typed everything small there.
- **Disk II with the P6 sequencer** (`apple2-disk2`, the default of every Правец): the P6 layout is MAME's (address bit 4 the read pulse, low; 3/2/1 Q7, Q6, QA; next state in data bits 7,6,4,5 to address 7,6,5,0; the write line flips with address bit 7) - the layout of the textbooks gives nothing sensible. The sequencer catches up to the processor's bus cycle at every access (`CPU::bus_time()`, the 6502 counts its accesses; devices are clocked in batches, so `bus_cycles` within an instruction alone drifted). A track is bits while the disk is in (a cache per drive): rebuilding a track from the bytes it round-trips through shifted it, and DOS wrote a sector at the wrong place after coming back. The motor turns a second after $C0n8, else DOS waits its whole spin-up every call. The stepper follows the head (phase = half track & 3), not the last phase. Fitting tracks to a 200 ms revolution was tried for INIT and dropped: INIT works without it once the cache is there, and it broke a .nib loader. It also found a 6502 table bug: ORA/AND/EOR/ADC/CMP/SBC abs,X took 5 clocks (the page cross added a sixth); DOS writes a nibble in exactly 32. Tests: `disk-pravetz-8a-init` (SAVE, LOAD, INIT), `disk-pravetz-8a-nib` (a protected .nib that wants write protection).
- **WOZ** (`fdd_woz.cpp`): the drive keeps the bits of every TMAP track (a byte per bit) and nibbles made of them in `buffer` for byte controllers; `apple2-disk2` reads quarter 2 x half track, writes the track back whole (a write on a blank quarter makes a track there and on the quarters beside it). A disk of bytes is saved as `.woz` through `FDD::nibbles_to_bits()`, the same rule the controller uses (a run of 4+ $FF is 10-bit sync). The snapshot carries the WOZ itself (`media/*.woz`) next to the nibbles. The bit cell is 4 us at the real processor clock (8.14 steps on the 8А); a cell of 8 steps read exactly fine but was not the drive. Writing keeps 8-step cells, what the sequencer makes - with the read cell there, two flux changes fell into one cell now and then. The WOZ 2 optimal bit timing is kept but not used: at 3.5 us (Border Zone) the boot ROM loses bytes - a full byte stays ~14 steps in the register, a LDA/BPL loop samples every 14; a Python model of P6 with the ROM loop (26-29 clocks) loses them too, 7.5 steps a bit does not. MC3470: past 3 zeros, a cell gives a pulse with p = 0.3 (xorshift, in the state); the Print Shop Companion reaches its menu only with it. Tests: `disk-pravetz-8a-woz`, `disk-pravetz-8a-woz-halftrack`, `state-pravetz-8a-woz`.
- **Tape of the 82/8М** (`tape_apple.h`, encoding `apple`): the IOU toggles `tape_out` on $C020 and reads `tape_in` in bit 7 of $C060 (the 82 has no SOFTSW). The decoder takes every edge as a half period: >= 575 us header, < 375 us bit 0 or sync, the first short half after 64+ header halves is the sync, its second half is skipped; the last half of a record has no closing edge, its pair is completed when the record ends. ### Правец-8Д (`Pravetz-8D.cfg`)

An Oric Atmos clone, nothing of Apple. Sources: MAME `tangerine/oric.cpp` (`prav8d`: wiring, keyboard matrix, ROM CRC 58079502) and Oricutron (`disk_pravetz.c`, `ula.c`, `tape.c`), kept in `docs-external/pravetz/8d`. The ROMs are from the Oricutron package (Aminet `misc/emu/oricutron.lha`): `pravetzt.rom` = MAME's, `8dos.rom` (512 bytes, CRC 49a74c06). agatcomp has nothing on the 8Д.

- **The machine is configuration**: `via6522` at $0300 (new, generic), `ay8910` with `bus = pins` (BC1 = CA2, BDIR = CB2, data = PA; the address cycle's upper nibble must be 0000 or the chip ignores the data cycles, as MAME's `m_active`), `scan-keyboard` with `decoder_bits = 3` (row = PB0-PB2) and the new `colmask`/`sense` lines (sense = a key down in the row within the AY port A mask, active low both; PB3 of the VIA), `oric-ula`, and the mapper. The VIA moves CA2 and CB2 one after the other, so leaving the address cycle passes through a write of the address byte to the register - MAME does the same; the program's data write follows.
- **Disk**: the Правец controller is a Disk II on $0310-$031F (same register order as $C0E0) plus a 512-byte ROM seen at $0320-$03FF. A write to $0380-$0383 latches A0 = overlay (RAM at $C000-$FFFF instead of the BASIC ROM) and A1 = the ROM half: a `port-address` drives the mapper `~config`. `CALL 800` (Oricutron types it for its autoboot) runs $0320 of half 0, which copies `STA $0382; JMP $0320` to $02EA and jumps there; half 1 is a P5-like loader: 6&2 table at $B456, sector 0 of track 0 into $B800 (it compares the sector with $79 and the track with $7D, left 0 by BASIC), `JMP $B800`. The rest of 8DOS comes from the disk. `disk-pravetz-8d-boot` uses an own boot sector (`tests/files/make-pravetz-8d-boot.py`) that also checks the overlay; the real system disk «8D RDOS 2.31 V 254» (`dos8d_231.dsk` from the user, shipped as `software/pravetz/rdos231-8d.dsk`, the default of `fdd0`; empty catalog, 507 free sectors, a .dsk in DOS 3.3 order) boots, and `disk-pravetz-8d-rdos` does SAVE, LOAD, RUN and DIR on it.
- **Keyboard**: the ROM table at $FF78 (64 codes, Shift +$40): letters are $E1-$FA, and bit 7 of $020C (C/L toggles it) leaves them $61-$7A (Cyrillic glyphs of the 8Д font) or turns them into $41-$5A. Shift+letter is always Latin. Ю Ш Э Щ Ч are only Shift + @ [ \ ] ^ ($60, $7B-$7E) in either mode, so the map puts the host keys ` { | } ~ there (their ASCII is those codes) and TYPE uses `rus_layout = koi7-shift`. The font is Bulgarian: $79 (key Y) is Ъ, not the Ы of КОИ-7, and there is no Ы (MAME labels the key "Y Ъ"); $7F is a bar. C/L is Caps Lock, МК is Ctrl. The ROM keeps one key: what is typed while TEXT copies the font is lost (on the machine too) - scripts wait after TEXT/HIRES.
- **ULA**: as Oricutron (attribute cell = paper, per-line reset to white on black, mode persists, blink on frame bit 4); MAME blinks at half that rate. The 50/60 Hz attribute sets 312/264 lines of 64 clocks at the next frame (the subclass changes `m_lines`). The picture is lines 0-223 of the frame; the vsync-to-CB1 cable option of MAME is not modelled.
- **Tape** (`tape_oric.h`, encoding `oric`): bits from the rising edges of PB7 (T1 free-run), framing 1, 0, 8 data LSB first, odd parity, 1 1 1 (Oricutron's generator). Loading lengthens the leader by 80 $16 and adds 100 ms of 1s after the header's name; saving cuts the ROM's long leader back to four $16. `tape-pravetz-8d` round-trips CSAVE/CLOAD. The motor is PB6 (`~motor`), so CLOAD starts the tape itself.
- **Review notes**: a T1/T2 write starts counting a clock later (flag at N+2, Oricutron's figure); AY ports are $FF while R7 makes them inputs (the keyboard mask after reset selects no column); the ULA mode walked by `render_all()` on the render thread is a copy; the encoder looks for a header only past the data of the previous record (its length from the header), the decoder trims a leader only right after a pause - data may hold $16 $16 $16 $24.
- **RESET is NMI**: the Oric-1 schematic (`docs-external/pravetz/8d/Pravetz_8D_Circuit.png`, BN0130 issue 7, 1984; not the 8Д's own board) has SW1 on NMI of the 6502; it also confirms the tape (PB7 out, CB1 in, relay from PB6), printer (PB4 strobe, CA1 ack) and keyboard wiring above. `scan-keyboard` `nmi_key = f12` drives `~nmi` of the CPU; the ROM warm-starts and keeps the program (`work-pravetz-8d-nmi`).
- **On-screen keyboard**: `files/pravetz-8d.svg` from `tools/pravetz-keyboard/make_keyboards.py` (`build_8d()`), laid out after the photo on Wikimedia Commons (File:Pravetz-8D.jpg): ОСВ (Esc) starts the Q row, МК the A row, Cyrillic above Latin, Ø, Shift drawn as an arrow. The ids are those of the hand-written matrix table `files/pravetz-8d.keys`. The photo agrees with MAME's remarks (DEL left and C/L right in the 5th row, Ч the 3rd key after P).
- **Picture lag in the window**: `apple2-video` and `oric-ula` drew every line but never set `was_updated`, so the window showed a frame only after a full redraw - keys seemed to answer seconds late on every Правец, while the suite passed (`SCREEN` reads the surface). Both set it with the last picture line now.
- **Not done**: the printer (PA + PB4 strobe, CA1 ack), the slow tape format, the VIA shift register.

## УК-НЦ

- **The УК-НЦ printer follows UKNCBTL** (`Board.cpp`, `SystemFrame`): data = port A of the ПП ВВ55 as written, strobe = PC7 active low (`~strobe = !pp-printer.CH[3]`: an output half carries its bits from 0), acknowledge = PB7, on line = PB1. The acknowledge here is `printer.busy`: up on the strobe, down when the byte is done. The printer shares the socket `lpt` with the Covox (default Covox): a printer always on line would change PB1/PB7, which programs read (Bad Apple checks the port). `printer-line ~a = 0` keeps the other status lines low, and `printer` is declared after `printer-line`, or its first values would be driven before the mux links to them (`tests/scripts/work-uknc-lpt-print.ecat`). Neither the ПП ROM nor LP.SYS prints: LP.SYS (CSR 176664, vector 464) hands the bytes to channel 1, whose ПП interrupt (330 -> 175754) only does INC @#7074, and the ПП dispatcher (174164) then calls the task in 7120. RBTRON.SAV puts the printer task there (at 023670 on `sysimage.dsk`); without it the bytes go nowhere and COPY still reports them copied. That task reads the status with word instructions at odd addresses (BIT #2,@#177101 for on line, BIT #200,@#177101 for the acknowledge) and drops the strobe with BIC #200,@#177102, which only works because the ВВ55 decodes A0 on the low byte (see core.md, odd word cycles). LP.SYS of this system asks `Page?` before it prints. Checked: `RU RBTRON`, then `COPY STARTS.COM LP:` prints the file
- **An interrupt request that is a one-shot event must be cleared by the acknowledge, not by the level**: a 1801 processor reports taking a vectored interrupt on `~iako` (the vector, for an instant). The УК-НЦ channels latch a request on the transition to ready and drop it there. Computed as "ready and enabled", the free transmitter of channel 0 was offered again after every other interrupt, and its ROM handler (175540) steals a character from the keyboard buffer when the ЗАГРУЗКА menu is waiting for input - the menu got the arrow code without its ESC and ignored it. The regression is `work-uknc-menu`
- **The УК-НЦ video controller's registers are loaded by the frame pulse** (`UKNCDisplay::reset_walk()`, from the reverse engineered ХМ1-136 in `docs-external/UKNC/BMK_texts`): the list from 0270, two-word, cursor off, and also the palette 0x76543210 (colour n = YRGB n), the cursor word 0x0008 and scale 1; the brightness bits stay. A table that sets its colours lower down shows these above that line. `boot-uknc-display-frame` is the test. The same texts give the ПП interrupt order of ХМ2-001 - 310 (timer event), 304 (timer zero), 300 (keyboard), then the channels: in `UKNC.cfg` the timer is nearest the processor, and `work-uknc-virq-order` points the vectors at loops of its own to see which one is taken. They describe ХМ1-032/003/136 and ХМ2-001, not the 031 of the литера 7 the timing measurements come from; a memory model built from their timing diagrams fits TSSPD worse (1.6 / 1.7 clocks) than the fitted one (0.53 / 0.97)

## Орион, Радио-86РК, Апогей, Микроша: РУС/ЛАТ

- **A tape write can leave the emulated keyboard in the other alphabet** (known bug, Орион-128): `scan-keyboard`
  takes its Rus/Lat register from `~ruslat_led`, and the Орион monitor writes the whole of port C - data bits
  included - while saving to tape, so the indicator line ends up data dependent while the monitor's own flag
  (`$F3E5`) does not move. `RUS_REMAP` then presses the key from the other half of the layout: `I` arrives as
  `$5B` and the monitor answers `?`, which looks exactly like a tape read failure. `LOG keyboard.rus` against
  the machine's own flag separates them; two presses of РУС/ЛАТ resynchronise. Радио-86РК, Апогей and
  Микроша are immune - their ROM re-asserts the indicator from its own variable on every keyboard poll. Left
  as is on purpose: the indicator is the only signal of the register, and the remap is what lets a ЙЦУКЕН
  host keyboard drive a ЯВЕРТЬ machine
- **The indicator line is taken into the register at a scan write, never the moment it moves**: the
  Радио-86РК and Апогей ROMs zero the whole of port C on every keyboard poll and set PC3 back from their flag
  a few instructions later (Апогей `$FE7F-$FE89`). Following `~ruslat_led` instantly made the drawing's РУС
  lamp flicker and could remap a host key typed inside that 20 us dip. `ScanKeyboard::interface_callback()`
  latches the line and applies a change of it on the next write to the scan lines, which the ROM does before
  the dip and after the restore
- **РУС/ЛАТ flips on the press, never on the release**: `ScanKeyboard::key_down()` toggles `rus_mode`, `key_up()` only releases the line. Toggling on both edges cancels itself out and leaves the register wherever the indicator line (`~ruslat_led`) happened to point - which the Орион configs used to paper over with an inverted `~ruslat_led`. All three now wire it straight, like РК86 and Микроша, and the register follows the monitor's own flag ($F3E5)

## ВГ75 (Радио-86РК family)

- **`I8275::clock()` must jump between events, not step per character clock**: it is driven at the character clock (1.33 MHz on a Радио-86РК, and the loop body is entered ~7 times per emulated instruction), so stepping one tick at a time costs a quarter of the whole emulator. Only two things happen inside a character row — the next DMA transfer and the end of the row — so the beam advances straight to the nearer of them; `m_dma_delay` is the full period until the next transfer, counted down by `clock()`, and `dma_tick()` is called only when one is due. Getting that period off by one silently changes the burst pacing and every reference screenshot with it.
- **The ВГ75 frame is drawn from a snapshot, never from live registers**: `I8275` runs on the emulation thread and may be reprogrammed at any moment, so `I8275Display` copies the row bytes plus the geometry, font bank, cursor and blink phase when the row is fetched, and the render thread lays the frame out from that alone. Reading `chars_per_row()` / `char_height()` while drawing means one row drawn with the width of one raster and the height of another.

## Ириша

- **A machine may carry several disk controllers of different types**: `Irisha-kngmd.cfg` has `fdc : wd1793` (5.25", drives A:/B:) and `fdc2 : gmd70` at ports 50-51 (8", drives E:/F:). Nothing is special-cased by name: the GUI finds drives by class `fdd`, the scripts by device name (`fdd2.track`). Only `cpu`, `mapper`, `display` and `keyboard` are reserved names (and `bios` and `mapper` in the loaders of `files.cpp`). A controller takes its drives with `FDC::load_drives(min, max, list)` (defined in `fdd.cpp`), which checks the count against the controller's selects and that each name is an `fdd`: the five controllers used to parse `drives` each on their own, and only one of them checked anything.
