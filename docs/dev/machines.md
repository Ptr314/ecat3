## Поиск-1 (IBM PC clone)

- **The Поиск-1 follows MAME (`src/mame/pc/poisk1.cpp`) except for the video memory**: it is the top 32 KB of the board RAM (shared with the processor, hence the wait states), not a separate buffer - but seen by the processor only through the B8000 window (`poisk-vram`), never at its own address. The 1991 BIOS sizes the RAM by probing 16 KB blocks up to the first gap; with the top 32 KB mapped it reported them as free and DOS put COMMAND.COM into the screen. CGA ports and writes to B8000-BBFFF trap through NMI (`poisk-trap`), and the BIOS draws text itself. The floppy cartridge B504 is a КР1818ВГ93 at C0h-C3h plus `poisk-fdc-control` at C4h (drive/motor/side, MR on D6 - a Restore when it goes high, which the ROM waits for; a read of C4h runs the controller to DRQ/INTRQ; a write to C6h restarts the motor one-shot, bit 0 of C6h reads 1 once it has run out). The factory driver ROM waits ~0.25 s for the motor before every operation on A: (its "motor already on" test compares with the drive number, 0 for A:), which is why DOS boots in about a minute; `Poisk-1-fdd302.ext` carries the Moscow v3.02 ROM, which waits only after the one-shot ran out. The factory BIOS INT 16h decrements AH in place and returns it changed for an unknown function, so a program probing for the AT keyboard with `AX=11FFh` (Volkov Commander 4.99) decides it is there and then polls functions 10h/11h that do nothing - an incompatibility of the real BIOS, not of the emulator. `LOG cpu.history` lists the last 256 linear addresses on the 8088 too.
- **A 20-bit address space needs `address_bits = _20` on the mapper**: the page table is sized from it, and an address above it takes the linear scan.
- **The cassette is the IBM PC one** (`encoding = ibmpc`, `tape_ibmpc.h`): a bit is one period of the square wave of PIT channel 2 (1184 counts for a 1, 592 for a 0), written to tape from `pit.output[2]` and read back on port 62h bit 4. The BIOS times the halves with channel 0, which is what found two faults of the shared `i8253`: a latch command kept only the low byte (the high byte read was stale), and a count written to a running mode 2/3 channel restarted it and flipped OUT, so every bit got a spurious edge (the write path rewrites channel 2 after each edge). Both are fixed for every machine; the regression suite passed unchanged. A `.cas` is the PCE format - the record's bytes with the leader as FFh and the sync bit as FEh. The BIOS writes records back to back with no pause, so the decoder recognises the next record by its leader: a run of 2080 ones (32 of the trailer + 2048), longer than any block of FFh bytes can give. A `.cas` that does not start with a leader is a bare file (digitised cassettes are often kept so, `TETRIS.CAS`): the loader wraps it into a header (A5h, the file name as is - the BIOS compares it byte for byte, capitals included) and a data record. The BIOS menu runs a loaded file on Enter only; any other key returns to the menu
- **`wd1793` has one slot for a delayed register write**, and a 16-bit OUT of the 8088 writes two registers within one instruction, before the devices are clocked: `set_value()` applies a waiting write before it takes the slot, or the first of the two (a command, a sector number) was lost
- Tests: `boot-poisk*`, `work-poisk-*` (`work-poisk-tape*`: read, write + read back, bare file) and `state-poisk-tape` / `state-poisk-tape-write` / `state-poisk-disk` (a snapshot in the middle of a tape read and of a tape write - a restored recording must set the decoder up again; graphics plus a sector that lives only in the drive buffer). `Poisk-1-cart-ram.ext` stands on `Poisk-1.cfg` itself and repeats the 128 KB edits: an extension on another extension is not packed for the web

## ДВК (`deploy/computers/dvk`)

ДВК-1/2 are the МС1201.01 board (К1801ВМ1, monitor ПЗУ 000) with the 15ИЭ terminal, ДВК-3 the МС1201.02 (КМ1801ВМ2, monitor 279 or 055, КСМ, КГД, MX, MY, DW), ДВК-4 the МС1201.04 (КМ1801ВМ3, monitor 134, КЦГД, MX, MY, DW). **Four shipped machines, one per model**: what was a separate variant is a switch or a test machine. A ROM that was a replaceable chip is a `rom` with `image_1`, `image_2`, ... (`title_N`, `label`): not a toolbar option but a choice field of the configuration editor (`ROM::get_config_fields()`), written into an extension as `image` - БЕЙСИК/ФОКАЛ on the ДВК-1, monitor 279/055 on the ДВК-3, monitor 134/377 and КЦГД firmware 181 / 182 / 182 + KeyGP on the ДВК-4 (181 first: most КЦГД software is written for it - 182 points every empty screen row at one shared video line, which FIGHTR draws into, and LOAD.SAV, the firmware extension COLUMN, MINE and others need, patches 181 and breaks 182's output; KeyGP breaks the games that load code at 040000, see below). Without `image` the first one is used. Tests pick a variant with a small extension in `tests/files` (`dvk3-055.ext`, `dvk1-focal.ext`, `dvk4-kcgd181.ext`, `dvk4-keygp.ext`, `dvk4-ksm-377.ext` - the last stands on `dvk4-ksm.ext`). Two-position options (the panel's «Пульт» and «Прерывания») are `DEVICE_OPTION_TOGGLE`: a checkable button on the toolbar and on the page (`wasm_device_options()` carries the type), values 0/1 as before, so the ini, `COMMAND panel.option(id,v)` and recordings are unchanged. The ДВК-4 with the КСМ (`tests/files/dvk4-ksm.ext`; `display.text` cannot read the 182 font) and the ДВК-3 with the КЦГД (`tests/files/dvk3-kcgd.ext`, monitor 055) live in the tests only. `kcgd-display` reads the firmware font when the text is asked for, not at reset: the switch changes the firmware after the reset. The documentation and the ROMs are in `docs-external/DVK/`; register maps follow the FPGA replica github.com/forth32/dvk-fpga and MAME (`dvk_ksm.cpp`, `dvk_mx.cpp`, `dvk_kgd.cpp`).
- **The terminal КСМ is a second machine**, not a display controller: its own i8080 (`ksm-cpu`, own mapper and clock domain) runs the real firmware (ksm_04/05) with an 8259, two 8251 and an 8255; `ksm-display` only scans its video RAM. It talks to the ДВК through `dl11` `~txd`/`~rxd` (byte-wide links) and nothing else. The КСМ firmware needs ~0.35 s after power-on before it takes characters from the line, while the ДВК monitor prints its first prompt at once. On the real machine the start is given by the power panel, modelled by `dvk-panel` (the author's Arduino replica `DVK_Control`): POWER GOOD after `power_good` (500 ms), АИП (`~dclo`) 13 ms later, АСП (`~aclo`) 10 ms after that. Without it the first prompt was lost. Do not put such a delay into the processor. Its two switches are device options (toolbar drop-downs, `COMMAND panel.option(id,v)`): «Пульт» drives ОСТ (`~halt`, a level - the CPU cannot leave the console while it is on) and «Прерывания» the 50 Hz ПРТ square wave, which is the line clock everywhere: `~irq2 = !panel.prt` on all three processors. The МС1201.04 has no LKS register (netlist: XS1 BA14 -> D7 -> S7 -> VM3 EVNT, nothing gates it; `dvk-lks` is the FPGA replica's and stays only in `vm3-test.cfg`), so nothing masks the line: the 134 monitor runs its memory test with interrupts open and fails with the switch on, which is why the ДВК-4 starts with «Прерывания» off and `boot-dvk4-xm` turns it on after the prompt. Without LKS, RT-11 reports no system clock in SHOW CONFIG (`cpu.irq2_requests` counts what reaches the processor). The 055 monitor's `P` is the ВМ2 STEP, which proceeds (RTT-like: the first instruction is fetched without an interrupt poll, and nothing returns to the console after it - an earlier model returned at once and executed nothing, so `P` looked like a dead single step). `k1801vm1` starts only when both lines are released: ACLO released after DCLO is the power-up, not the interrupt through 024. The tests still press ВК first
- **The 15ИЭ-00-013 terminal of the ДВК-1/2 is written in code** (`ie15` + `ie15-keyboard`, `dvk_ie15.*`), not run from its firmware: the dumps in `docs-external/DVK/15ИЭ` are for the terminal's own discrete-logic processor (MAME has a core for it), and the user chose the behaviour in code. Almost VT52 (MAME: no Hold Screen, no graphics set), Cyrillic through SO/SI, glyphs from its real character generator (`ie15_cg.rom`, 256 x 8 bytes, KOI-8, bit 7 = left pixel; cell 10 x 11, 80 x 24). The keyboard is the Ириша's 15ВВВ - `15vvv.keys`, `15vvv.map` and `15vvv_keyboard.svg` moved to `deploy/data` for both - a `map-keyboard` whose codes go to the terminal (`send_key()` is virtual, `port-value` optional for it). Arrow and home codes ($1C/$1D/$19/$1A, $08) become ESC A/B/C/D/H only from the cursor block (the keyboard's ДК line; $08 is also Ctrl+H). The host Backspace sends ЗБ (DEL, `key_bksp`) on the ДВК: the shared map gives it $08 for the Ириша, while RT-11 and BASIC erase by DEL. The five mode switches (ДУП, ЛИН, РЕД, ПЧ, СДВ) have no codes: `ie15-keyboard` registers them with the new generic role `toggle` (`KEY_ROLE_TOGGLE`, kept in `Keyboard::m_toggled`, saved in a snapshot); ЛИН off is local mode, ДУП off is half duplex; both on at power-on, a machine reset leaves them. All eight lamps live (MAME `ie15.cpp`: ЛАТ, НР = case latch, ПРД always, the five switches). Key codes from the GUI thread are queued and handled in `clock()`. `COMMAND display.receive("...")` feeds bytes as if from the host (`decode_send_text()`, moved to `utils`); `work-dvk1-ie15` is the test
- **The МС7004 drawing** (`ms7004_keyboard.svg`, source `src/pics/ms7004_keyboard_font.svg` - keep the ids of both the same) works through `ms7004.keys` (`id: LK201 code`; `MS7004::parse_key_table()`/`send_key_id()` press the key through the same `press()` as a host key). Codes come from the keyboard firmware's matrix table (`ms7004.lst` 0380-03FF); the keys LK201 lacks are placed by matrix column: `key_lcurl` $FC, `key_rcurl` $F5, `key_tilda` $C9, `key_lf` $C4 (the КСМ gives LF), `key_hard` (Ъ) $F1, `key_under` $FD. LEDs follow the firmware (0531/05FF): $13 + `1000abcd` lights, $11 darkens (d wait, c compose, b lock/ФКС, a hold/СТОП КАДР); `1001xxxx` is ЛАТ on P1.5, inverted ($11 lights it); $89/$8B light/darken wait; $FD and reset darken all. The КЦГД 181 sends $11 $90, $13 $90, $11 $90 at start (ЛАТ lit) and lights СТОП КАДР; the КСМ ROM never writes the keyboard channel's data port (only 8251 control words to 6F), so on the ДВК-3 the lamps stay dark - `keyboard.~rxd = ksm-kbd.txd` is wired anyway. `command_log` shows the last 16 bytes from the terminal; `work-dvk4-ms7004-leds` is the test
- **The КСМ 8259 answers the 8080 with CALL** (8080 mode, ICW1 D6h / ICW2 0Bh, level n -> 0BC0h + 4n): `i8080` `int_opcode = $CD` takes the address from `~int_address` = `i8259` `~call`, and drives `~inta` low in `reset()` so the first acknowledge is an edge.
- **`ms7004` sends LK201 key codes as they are**; the КСМ firmware turns a code into a character through its table at 0AFD + ~code (the `CMA` there belongs to the table index, not to the line). The МС7004 is ЙЦУКЕН with Latin letters on the same keys (J on the Q key); the host map gives Latin letters to keys with the same Latin label, `use_remap = 0`. **Both terminals change the case of the Ш Щ Э Ч Ю Ъ keys like letters** (Latin: 133-137 and 100): with ВР Ю is `` ` ``, Ч `~`, and Ъ on the КЦГД 181 is DEL (177). So every such sign is marked `-shift`/`+shift` plus `letter` (`[ ] \ ^ @ _` lower, `{ } | ~ `` ` `` upper; `` ` `` is host key `~`, `~` is `tilde`; `work-dvk4-ms7004-symbols`). ФКС inverts the letter group on both terminals and on the КСМ also the digits and signs (a true shift lock), so the keyboard inverts ВР for a marked sign while the terminal's ФКС is on, by `fks`: `lamp` (КЦГД: the ФКС lamp, which 181 drives from 11042 and which toggles only with ВР held; `letter` signs only, and only while the ЛАТ lamp is lit, since in РУС these keys are letters) or `toggle` (КСМ: it drives no lamps, but each ФКС press flips 20B4 bit 2 (05CD), so the keyboard counts the B0 codes it queued; every marked sign; `work-dvk3-ms7004-fks`). Unmarked letters still follow ФКС, which is how a user gets PC-like case. **B4 differs between the firmwares**: КСМ and КЦГД 182 resend the stored character (pressing ВР clears it), while КЦГД 181 (110410) re-translates the last stored key code under the current ВР and does not store ЗБ (177 bypasses 110200), so holding ЗБ repeats the character before it, and a character typed with ВР repeats without it once ВР is up. This is the firmware, not the model.
- **`ms7004` follows the keyboard's own firmware** (`docs-external/DVK/MC7004_keyboard_original.rom`, commented disassembly `ms7004.lst` in CP866), which is not LK201: every release of ВР or СУ sends B3 (0231), even with the other still held; a held key's release sends nothing; three ordinary keys at most. The КСМ firmware takes AE and AF as "down" only and B3 clears СУ first, ВР only when СУ is already clear (0587) - so ВР released under СУ leaves the terminal with ВР down and СУ up until СУ comes up, as on the real machine. An older model sent B3 only when no modifier was held and the code again otherwise, which left ВР latched after Windows' Ctrl+Shift. **Autorepeat is the keyboard's**: the last pressed key, while held, gives B4 after `repeat_delay` (360 ms) and every `repeat_period` (28 ms) - counted from the firmware's cycles: 46 cycles = 150 us by its comment, a matrix pass ~33 ms, 11 passes - except ВК (BD), the top row (< 80) and 80-8F; the terminal repeats its last character (КСМ 057A, unless its setup turned autorepeat off; КЦГД 181 the same, checked by sending B4). The window drops host autorepeat (`isAutoRepeat`), so before this the ДВК had none. **The host keypad is the МС7004 keypad** (92h-A0h, Enter = 95h; KCGD games like BABY play on keys 4/5/6 of it): a keypad digit or sign carries `EmuKey::Keypad` (= `Qt::KeypadModifier`, set by `host_layout_key()` and by the page for `Numpad*` codes; not the arrows, which macOS marks too), named `kp0`..`kp9`, `kpdot`, `kpplus`, `kpminus`, `kpmult`, `kpdiv`. `Emulator::key_event()` passes it on only to a keyboard whose `keypad_keys()` is true and gives every other machine and the joysticks the plain key, so nothing else changed; `MS7004::entry_of()` falls back to the plain key for a keypad key its map lacks. A `map-keyboard` has `keypad_keys()` true as soon as its map names a `kp*` key (`MapKeyboard::resolve_keypad()` falls back the same way): the Агат, whose right block is function keys ($90-$94, $9C-$9F, $81-$83 by Appendix 2 of the Агат-9 manual, agatcomp.ru `A9_K1`), not digits, and is taken by position - 1 2 3 on top, so host kp7 is функц 1 (`work-agat-9-keypad`) Commands: FD (01 00 00 00, repeat on), AB (01 00), 89 (B7, then silent until 8B), D3 (BA), E1/D9/E3 (repeat off/on). `work-dvk3-ctrl-shift` reads the КСМ flags (RAM 20B3/20B4) and `keyboard.repeats`
- **The ВМ2 board register SEL is one parameter, `sel`** (bkbtl-doc «1801vm1 vs 1801vm2»): its high byte is the start vector `SEL000` and the base of the console vectors, the whole of it is what RSEL (000020, unaddressed read) returns - 160000 on the УК-НЦ, 140001 on the ДВК-3, 100000 on the КЦГД. `start_address`/`start_vector`/`halt_sel`/`una_value` are the old split form, kept for test rigs and old snapshots. The start reads the vector in the console space and then takes HALT/USER from bit 8 of the PSW it got: the 055/279 monitors have 740 there and run in the console, the КЦГД firmware has 340 and runs as a normal program. **PSW bit 8 is the mode** on every word load of PSW (any vector, RUN/STEP from КРСП) and goes onto the stack with the PSW, except that RTI/RTT take it only when they return into 160000-177777 and otherwise load the low byte and keep the mode (the chip model's `dc_b7`, `ax[15:13] == 111`, fed to the microprogram as `br[7]`; UKNCBTL decides the same way): the УК-НЦ disk БЕЙСИК returns from user mode into the console by RTI (PSW 000401 to 166556), while FODOS boots on the ДВК-3 through an RTI with 052404 on the stack to 155654 and must stay in user mode. **КРСК/КРСП are not a separate pair on the ВМ2**: the chip writes them with PC and PSW unless the PSW has both bits 7 and 8 (cpu11 `vm2_wb.v`, `pc_wr`/`cpsw_stb`), so a console entry through a vector with 0600/0740 freezes them on the interrupted program, while in the console with priority 0 (PSW 0400) they track PC/PSW - MFPC reads the next address, START/STEP go nowhere (Alex_K's CHLT/PHLT run chains of console instructions that way). **On the УК-НЦ the console range of the CPU mapper must come before the registers**: the console sees 160000-177777 as RAM, and with the range after them 176560-177567 still answered as registers (the CHLT chain fetched from the СА register). Console instructions are decoded in ranges (START 10-13, STEP 14-17, RSEL 20, MFUS 21, RCPC 22-23, RCPS 24-27, 030 (a normalization step loop the cpu11 decoder calls «unknown»: action from the chip model, 24 clocks a step from Alex_K's C030), MTUS 31, WCPC 32-33, WCPS 34-37) and outside the console all of them are the reserved instruction, vector 010 Running the КЦГД in the console broke the RTI trace (no trace trap in the console). **The КЦГД ROM range is `strict = 1`**: КР1801РЕ2 does not answer a write, so a write into 100000-157777 is a bus timeout. The KCGD81/KCGD82 loaders (games disk, «графический протокол») rest on it and on STEP: a self-copying `MOV (SP)+,(PC)` crawls up memory until it writes into the ROM and traps through a vector 4 it set itself, a checksum of the 8 KB ROM is sent to the ДВК, an RTI into 160104 with PSW 000740 enters the console (bit 8 is taken because the return is into 160000-177777), and the console code MTPMs the payload into user memory, MTPCs its entry and STEPs into it. KCGD81 loads on 181 at 5.5 MHz; KCGD82 (182) loads with the ДВК processor at 5.0 MHz or slower (`timing = vm3`, reply 4), or at 5.5 MHz only with `reply_clocks = _6` - the player replays recorded pauses as SOB loops, and the machine it was recorded on was slower than a 5.5 MHz МС1201.04 with an 800-thousand-ops memory. On ВМ2 (and ВМ3) a T bit set by RTI traps right after it and RTT after one instruction, and a trap instruction (BPT/IOT/EMT/TRAP) is not followed by a trace trap. ВМ1 the same by its description: RTI ends with an interrupt poll, RTT and STEP fetch the next instruction without one (`m_no_poll`), so neither a request nor the trace trap comes between them and that instruction. The ВМ2 PSW is the low byte only (`execute()` masks it; a word loaded whole carried bit 11 into the FIS trap frame), and a bus timeout in the console goes through `SEL | 004` with nothing saved - the console program runs on the interrupted program's stack, which the console space may not have. The FODOS factory test disk (`deploy/software/dvk/FODOSTMO.DSK`, test monitor FTMON, chains `VM2MY.CCC` / `VM3.CCC`; `slow-dvk3-fodos-vm2`, `slow-dvk4-fodos-vm3`) found these. FTMON rewrites the vector area with interrupts enabled, so the panel's «Прерывания» switch must be off for it, or a clock tick through the half-written vector 100 halts the machine. `TSKGD1` (КГД), `012101` (КСМ characters) and `TESTMY` (MY: formatting, functional test) pass
- **The MY controller is the whole КМД board**: its own К1801ВМ1 (`kmd-cpu`, 4 MHz, starts at 010000 from the high byte of its 177716) runs firmware 255 with 4 KB RAM and a `bk-fdc` (ВП1-128); `dvk-kmd` is only the link - the host registers 172140/172142, the firmware's view of them at 177100/177102, and the DMA window 40000-77777. The window's address bits 14-21 are the low byte of MYDR: the firmware (subroutine 007550) shifts the buffer address bits 14-15 and the MYCSR bits 8-13 there itself and writes the byte into both halves (two ВП1-095 on the board; MAME takes only bits 0-1). `address_bits = _22` on the ДВК-4 (jumpers S1-S6 carry A16-A21), 16 on the ДВК-3. Host INIT is IRQ2 of the board. The netlist and BOM are in `docs-external/DVK/kmd`. TESTMY's «запись/чтение с меткой» needs the deleted data mark (F8) of a written sector to stay - the drive keeps whole tracks (`fdd` `mode = mfm_ibm`, the same for the БК and the УК-НЦ): `bk-fdc` loads its head buffer from the drive's track and flushes it back bytes and sync marks as they are (`FDD::read_track_marks`/`write_track_marks`, the AIM mark map with `AIM_CMD_DESYNC` at the first A1). The flat image is laid out by `generate_tracks_ibm_mfm` (`mfm_tools`, the ROM's own layout) and parsed back by `decode_tracks_ibm_mfm`; `.mfm` has no marks, `find_marks_ibm_mfm` finds them by the bytes (three A1 before FE/FB/F8). A drive in sector mode (an old snapshot - `state-bk-*` are such - or a config without `mode`) is rebuilt on first access, with the deleted bits an old snapshot kept in the controller. `slow-dvk3-testmy` checks `my1.deleted` across a `.mfm` round trip. The drive also saves its mark map in a snapshot now (before, the Агат 840 lost its AIM codes there). Formatting 80 tracks takes about 280 s of emulated time
- **The DW hard disk (`dvk-dw`, КЗД 3.057.316) keeps the "word ready" timer apart from the operation event (sharing one slot, a data register access in the middle of a reset or a seek cancelled it); it is MAME's `dvk_dwhle` registers with three corrections the factory test TESTDW (on the DW disk) forced**: the sector register is 1-based (DW.SYS writes (block + 1) & 15, the 279/134 boot reads sector 1 = block 0; the image is plain blocks, (cyl * heads + head) * sectors + sector - 1, as `DW_System54.DSK` of Patronov's emulator (4 heads, 16 sectors - the defaults; `heads` up to 8, `sectors`, `cylinders`, `small` for the SI 5 MB bit come from the config), shipped as `software/dvk/rt11-dw.dsk`); interrupt requests are edge-triggered - enabling IE with DONE already up gives none (MAME raises one, and TESTDW's interrupt test then enters its read handler before the read), while a reset is an operation of `init_time` (200 ms; 100 ms is too short for the same test, which waits for the interrupt from the end of the reset, and 400 ms still fits the busy timeout of its register test); and the data register without a read/write command is a 256-word ring buffer (the buffer test writes 256 words with no command - MAME sent them to the disk). The full cycle ends with code 015 «операция завершена» in cell 001000 (`slow-dvk3-testdw`). The ДВК-4 has a second controller `dw1` at 174040, vector 310, chained behind `dw`; the monitors (134, 377, 279) hard-code the 174000 registers, so it is a data disk only (`work-dvk4-dw1`, 8 heads). The image is not put into the socket by the configs: 5 MB in every web bundle; on the page the visitor picks an image on their own computer (see "Web page" in `frontends.md`). `HddImage` (`devices/common/hdd_image.*`) is the image file of every hard disk - `dvk-dw` and `UKNCHDD` (УК-НЦ, СМК/БК): shared open (`_wfsopen` with `_SH_DENYNO`), write protect, write to memory, the snapshot blob; the controllers keep only geometry and registers. `find_file_location()` checks existence with `GetFileAttributesW`/`stat`, not by opening: `dsk_tools::file_exists()` opens a stream, which on Windows fails while another process holds the file for writing - a parallel test run "lost" the image
- **The КГД has no sync generator** (`docs-external/DVK/КГД`, ПБА4.135.998): КСИ, ССИ and ГТИ come from the terminal on XP2, a one-shot on КСИ loads its address registers and ССИ steps them, so its line 0 is the first line after the frame sync. The КСМ frame is 28 rows of 11 lines (rows 4-31 of its row PROM `ksm_02_PLM_D16`, MAME's 28 * 11 at 15.4 MHz / 1000 dots; КСМ schematic У13.625.305 in `docs-external/DVK/КСМ`: the row counter D6+D7 (К155ИЕ7) is loaded with 4 - D6 inputs 0100 - by a pulse differentiated (C4/R7/R8) from the fall of row bit 4, and the frame flip-flop D11.2 is preset by the same pulse and clocked by row bit 1, which first rises at row 6): two rows of blanking, a row from F830 (spaces), the status row and 24 text rows. The 26 visible rows are the КГД's 286 lines, so `ksm-display` puts the text 11 lines down and draws the F830 row above the status line; `dvk-kgd`'s scan counter (176646) counts that 308-line frame
- **ВМ2 console instruction 000020 reads the board's startup register** (`sel`, 140001 on ДВК-3: 140000 + mode 001). The 055 monitor decides by its low bits whether to enter the console, boot or run.
- **ACLO: the power-fail interrupt (024) comes when the line is asserted, the start when it is released** (ВМ1 description: the falling edge of nACLO; ВМ2 model: `aclo_fall`; UKNCBTL). A running processor ignores the release (on the ВМ1 the ACIN input matters only for the initial start). The ВМ1 masks 024 with PSW bit 10 only, the ВМ2 with priority 7 in the console. The model used to raise 024 on the release, and that hid an inverted wire: bit 15 of the УК-НЦ PPU's 177716 is 1 for "power good" (`~aclo = pp-sys.value[15]`, as `SetACLOPin((word & 0100000) ? false : true)` in UKNCBTL), so the CPU ran with ACLO asserted and the hard-disk resident's pulse (0, then 1) gave its 024 on the release. `cpu.aclo_edges` counts the edges
- **In the ВМ2 console mode (SEL) only 140000-177777 answer** (monitor ROM, shadow RAM); the monitor reaches user memory with MFPM/MTPM. A timer request latched while in the console is taken right after RUN, so a program started with `G` needs vector 100 set.
- **ROM must not answer writes on МС1201.01** (`strict = 1`): the ROM BASIC sizes memory by writing down from 160000 and stops at the first timeout. Its own code occupies 100-..., so the line clock must stay off (no `~irq2`) - the real board has a front panel switch for it.
- **`dvk-mx` reads and writes a whole track** in FM words from the sync word 000363, and the drive keeps the disk as whole tracks (`fdd` `mode = fm_dvk_mx`, `FDD::read_track`/`write_track`, 1562 words a turn, low byte first) - the whole-track mode the Агат uses, with the generator and parser in `mfm_tools` (`generate_tracks_dvk_mx`, `decode_tracks_dvk_mx`). A flat sector image (11 x 256 per side) becomes RT-11-format tracks on load and is parsed back by the sync word on a flat save; `.mfm` keeps the tracks as they are, which `slow-dvk3-testmx` checks through the `mx.disk` field. A drive left in sector mode (a config without `mode`, an older snapshot) is rebuilt into tracks on first access, and the per-controller written tracks of such a snapshot are laid onto it in `state_restored()`. The driver ends a write by clearing the WRITE bit and immediately starts a verify read - that clear must store the track. Two STEP writes within 2 ms are one step (MAME).
- **A track the program wrote is read back word for word** - it is the disk; a write lands from the index and leaves the rest of the track as it was. The format belongs to the program: RT-11 MX.SYS ends a track with three words 0101400 + track * 2 + side, the factory test TESTMX with one word track * 2 + side; rebuilt to the RT-11 pattern the test saw a «side error». A write is not stopped by the index (as in MAME): words after it overwrite the start of the same track, and the write ends when the program clears WRITE or stops feeding words (an underrun). TSTMX (TMX V04.03, «КНГМД and drives») feeds 177777 until it sees the index bit after a TR and only then lets go - stopped at the index it never got its TR and hung; with that fixed it passes in full, type 1 (40 tracks, `slow-dvk3-tstmx`) and type 3 (МС5305, 80 tracks, both sides, on a drive with `tracks = _80`). SYST/SYST1 (with a printer), LPIN (printer), DXIN (DX interface) and TOZUDP (extra RAM board) stop on a bus timeout - the machines have none of those boards

The speed inputs FR3-FR0 (pins 6-3) are hard-wired 1100 = 57600 on D9/D10 and 1001 = 4800 on the keyboard channel D16 (table 7.7 of the ВП1-035 description, same for -065: 0000 = 50 ... 1010 = 9600, 1011 = 19200, 1100 = 57600)
- **`dvk-dx` (RX11) works on whole IBM 3740 FM tracks** (`fdd` `mode = fm_ibm`, 5208 bytes a turn, marks FC/FE/FB/F8 in the mark map, `mfm_tools` `*_ibm_fm`): a sector is found by its ID field (`find_sector_ibm_fm`), function 6 writes the deleted data mark F8 (`put_sector_ibm_fm` rewrites mark, data and CRC) and reading such a sector sets DD in RXES - before, the mark was lost on the spot. `work-dvk2-dx-deleted` drives the registers from the script and checks the mark across a `.mfm` round trip; `.mfm` marks are found by walking the fields (`find_marks_ibm_fm`)
- **`dvk-dx` (RX11): the function and unit bits of RXCS are write-only** - the standard bootstrap waits on mask 100247, which includes them.
- **The КМ1801ВМ3 (`1801vm3`) is the same `pdp11core` with a `vm3` flag**; everything of its own is in `pdp11core_vm3.cpp` (MMU, internal registers, traps, halt mode, MFPx/MTPx) and is reached through `if (vm3)` hooks, so the ВМ1/ВМ2 paths are unchanged. The bus functions of the core take 22-bit physical addresses (`uint32_t`); the machine's mapper is physical (`address_bits = _23`: I/O page 17760000-17777777, the halt-mode shadow space from 20000000 = SEL). The MMU and PSW registers live inside the chip and are not in the mapper. The spec is the chip model (github.com/1801BM1/cpu11 `vm3`, forth32 `hdl/vm3/vm3_wb.v`) plus the DEC 11/34 diagnostics in `tests/files/vm3/` (`cpu-vm3-*`; `boot-dvk4-xm` boots RT-11XM from the shipped MY disk), run on the debug machine `vm3-test.cfg` with output read from `tt.text`. Things they pinned down: the PDR W bit is set on any write through the page except a write to SR0; SR0 shows mode and page of every relocated reference until an abort freezes it; SR2 is the address of the last *successfully fetched* instruction; an explicit PSW write overrides the instruction's own condition codes; autoincrements are undone when an instruction aborts, autodecrements stay; checks NR/PL/RO are independent (both bits can be set); opcodes 7-77 are reserved
- **The ВМ3 halt mode has its own stack register (R10)** for implicit stack operations - JSR, RTS, RTI and the entry, which pushes PSW/PC at 100000 (077776/077774 of the shadow space, where the 134 monitor reads them) - while `SP` named in an instruction is the kernel SP. The monitor sets `MOV #17000,SP` for the program it is about to start and then returns with RTS PC; one shared SP threw it into garbage. `pdp11core::stack_reg()` picks the register for push/pop
- **The КМД firmwares are for different variants of the board** (bkbtl-doc wiki «1801re2 ROMs»; dumps in `docs-external/DVK/dvk-rom/`): 255 - RAM on 537РУ8/РУ10, which is our board by the netlist (D22/D23, 4 KB at 020000-027777, stack 30000); 092 - RAM on 537РУ11 (512 bytes, stack 21000); 093 - К1809РУ1 (2 KB, stack 24000); 091 - the original КМД (К1809РУ1 and the ВП1-097 disk controller instead of ВП1-128). 092/093/255 are the same program apart from the RAM; 091 is a different one. 537РУ11 and К1809РУ1 are RAMs with their own МПИ interface, and 177760 is *their* register of start address and configuration: 092/093 write it at start-up (20400, 23000) and trap through vector 4 if nothing answers - unmapped, 092 never does a DMA. The netlist has nothing at 177760 (selects are gates on AD12-15, ВП1-096 D14 is on the host side), so nothing answers it here and only 255 is shipped (all four passed TESTMY and booted RT-11 identically while 177760 was accepted)
- **Monitor 377 is an alternative to 134 for the МС1201.04** (НПП «Кристалл» 1991, author К.Е. Юдин, for МС0507.03/.04 and МС0504; `docs-external/DVK/377.pdf` is its manual): the same ROM layout (6 KB, shadow RAM in the last 2 KB), the switch «ПЗУ монитора» of the ДВК-4. At power-on it runs its tests - HALT mode, RAM (much faster than 134: about 3 s), МMU and interrupts, the hard disk (НЖД = DW: reset, buffer, read of cylinders 0 and 152) - and only when all pass boots automatically: MY0, MY1 (only a disk whose block 0 starts with 240 or 260), then DW. A machine without DW, or with no image in it, stops in the console with «? - Ошибка» every power-on (010000 = not ready, «нет устройства» without the controller); `B` asks «Boot:» and takes a two-letter device name and unit (`MY0`, `DW0`), `Tn` runs test n (table 3 of the manual), the console commands are those of the DEC ODT plus `I`/`J` breakpoints, `F` search, `K`/`U`/`=` address spaces. It draws its banner with VT100 sequences (ESC #3/#4, ESC [7m): the КЦГД shows them, the КСМ prints them raw. The MY probe waits for the board's answer to command 7 with a counted loop of ~65000 passes; the КМД answers in about 0.9 s and the probe still succeeds. `boot-dvk4-377`
- **The 134 monitor runs from a copy**: at power-on it checks itself and the terminal (a `*` sent and expected back - a loopback plug selects the factory endless test), copies the ROM to RAM 0 through the HPAR window and runs the memory test from there in kernel mode with the 22-bit MMU on; that test ends with HALT, and only then the monitor prints `@`, about 10 s after power-on. Boot is `B` plus a device name and unit, no CR (`BMY0`, `BMX0`)
- **The КЦГД is a terminal, not a framebuffer**: its own КМ1801ВМ2 (7.7 MHz, firmware 181 at 100000, start and console vectors from 100000), own MS7004 and a serial line to the ДВК (two ВП1-065 on the board; the netlist shows only transceivers and address jumpers on the host bus). So it replaces the КСМ and the machine still has one display - no second screen was needed. `kcgd` holds the 17-bit 64K-word video memory (lower 16K words are the КЦГД CPU's RAM at 0, the rest through 160000/160002) and the ВП1-033 registers 167770-167777; the mapper gives it absolute addresses with `kcgd[160000]`. The scan is not invented: `kcgd` runs the counters and the three К556РТ4 dumps (`kcgd_d61..63.bin`; D33 cell of 16 x 30.8 MHz, 123 cells a line, 265 lines a field, 59.06 Hz, bit 0 of a dump nibble is pin 12) once at load (`build_scan()`) and plays the field back as a table of EVNT/REQB changes; the display only follows its field counter. The ВМ2 divides CLC by two (f1/f2, `vm2/hdl/org`), CLCO = ~f1 reloads D33, which locks the cell to the processor's phase. The dump never drives V9 (EVNT by the netlist) low, so `evnt_bit = 2` takes the frame sync V8 until that is cleared up. `kcgd-display` lays the frame out from the line-address table (word 015574/2, entries read from the end, each shown twice without interlace), 8x2-bit or 4x4-bit pixels by bit 16. The palette register is 6 bits, 2 per DAC output U55/U56/U57 (netlist: D73/D74 -> D72 -> 2-bit resistor DACs); U55 is red, U56 green, U57 blue (confirmed by the replica's author; `rgb` keeps the order configurable), so the firmware's default text value 017 is yellow. A character cell is 10 px (4 chars in 5 words); `display.text` matches glyphs against the 181 font through its KOI-7 tables (the font is not in code order). ROM 182 stores its font elsewhere, `text` does not work with it. The KeyGP ROM (RR1-183/184, graphics commands `ESC M <cmd> <args>`) sits at 120000-157777 with firmware 182: one `kcgd-rom` of 24 KB over 100000-157777 with `partial = 1` (`kcgd182-keygp.rom` is 182+183+184 back to back; the 8 KB variants leave the rest empty, and the range is `routed = 1` so an empty socket does not answer - KC.SAV with 181 counts an answer at 120000 as its error 13). Firmware 182 which jumps to 120000 at start-up (vector 4 brings it back when nothing answers) and lets KeyGP patch its RAM hooks; the command table then sits in КЦГД RAM at 045336 + 2 x code (`work-dvk4-kcgd-gp`, on `tests/files/dvk4-keygp.ext`). KeyGP checks for 182 (114142 at 100000), so it does nothing with 181. **KeyGP keeps a clock in КЦГД RAM 040146/040150**, advanced by its interrupt B handler (122116, vector 304, every REQB): a program that firmware 182 loads with `ESC X` at 040000 gets that word changed while it is being received - BABY's loader lost its `SOB` and restarted the КЦГД. That is the ROM, not the emulator: such games need firmware 182 or 181 (`ESC X` loads code into the КЦГД and runs it; BABY sends a 210-byte loader to 040000, which takes the game at 020000-053677 straight from 176562) Firmware 182 starts in VT52 mode (`ESC <` switches to ANSI), and `ESC M` graphics work in VT52 only - in ANSI `ESC M` is reverse index. `'` takes one point (x as two 6-bit chars + 040, y as one, origin bottom left) and draws a rectangle from the current point. The language is undocumented here; `docs-external/DVK/circle.sav` (a game written for it) also has a string loop bug at 004164 (`MOV (R1),R2` without autoincrement) The mouse (`kcgd-mouse`) is two 3-bit up/down counters read in 167774 bits 8-11 (netlist: К555ИЕ7 D84/D14, mux D15 onto AD08-11, axis by control bit 2) - no firmware reads it, programs downloaded into the КЦГД do. The factory test `KC.SAV` (FODOS test disk, `work-dvk4-kcgd-factory`) pinned the rest: palette registers are 8 bits and readable at 167773 by index; REQB is bit Q12 of the scan line counter (toggles every 16 lines of 64 us, ~1 ms; 26 lines across the field reload to 061); REQA is the latched bit 16 of the last 160002 read XOR control bit 6 at the moment 167770 is read; interrupt A/B requests come on the rising edge of "enabled and raised", including enabling an already raised one; the КЦГД CPU's RAM is the video DRAM the raster shares: `kcgd` is the `WaitSource` of its own memory (one processor window every 3 character cells, RPLY at the end of the next cell - D61, D70, D30, D19), which `timing = vm2` asks for every cycle (and `legacy` instead of `reply_delay`); with it and the ВМ2 table KC.SAV's REQB wait loop runs 132 clocks, as the chip does, and the test passes without any tuned delay; the MS7004 must answer $FD with $01,0,0,0. Every device of class `mouse` is a `HostMouse` (`move()`, `mouse_plugged()`), which is what `Emulator::mice` holds; the БК «Марсианка» `Mouse` is one of them
- **The `*_mc1201.rom` dumps** (031, 054, 279 in `docs-external/DVK/`) are stored with the words in reverse order and inverted data, plus 2 trailing bytes; `deploy/computers/dvk/files/*.rom` hold them decoded (279 matches forth32's copy except their B RK patch).

## Floppy formats (HFE, Агат 140 KB)

- **HFE** (`.hfe`, HxC Floppy Emulator v1, what Gotek/FlashFloppy reads) is the bit-cell form of the same tracks for `mfm_ibm`, `fm_ibm` and `fm_dvk_mx`: `FDD::load_hfe`/`save_hfe`, with the container and the cell codecs in the `dsk_tools` core (`src/libs/dsk_tools/src/hfe.cpp`: `hfe_read`/`hfe_write`, `mfm_encode`/`decode`, `fm_encode`/`decode`; a flag per byte marks a sync byte without its clock - MFM A1 = 4489, FM FE/FB/F8 with clock C7, FC with D7). Decoding takes the byte grid anew at every mark, so a track not written from a byte boundary reads too. MFM decoding looks for 4489 only: the C2 sync 5224 also turns up, shifted, inside a 4E gap and broke the grid. MX words go high byte first (not checked against a real MX drive). `fdd.checksum` (a hash of the tracks and marks) shows a round trip is exact; `work-dvk2-dx-deleted`, `slow-dvk3-testmx` and `slow-dvk3-testmy` do one through `.hfe`, and a BK `.hfe` was checked once with an independent sector reader (all 1600 CRCs). The rate, rpm and encoding come from the library (`TrackLayout` of the drive mode, `track_hfe_params`, `track_bytes` - 3125 bytes a turn for MX, while the drive keeps 1562 whole words), and the header's write-allowed flag becomes `write_protect` on load and is written from it. The library's IBM sector reader (`ibm_track_fields`) skips what lies between fields - a write splice, junk after a rewritten sector - instead of giving up on the track; `fdd.deleted` counts through it (TESTMY leaves 128 deleted sectors, the old reader saw 110) The Агат 840 has `.hfe` too (`agat_840_to_cells`/`agat_840_from_cells` in `mfm_tools`): its MFM table is plain MFM (checked byte for byte against `encode_agat_MFM_byte`), the sync is A4 with the clock of its last bit dropped (cells 4490h, `dsk_tools` writes them as bytes 22 09), and the drive's DESYNC mark sits on the FF after it, as in the AIM dumps; the track keeps the file's length (6464 bytes from `dsk_tools`, 6381 from a .dsk). A `.hfe` of `fddconv` and one of eCat3 convert into each other and back to the same .dsk (`work-agat-9-hfe`); `dsk_tools` writes Агат images with write not allowed, so they open protected. The 140 KB GCR disk (`mfm_agat_140`) has `.hfe` too, with `gcr_encode()`/`gcr_decode()` of the `dsk_tools` core (`agat_140_to_cells()`/`agat_140_fit_track()` in `mfm_tools`): the drive keeps the bytes the controller reads, so each goes out as its 8 bits, top bit first, and every FF with two 0 bits more - the 10-bit sync bytes of the gaps, which the latch drops, so an FF inside a data field reads the same; a disk bit is two cells, a 1 a transition in the second. The header is the one `fddconv` writes for 140 KB disks: one side, 250 kbit/s, 300 rpm, encoding FF, interface 7, double step. Loading takes one side of 35 to 40 tracks whose header says Apple II GCR or no encoding (side 0 of two); `gcr_decode()` gives each track's nibbles of one turn as the latch reads them, counting bits by a clock where the transitions leave their cells (the HxC software puts them in the first cell of a pair, write splices and flux captures shift them), and every track then gets the length of the longest, the missing bytes going into its longest run of FF, a gap. A round trip keeps `fdd.checksum` (`work-agat-7-140-hfe`), and the `.hfe` of the IKP disk decodes to `IKP7_140.dsk` in `fddconv` too; 11 of the 13 GCR `.hfe` of an Agat collection (from the HxC software, Greaseweazle and FlashFloppy) save as the same .dsk as an independent converter makes of them, and the other two load but hold tracks `decode_agat_140_image()` refuses (unreadable sectors; address epilogues DE AA FF), so they don't save as .dsk. The track layouts themselves (IBM MFM, IBM 3740 FM, MX) are in the `dsk_tools` core too (`src/track_formats.cpp`; `mfm_tools` only wraps them), and the full library's `LoaderHXC_HFE`/`WriterHxCHFE` use the same functions for the `TYPE_RT11:*` disks, so an `.hfe` written by `fddconv` reads here with the same `checksum` as the flat image, and the other way round
- **The 140 KB drive takes 35 to 40 tracks and both sector orders.** `generate_mfm_agat_140()` counts the tracks of a sector image from its size (a tail shorter than a sector, as the 128-byte Agat label, is left out), `load_image()` those of a `.nib` or `.nic` from the file's, and `decode_agat_140_image()` of `dsk_tools` saves as many as the drive has; the controller steps the head up to track 39 (half-track 78). A `.po` keeps its sectors in ProDOS order, `.dsk` and `.do` in DOS 3.3 order, and a `.dsk` whose block 2 in ProDOS order starts as the key block of a ProDOS volume directory is read as a `.po` (`agat_140_prodos_order()`, `agat_140_dos_to_prodos()` in `mfm_tools`), the rule of FlashFloppy's Apple2 mode. `disk-agat-7-140-order` and `disk-agat-7-140-forty` check both through `fdd.checksum`

## БК, СМК-512, К1801ВМ1 start and console

- **The К1801ВМ1 starts from its 177716** (+ 020 per processor number, `cpu_number`): PC = the high byte, PSW = 340, after ACLO is released - the description's start microcode. `start_address` means nothing to it; every machine already answers there (БК 100000/140000, СМК/А16М ROM, ДВК-1/2 jumpers 160000, КМД 010000), the test rigs got a read-only `port`
- **nIRQ1 of the К1801ВМ1 is a level** (description: "вход чувствителен к уровню"), masked only by PSW bits 10/11. A held СТОП straight on it re-enters on every instruction, and on a plain БК every entry is a trap through 004 with a push: 100 ms of the key ran the stack through all of memory. The real board makes a pulse instead (`docs-external/BK/BK0010_01.JPG`): contact ОСТ1 is the node of R5 180k from +5 V and C2 68n, ОСТ2 goes through VD1 to R1 75 Ω and inverter D1.1, then synchroniser D11 to nIRQ1 - pressing the key discharges C2 into R1, about 6 µs above the threshold, and a held key gives nothing more until C2 recharges (~12 ms, not modelled). The БК configs build it from a triggered `generator` (`stop-pulse`, `length` 18 clocks at 3 MHz, 24 at 4 MHz), and the core latches the IRQ1 request flag so a pulse shorter than an instruction is not lost (taken when PSW 10/11 allow, raised again while the line stays low)
- **The К1801ВМ1 console mode is external, and the БК's vector 4 on СТОП/HALT is a consequence of it**: entry is RMW 177716 |= 010, PSW to 177676, PC to 177674, new PC/PSW from 160002 (`pdp11core::vm1_console_entry`); START/STEP read them back. On a plain БК nothing answers 177676, the bus timeout becomes the ordinary trap through 4 - `halt_vector`/`halt_sel` do not apply to `1801vm1`. A timeout inside such an entry counts in `cpu.timeouts` (the БК0010 monitor executes a HALT at 120000 on start-up). PSW bits 10/11 come only from a console vector: RTI/RTT clear them (and drop `halt_mode`: a console handler may leave that way instead of START), MTPS keeps them, and while set a timeout goes to 160002 and nIRQ1 waits. `work-bk-smk-halt` is the test, with the СМК-512 Hlt modes providing the console memory
- **The БК 2xAY board is its own entry of the sound socket**, beside the single `ay`: `ts-ay1` (`chip = 1`, `title = 2xAY TurboSound`) and `ts-ay2` (`chip = 2`, `pair = ts-ay1`) sit on 177714 with `through = 1`, and each decodes the select word itself - TurboSound 0377/0376, GryphonSound bits 15/14, the protocol of the bk-catalog emulator. Not folded into `ay`: a word select with a zero high byte (after the port inversion both Gryphon bits) would send a single-AY program to both chips. `ts-ay2` joins the mix only once written. It is last in `devices = ay|covox|ts-ay1` so the indices saved in `[DeviceOptions]` do not shift. A device's `title` overrides its `plug_title()` in any `connector`, so a board name never goes into device code. `work-bk-ay-turbosound` is the test
- **The СМК-512 BIOS maps drive numbers differently from the КНГМД**: 0-1 are the floppies, 2 and up the logical disks of the hard disk, while the КНГМД driver folds the drive number to 0-3. A program asking for a drive the СМК does not have gets BIOS error 13 (in cell 052) after the ~10 s wait for an empty IDE channel - `andos330.img` used to keep its shell's right panel on E: for exactly this reason, see `disk-bk0011m-smk-shell`. The BIOS keeps its partition table copy and variables in board RAM segment 7 (176000-176777, 176770 = number of logical disks)
- **Hard disk images of the БК are stored as on the drive, so the CPU sees them inverted**: search an image for text only after inverting its bytes. A `*.hdi` starts with a 512-byte IDENTIFY header before sector 0 (`UKNCHDD::m_data_offset`); without it every sector reads one off and the BIOS finds no partition table
- **The БК0011М frame interrupt comes at the end of the horizontal sync pulse of the first service line** (`HSYNC(line, 2)` of `RasterDisplay`, 8 3/8 words into the line, line 257 of the model), not with the vertical sync pulse of the 037 (SYNC2, service lines 21-23) as it used to. The evidence is the demo Babylona: its palette program (256 blocks of six `MOV Rx,(R0)` 32 clocks apart, after a delay loop timed on a real machine) fits its reference picture to the byte with the block for line y+1 drawn on line y and the first write at byte -4; with the interrupt at the vertical sync it was 20 lines low. The MiSTer core has the same point (irq at vc 256, hc 649). With this and the mid-instruction write below the demo matches its reference at 97% (72% before); 3 bytes (~8 clocks) are left, the picture coming that much earlier on the reference. `work-bk-0011m-raster` and `-precise` count 20 lines longer for it
- **The high precision mode of `bk-display` lays a line out a byte at a time as the beam passes** (`BKDisplay::BEAM()`, `beam_draw()`, `beam_commit()`): a line is 48 words of the video clock, 16 of blanking and then 32 of the picture: by `va_037.v` of the reconstruction (github 1801BM1/k1801, 037/rtl) `TV51` at the last picture word steps the line counter, so a line of the model has its picture in the last two thirds, and the beam is past `clocks * line_bytes * 3 / (2 * line_length()) - line_bytes / 2` bytes of it. The line mode samples at 21 us, the start of that picture. The bytes go into `m_beam_buf` and onto the surface whole at the next line start (one surface lock a line, as without the mode); `HSYNC(line, 1)` then draws nothing. The registers are read once a call, that is once a processor instruction, and a register that changed takes effect from the middle of the instruction: the devices are clocked after `execute()`, and the vm1 timing knows when a cycle happened only in `finish()`; MOV R,(R) strobes its write 15.5 clocks into its 32 on the chip model. Taking it from the instruction's start put Babylona's palette 6 bytes early. Off, it costs one flag test in `RasterDisplay::clock()`; on, ~9% on a БК0011М running `BR .` at max speed. `work-bk-0011m-precise` is the test: the handler of `work-bk-0011m-raster` six SOB turns longer puts the palette change at dot 76 of line 171. The demo Babylona (`docs-external/BK/sands-and-bomb-babylona`; a plain БК .bin with 002000 in its header: load it there and start at 002000, or from tape by the monitor, `L` and `2000G`) is the check against a real machine

## Агат

- **The 625/50 raster (both Агат) is exactly 1/25 s**: 625 lines, 313 in the first field and 312 in the second (it counted 626, a frame 64 us long - the first visible line of no display depends on line 625: 512 lines are 102..613 on the Агат-7, 38..549 on the Агат-9), and a frame of `2 * clock / 50` clocks with the remainder spread over the lines (`m_line_rem`, `m_rem_acc`: at 1.021 MHz the Агат-9 line is 65.34 clocks, 65 and 66 in turn; it was 65, 50.26 Hz). The Агат draws the 256-line mode in both fields, as the machine shows it, so the picture changes 50 times a second; the regression suite passed unchanged after all three
- **An ВВ55 mode word resets the output registers**: a control word with bit 7 set clears ports A, B and C and drives the output ones to 0 (8255A datasheet, "Mode Definition Format"); a bit set/reset word (bit 7 clear) does not. It is the only thing the Агат-840 boot ROM does to put the controller into a known state, so without it a warm restart out of a program that left drive B selected steps forever waiting for a track 00 that drive cannot report. Школьница's «Конец работы» is exactly that case; `work-agat-9-restart` is the test
- **The Агат ЯЗС (`agat-yazs`) has the schematic's topology but not its values**: the drums, the envelope former and the drum/tone balance are fitted to recordings of two real cards - `docs-external/Agat/sound/YAZS_Test.wav` (SOUNDTEST automatic mode, `soundtest.DSK`) and the NCL demo (agatcomp.ru `SoundNCL/SoftNCL/DemoNCL/`, the song of `music-d.dsk`); the schematic's values stay in comments. By the schematic drum 7 buzzed at 100 Hz where the card hisses at 6-13 kHz. The SOUNDTEST card is faulty: D0 of drum 6 does nothing there, while the demo relies on it - do not fit drum 6 to that recording again. The emulator records sound in real time only (4 min for SOUNDTEST); fit on a bench that compiles a copy of `agat_yazs.cpp` (constants as variables) against the headless objects and replays the test's register writes. `tones`, `drum6`, `drum7` (percent) scale each source's share of the mix

## УК-НЦ

- **An interrupt request that is a one-shot event must be cleared by the acknowledge, not by the level**: a 1801 processor reports taking a vectored interrupt on `~iako` (the vector, for an instant). The УК-НЦ channels latch a request on the transition to ready and drop it there. Computed as "ready and enabled", the free transmitter of channel 0 was offered again after every other interrupt, and its ROM handler (175540) steals a character from the keyboard buffer when the ЗАГРУЗКА menu is waiting for input - the menu got the arrow code without its ESC and ignored it. The regression is `work-uknc-menu`
- **The УК-НЦ video controller's registers are loaded by the frame pulse** (`UKNCDisplay::reset_walk()`, from the reverse engineered ХМ1-136 in `docs-external/UKNC/BMK_texts`): the list from 0270, two-word, cursor off, and also the palette 0x76543210 (colour n = YRGB n), the cursor word 0x0008 and scale 1; the brightness bits stay. A table that sets its colours lower down shows these above that line. `boot-uknc-display-frame` is the test. The same texts give the ПП interrupt order of ХМ2-001 - 310 (timer event), 304 (timer zero), 300 (keyboard), then the channels: in `UKNC.cfg` the timer is nearest the processor, and `work-uknc-virq-order` points the vectors at loops of its own to see which one is taken. They describe ХМ1-032/003/136 and ХМ2-001, not the 031 of the литера 7 the timing measurements come from; a memory model built from their timing diagrams fits TSSPD worse (1.6 / 1.7 clocks) than the fitted one (0.53 / 0.97)

## Орион, Радио-86РК, Апогей, Микроша: РУС/ЛАТ

- **A tape write can leave the emulated keyboard in the other alphabet** (known bug, Орион-128): `scan-keyboard`
  takes its Rus/Lat register from `~ruslat_led`, and the Орион monitor writes the whole of port C - data bits
  included - while saving to tape, so the indicator line ends up data dependent while the monitor's own flag
  (`$F3E5`) does not move. `RUS_REMAP` then presses the key from the other half of the layout: `I` arrives as
  `$5B` and the monitor answers `?`, which looks exactly like a tape read failure. `LOG keyboard.rus` against
  the machine's own flag separates them; two presses of РУС/ЛАТ resynchronise. Радио-86РК, Апогей and
  Микроша are immune - their ROM re-asserts the indicator from its own variable on every keyboard poll. Left
  as is on purpose: the indicator is the only signal of the register, and the remap is what lets a ЙЦУКЕН
  host keyboard drive a ЯВЕРТЬ machine
- **The indicator line is taken into the register at a scan write, never the moment it moves**: the
  Радио-86РК and Апогей ROMs zero the whole of port C on every keyboard poll and set PC3 back from their flag
  a few instructions later (Апогей `$FE7F-$FE89`). Following `~ruslat_led` instantly made the drawing's РУС
  lamp flicker and could remap a host key typed inside that 20 us dip. `ScanKeyboard::interface_callback()`
  latches the line and applies a change of it on the next write to the scan lines, which the ROM does before
  the dip and after the restore
- **РУС/ЛАТ flips on the press, never on the release**: `ScanKeyboard::key_down()` toggles `rus_mode`, `key_up()` only releases the line. Toggling on both edges cancels itself out and leaves the register wherever the indicator line (`~ruslat_led`) happened to point - which the Орион configs used to paper over with an inverted `~ruslat_led`. All three now wire it straight, like РК86 and Микроша, and the register follows the monitor's own flag ($F3E5)

## ВГ75 (Радио-86РК family)

- **`I8275::clock()` must jump between events, not step per character clock**: it is driven at the character clock (1.33 MHz on a Радио-86РК, and the loop body is entered ~7 times per emulated instruction), so stepping one tick at a time costs a quarter of the whole emulator. Only two things happen inside a character row — the next DMA transfer and the end of the row — so the beam advances straight to the nearer of them; `m_dma_delay` is the full period until the next transfer, counted down by `clock()`, and `dma_tick()` is called only when one is due. Getting that period off by one silently changes the burst pacing and every reference screenshot with it.
- **The ВГ75 frame is drawn from a snapshot, never from live registers**: `I8275` runs on the emulation thread and may be reprogrammed at any moment, so `I8275Display` copies the row bytes plus the geometry, font bank, cursor and blink phase when the row is fetched, and the render thread lays the frame out from that alone. Reading `chars_per_row()` / `char_height()` while drawing means one row drawn with the width of one raster and the height of another.

## Ириша

- **A machine may carry several disk controllers of different types**: `Irisha-kngmd.cfg` has `fdc : wd1793` (5.25", drives A:/B:) and `fdc2 : gmd70` at ports 50-51 (8", drives E:/F:). Nothing is special-cased by name: the GUI finds drives by class `fdd`, the scripts by device name (`fdd2.track`). Only `cpu`, `mapper`, `display` and `keyboard` are reserved names (and `bios` and `mapper` in the loaders of `files.cpp`). A controller takes its drives with `FDC::load_drives(min, max, list)` (defined in `fdd.cpp`), which checks the count against the controller's selects and that each name is an `fdd`: the five controllers used to parse `drives` each on their own, and only one of them checked anything.
