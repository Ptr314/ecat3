# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**eCat3** is a universal emulator for retro computers (Orion-128, Radio-86RK, Agat-7, Agat-9, Apogey, Mikrosha, Irisha, and the 16-bit БК0010 / БК0010-01 / БК0011М, the latter two also with the СМК-512 board and the А16М floppy controller, the ДВК-1 / ДВК-2 / ДВК-3 / ДВК-4, and the IBM PC clone Поиск-1) written in C++. The emulator core (`src/emulator/`) is **Qt-free** — it uses only the C++ standard library, making it portable to WebAssembly and other non-Qt targets. The Qt framework is used only for the desktop GUI layer (`src/mainwindow.*`, `src/dialogs/`, `src/renderers/`). The project targets Windows 7+, macOS, and Linux with support for multiple rendering backends (Qt, SDL2, OpenGL).

## Key Architecture

### Modular Device-Based Architecture

The emulator uses a device-based architecture where computers are built from interconnected components:

- **CPU Layer** (`emulator/devices/cpu/`): i8080, Z80, 6502, 65C02, К1801ВМ1 (PDP-11), 8088/8086 - independent instruction execution engines
- **Memory Mapper** (`emulator/devices/common/page_mapper.h`): Central address-space manager that routes memory access to correct devices
- **Device Types**:
  - **Common Devices** (`emulator/devices/common/`): Generic peripherals (RAM, ROM, i8255, i8253, WD1793 and GMD70 disk controllers, etc.)
  - **Machine-Specific Devices** (`emulator/devices/specific/`): Agat/Orion/Irisha/БК display controllers, БК timer, FDC variants
- **Interface System**: Devices connect via interfaces (analogous to real hardware buses). Interfaces support bit-range connections and inversion.

### Configuration-Driven System Design

Computer configurations live in **`.cfg` files** (text format, see docs/CONFIG.md for syntax). During startup:
1. Config parser reads device definitions and their parameter values
2. Devices are instantiated and registered in device list
3. Interface connections are established
4. System runs with defined architecture

This means most hardware behavior is **not hardcoded** - it's defined via config files. New machines can be added by creating `.cfg` files without code changes.

**Configuration extensions (`.ext`, `.ext.zip`)** are variants written as edits to a base `.cfg` (`@extends`, `@version`, `dev:prop = value`, `-dev:key [= value]`, `name : type { ... }`, `@before`, `@script`); `docs/CONFIG.md` has the rules. Every machine file goes through one function, `load_machine_description()` (`emulator/config_ext.h`): a `.cfg` as is, an extension parsed by `ConfigExtension` and applied to the parsed `EmulatorConfig` before any device exists, a `.ext.zip` unpacked into `Emulator::cache_path` first. Both formats share the tokenizer (`ConfigReader`) and `parse_parameter()` in `config.cpp`, so a value means the same thing in either. Things to know:
- `@protected` marks a shipped variant: the chooser's Edit and Delete are greyed out for it (`MachineSource::is_protected`, `Qt::UserRole + 3` of the item), Copy is not, and the copy drops the flag. **A Copy of an extension is a new extension standing on it** (`ExtEditModel::open(path, paths, derive)`, `@extends <the copied .ext>`, no edits of its own), not its edits repeated on the bottom `.cfg`: the web page fetches the bundle of the machine `@extends` names, and the plain base's lacks the variant's files (ЯЗС: "File not found flop140.boot.v2.bin"). `--selftest` (`check_ext_editor_copy`) checks it.
- **A device block** (`name : type { ... }`, as in a `.cfg`) adds a device: `ExtEdit::AddDevice`, read by `parse_device_parameters()` - the same code as `load_from_text()`, on the extension's text padded with a line break. A line is a block when a lone word follows the colon and a brace follows it on the same line; every `device:property` line has `=` before any brace. A name the base already has is an error. **`@before`** places the run of edits after it, each in front of the same place so the run keeps its order: `@before dev` for new devices (the order is the clocking and reset order), `@before dev:key [= value]` for range lines of that same device. The first edit of another kind ends the run; an `@before` that placed nothing is an error, and so is a placed line the base already has - a change of options to an existing line written right after a run would otherwise be swallowed by it and moved (that happened while converting `BK-0011M-smk512`: write such a change before the `@before`). A new line written after a run joins it as well, with no error to say so - `Agat-9-pp` put its last range in front of `boot840` that way until `--print-config` showed it. Lines the extension itself added above are not the base's, so one range can go to one device twice (read and write, `Orion-128-m3`). Another part of an interface wired in parts (`~config[3]` beside `~config[0-1]`) is added, not refused as "other modifiers". `ExtEditModel::build()` writes a field of an added device into its block, since it has no base to differ from. `eCat3-headless --selftest` checks the order, the round trip through `serialize()` and the editor; `tests/scripts/ext-add-device.ext` checks a placed range on a running machine
- **An extension may stand on an extension**: `@extends` names a `.cfg` or a plain `.ext` (not `.ext.zip`, not a state), and `load_extension_chain()` builds the chain from the `.cfg` at the bottom, refusing a loop. `MachineSource::base_cfg` is that bottom `.cfg`; the files of an extension in the middle of a chain are found only if they lie by the base or the file opened (`ext_path` is one directory). **`cfg_or_ext()`**: a machine file named `X.cfg` that is missing while `X.ext` exists means `X.ext` - in `@extends`, `MACHINE`, the command line, the ini default - which is what let the variants become extensions of their bases - БК (`BK-0011M-fdd`, `-smk512`, `-mstd` on `BK-0011M.cfg`; `BK-0010-01-fdd`, `-smk512` on `BK-0010-01.cfg`), Агат (`Agat-7-840-pp`, `Agat-7-max` on `Agat-7-840.cfg`, `Agat-9-pp` on `Agat-9.cfg`), Орион (`Orion-128-m3` on `-m1`, `-tZ80` and `-Z80-zexall` on `-Z80`), `Spektr001` on `Radio-86rk.cfg` - without breaking the extensions, recordings and `?load=` links written against their old names (`tests/files/ext-bk-fdd-empty.ext` still says `@extends bk/BK-0011M-fdd.cfg` on purpose). The page does the same in `startMachineFile()`; `package_machines.py` skips an extension built on another one (the bundle would need the chain). The editor compares against `load_extension_base()`. A `.cfg` rewritten as an extension is checked with `eCat3-headless --print-config <file>` before and after: devices in the same order, and inside a device the same lines once sorted stably by name (a changed plain property moves to the end of its device, lines of one name keep their order)
- `-device` (no colon) removes a whole device before any exists. Nothing follows its references: the mapper ranges, links and `mix` entries naming it must be removed by the same extension, or the load stops at the first one (`UKNC-basic.ext` drops the hard disk and the sound module this way - they live in `ppu-mapper`, not `mapper`).
- A key (`name + left_range`) is **not unique** in a base: the БК mapper sends `@memory[177714-177715]` to three devices and `port-ppi` takes `~data[0-7]` from two. A removal picks one by value (`-mapper:@memory[177714-177715] = ay`); replacing an ambiguous key is an error.
- `{base64: ...}` after a file name is decoded by `materialize_inline_data()` into `cache_path/inline/` and the parameter gets the absolute path, so no device loader knows about inline data. `find_file_location()` therefore takes absolute names as they are, and searches `SystemData::ext_path` (the extension's own directory) right after the script's.
- **The cache (`cache_path`: `ext/` unpacked archives, `inline/` base64 data) is cleaned by age** - `cache_cleanup()` (`emulator/cache.*`, plain system calls since the core is C++11) runs at start-up of the window and of the console build and removes what was not touched for 30 days; `unpack_archive()` and `materialize_inline_data()` `cache_touch()` what they reuse, since a reuse that finds the same bytes writes nothing. Not by "mine, now that I exit": a parallel test run loads one archive in several processes at once. **An archive is bounded before anything is written**: 1 GB unpacked (256 MB in the browser, where MEMFS is the tab's memory), 4096 files, 64 MB a file (`ZipReader::max_entry_size`). The sizes in the central directory can be trusted for the sum because `ZipReader::read()` refuses an entry whose data comes out of another size; `tests/files/ext-errors/archive-too-large.ext.zip` (made by `make_archive_limit.py`) claims 2 GB in a 435-byte file, and the runner reads the `// @error` of an `.ext.zip` from the `.ext` inside it
- `sd.system_file` is the file asked for (the `.ext`), which keys `[DeviceOptions]` and `MACHINE` of a recording; `sd.system_path` is the base's directory.
- The `@script` is started by the frontend (`has_embedded_script()` / `load_embedded_script()`), and only when nothing else drives the machine: an explicit `--script`, a replay and an MCP client win.
- `ConfigReader::next()` drops the last character of a text that ends without a line break. A `.cfg` always ends on `}`; the extension parser appends `\n` to each property it tokenizes.
- **The editor** (`dialogs/exteditorwindow.*`, opened from the machine chooser) shows what `ComputerDevice::get_config_fields()` returns. `collect_config_fields()` (`emulator/config_fields.h`) constructs the machine's devices through `register_all_devices()` on a private `DeviceManager` and never calls `load_config`, so `get_config_fields()` must read `cd` only, and a constructor must stay free of side effects (and leaks: the editor builds a machine every time it opens). `ExtEditModel` is the Qt-free part: base and current values per field, `build()` rewrites only the edits of known fields and keeps the rest and `@script`. A new editable parameter is one override in the device, no GUI change.
- **The web page can start an extension it downloads**: `index.html?load=<url>` (`startUrlMachine()` in `src/wasm/ecat_wasm.js`) fetches the file into `/tmp/load/` of MEMFS and loads it like any machine. The base `.cfg` and its ROMs live in the bundle of *their* machine, which the page fetches first, so it needs the base before the load: `wasm_machine_base()` answers with `machine_base_file()` (`config_ext.h`), which parses the extension alone and resolves `@extends` without loading anything. A base that is not a machine of the build, and a server that does not allow the download (the page is cross-origin isolated, so a cross-origin file needs CORS), are the two ways this fails; `wasm_last_error()` carries the core's message to the status line, since `wasm_load_machine()` returns only a code. The same path takes a machine file picked on the visitor's own computer: the "Open file" button hands the bytes to `startMachineFile()`, the half of `startUrlMachine()` that does not care where they came from. That button is shown for every machine, not only for one whose `system` section names `files` - without it a snapshot of the УК-НЦ, which names none, could be opened in the browser by a link and by nothing else. `setupOpenFile()` lives outside the closure that holds the machine list, so `startMachineFile` is a module-level holder that `initEcat()` fills.
- **A hard disk image picked on the page is not copied into MEMFS** (hundreds of MB would be the tab's memory): `HddImage::source_factory` (set by `wasm_main.cpp`) turns a name `/host/<id>/<file>` into an `HddSource`, and a plain worker of the page (`HOST_FILE_WORKER` in `ecat_wasm.js`) holds the `File` and reads what is asked with `FileReaderSync`, straight into the wasm memory, through a mailbox of 8 words in it (`HostFile`, 64 KB blocks cached). The asker waits with `emscripten_futex_wait` - the emulation thread, or the main thread when a controller reads the image while attaching it (spinning there is allowed); the worker needs nobody's event loop, so neither can deadlock. A WORKERFS mount would not do: with pthreads the FS calls are proxied to the main thread, where `FileReaderSync` does not exist. Such an image is never written: `HddImage` keeps the writes in memory, and Save (`wasm_hdd_save`, `HddImage::contents()`) hands out the image with them. The mailbox is freed only after the worker has answered its stop, or it would read reused memory as a request. Controllers expose the image through `HddImageOwner`
- Tests: `tests/scripts/*.ext` run as their own script, `tests/files/ext-errors/*.ext` must fail to load with the `// @error` text on stderr (headless only, see `tests/README.md`).

### Saved state (`.ecats`, `.ecats.zip`)

A snapshot of a running machine, accurate enough that the guest cannot tell it was restarted. Written by `SAVESTATE` (script) or File > Save state, opened like any other machine file — `is_machine_file()` accepts it, so every frontend including `index.html?load=` works with no code of its own. `docs/CONFIG.md` has the format.

**It is self-contained.** The file carries the machine's *resolved* configuration (`@config`, written by `serialize_config()`), and the archive carries every file that configuration names — ROMs, key tables, the keyboard drawing, the charmap — plus the media. So a snapshot does not break when a ROM or an image elsewhere changes. `docs/CONFIG.md` describes the two forms: `.ecats.zip`, and a bare `.ecats` with a `<stem>.files/` directory beside it, whose member names carry that prefix so both resolve through `MachineSource::ext_path`.

- **Both sections are `.cfg` syntax**, read by `EmulatorConfig::load_from_text()` — the tokenizer, ranges, `{extended}` blocks and comments come for free. A large buffer is `key = {hex: ...}`, an addressed dump where `*` means "the line above repeats to the next stated address", so untouched RAM is three lines.
- **`StateWriter::num()` always writes a base prefix**, decimal included (`_123`), unlike `format_number()`. A state of a decimal-radix machine would otherwise read differently from one of a БК.
- **A line is `~name = <value> {old = …, edge = …, mode = …}`**, and `off` means `_FFFF`, "nobody is driving this". Written as a number it would either be an unreadable row of ones or, masked to the line width, something else entirely.
- **Save is on the emulation thread.** From a script it is synchronous inside `tick()` (between two instructions, so the same script saves the same state); from the GUI it is a request flag consumed at the top of `timer_proc()`, the `m_screenshot_requested` pattern.
- **Restore is inside `Emulator::run()`**, between `reset(true)` and the loop: everything is built, nothing has been clocked, and that thread owns all of it. Five passes — device options (a `connector` plugs whole devices, so it must be first), `load_state()` per device, then `state_restored()`, then `clock_counter` and the domain positions. Because it is in `run()`, no frontend needs a line for loading.
- **`ClockDomain::norm` is rebased on save** (`base = min(norm)`). Restored raw, the first `timer_proc()` finds every domain past its target and runs `norm -= target` on a `uint64_t`, which wraps and freezes the machine for good.
- **`CPU::reset_mode` must be cleared in `load_state()`**: a reset is deferred to the first `execute()`, which would throw the restored registers away.
- **A device's `load_state()` must not drive a line.** The base class restores the device's interfaces first (through `Interface::restore()`, which assigns without cascading); anything driven afterwards would reach devices that have not been restored yet. Work that needs every device restored goes in `state_restored()` — `MemoryMapper` invalidates its page cache there, `GenericSound` refreshes its mix, `GenericDisplay` marks the surface for a full repaint (the Орион and the Ириша paint on every write to video memory and would otherwise show the picture of the run that took the snapshot).
- **Whatever a device derived from a line, it must derive again in `state_restored()`.** `Interface::restore()` assigns without firing `interface_callback()`, so anything a device computed *from* an interface and cached keeps whatever the reset left in it. This is invisible to every field a script can read — the bug is in the cached copy, not in the line. `UKNCSound` cached "does my level move on its own" there (`m_self_volatile`, from the grid bits of 177716) and the mixer held a stale level after a restore: the tone came back coarse and aliased until the program next wrote the register. `tests/scripts/state-uknc-sound.ecat` and the `sound.moving` field are the guard.
- **Media are state, not configuration.** A device whose `state_owns_file()` claims a parameter (`fdd:image`, `uknc-hdd:image`, the tape) has it dropped from the `@config` it carries, and writes its live contents into the bundle instead — raw, not through `save_image()`, which converts by extension. A snapshot taken right after a sector was written holds it in the `BKFDC` track cache and the `FDD` buffer and nowhere on disk; `BKFDC::save_state()` calls `flush_all()` first for that reason. `tests/scripts/state-bk-0011m-disk.ecat` is the test.
- **Host-side input is never restored** — held keys, pending mouse motion. Nobody is holding anything when a snapshot is opened, and a key that came back down would stay down forever. The machine side (the code register, the ready trigger) is restored, so a program waiting for a keystroke sees what it saw. Debugger breakpoints and the step mode are left out too: a state that opens already stopped is not what "continue from here" means.
- **A missing key keeps what the reset gave**, an unknown key is ignored and collected in `Emulator::state_report()`. Diagnostics never reach stderr — any output there fails every regression test.
- **A `.ecats` cannot carry `@script`**: a file fetched from a link must not run anything.
- Tests: `tests/scripts/state-*.ecat` load a committed fixture from `tests/files/*.ecats.zip`, made by hand with the `tests/files/make-state-*.ecat` generators. The snapshot itself is *not* a byte-comparable artifact — the instruction a `WAIT` lands on is host-timing dependent — so the tests compare the screen and memory that come back.
- `eCat3-headless --selftest` checks the invariants this rests on: `serialize_config()` round-trips every `.cfg` of the installation, `ZipWriter` round-trips through `ZipReader`, and the hex dump round-trips with its folding.

### К1801ВМ1 bus timing (`timing = vm1`)

The БК machines time every bus cycle of the processor; the УК-НЦ keeps the old formulas (`timing = legacy`, `reply_delay`), and nothing of the new path runs for it - `k1801vm1::m_timing` is null. `tools/bk-timing/README.md` has how the numbers were obtained and how to rebuild them.

- **The microprogram fixes the gaps, the memory fixes the replies.** The next SYNC comes a fixed number of half clocks after the previous strobe was released, whatever the memory; the strobe is released 3 half clocks after RPLY. `vm1_timing_table.inc` holds these gaps for every form (operation x source x destination addressing, PC modes apart, interrupt entries), taken from a simulation of the reverse engineered chip. It is generated - edit `tools/bk-timing`, not the file.
- **A template runs from the release of the instruction's own opcode fetch to the prefetch of the next opcode**, which is its last step. The emulator does not perform that prefetch: `MemoryMapper::peek_read_device()` answers which memory it would reach, without side effects. The tail of a form (the microprogram still busy after the prefetch) is **added** to the prefetch release, not overlapped - a model that overlapped them made register instructions two windows long on the БК0011М instead of three.
- **Accesses are matched to steps by role, in order**: the instruction stream (opcode, index, `#n`, `@#a` - `pdp11core::m_stream`, set by `read_stream()`) and data separately; the chip and the emulator agree on the order within each, not on how they interleave. Whether a read and the following write of one address are one read-modify-write cycle is the template's call, not the address's: `MOV (R1),@0(R1)` reads its pointer from where it then writes, in two cycles.
- **A memory answers through a `bus-timing` device** its `bus_timing` parameter names; one per controller, and every device the processor can see answering must name it - on the БК0011М that includes the `page-mapper` windows, since `MemoryMapper::last_device` is the window, not the page behind it. The parameter is not called `bus`: `ay8910` already has one.
- **Time is absolute, in 1/12 of a clock** (so the 037 period is 48/64/96 ticks at 3/4/6 MHz), and the phase against the 037 is part of the saved state (`timing_now/start/release`). On the БК0011М the same instruction takes different times by phase, and the measured averages are fractional; a per-form average would lose exactly that.
- **Anything without a template** - an instruction that ended in a trap, JMP/JSR to a register, WAIT, RESET - keeps the legacy count and only moves the chain along (`Vm1BusTiming::idle()`), as does time without the bus (`hold()`, a processor held by `~dclo`).
- **The Verilog bench is exact on static memory only.** With the ВП1-037 it needs the flip-flop both БК put on the RPLY input (`RSYNC = 1` in `tools/bk-timing/tb_bk.v`), and even then it stays 1-3 windows fast on part of the forms at 3 and 4 MHz. That is why the `bus-timing` numbers are fitted to the measurements of real machines, not taken from the bench: they are a chain-model equivalent that includes the flip-flop, not a description of the chip.
- `tests/scripts/timing-bk0010.ecat` / `timing-bk0011m.ecat` run Manwe's speed tests (`tests/files/bk-timing`) and must show the numbers of the real machines; `eCat3-headless --selftest` checks the table and a few forms against the measurements.

### 8088/8086 bus timing and the Поиск-1

`i8086core` (`devices/cpu/i8086core.*`, Qt-free) is one core for both chips; they differ in the bus only (8088: 8-bit, 4-byte queue, a word is two cycles; 8086: 16-bit, 6 bytes). `tools/x86-tests/README.md` has the test runner and where it stands.

- **The bus is timed clock by clock, the inside of an instruction is not.** A bus cycle is T1-T4 plus wait states; the BIU prefetches into the queue whenever the bus is free and the queue has room, and is simulated lazily up to the moment the EU next needs the bus. The EU's own clocks are the Intel table numbers less 4 per transfer the table counts, and a jump subtracts 4 more for the refetch. No microcode: results match SingleStepTests in every case except the flags pushed on a divide error; clocks match about half the time.
- **A REP string instruction runs one iteration per `execute()`**, its decoded form kept in `i8086bus_state`; an interrupt between iterations returns to the prefix right before the opcode, so a second prefix is lost, as on the chip.
- **Wait states come from the memory, not from the address**: `AddressableDevice::wait_source`, set by `wait = <device>`, is a `WaitSource` the core asks after every memory cycle (through `mm->last_device`), with the cycle's T1 as an offset from the point the devices have been clocked to. The Поиск-1 board RAM names the display, a cartridge RAM names nothing and runs at full speed - which is what games relied on.
- **The 8259 hands the 8086 its vector on `~vector`**, a line of its own: `~data` is MODE_R and `change()` on it drives nothing. The CPU drives `~inta` low in `reset()` (after every `load_config`), or the first acknowledge is not an edge and the vector never comes.
- **The Поиск-1 follows MAME (`src/mame/pc/poisk1.cpp`) except for the video memory**: it is the top 32 KB of the board RAM (shared with the processor, hence the wait states), not a separate buffer - but seen by the processor only through the B8000 window (`poisk-vram`), never at its own address. The 1991 BIOS sizes the RAM by probing 16 KB blocks up to the first gap; with the top 32 KB mapped it reported them as free and DOS put COMMAND.COM into the screen. CGA ports and writes to B8000-BBFFF trap through NMI (`poisk-trap`), and the BIOS draws text itself. The floppy cartridge B504 is a КР1818ВГ93 at C0h-C3h plus `poisk-fdc-control` at C4h (drive/motor/side, MR on D6 - a Restore when it goes high, which the ROM waits for; a read of C4h runs the controller to DRQ/INTRQ; a write to C6h restarts the motor one-shot, bit 0 of C6h reads 1 once it has run out). The factory driver ROM waits ~0.25 s for the motor before every operation on A: (its "motor already on" test compares with the drive number, 0 for A:), which is why DOS boots in about a minute; `Poisk-1-fdd302.ext` carries the Moscow v3.02 ROM, which waits only after the one-shot ran out. The factory BIOS INT 16h decrements AH in place and returns it changed for an unknown function, so a program probing for the AT keyboard with `AX=11FFh` (Volkov Commander 4.99) decides it is there and then polls functions 10h/11h that do nothing - an incompatibility of the real BIOS, not of the emulator. `LOG cpu.history` lists the last 256 linear addresses on the 8088 too.
- **Two links between the same pair of interfaces with different bits are two links**: `Interface::connect()` used to treat any second link between two interfaces as the reverse half of the first and drop it, so `~ir[6] = pit.output[1]` after `~ir[0] = pit.output[0]` silently never reached the 8259 (the Поиск-1 keyboard is polled on IRQ6). The duplicate check now compares the bits too; the regression suite passed unchanged after the fix, so no earlier machine depended on the dropped links
- **A 20-bit address space needs `address_bits = _20` on the mapper**: the page table is sized from it, and an address above it takes the linear scan.
- **The cassette is the IBM PC one** (`encoding = ibmpc`, `tape_ibmpc.h`): a bit is one period of the square wave of PIT channel 2 (1184 counts for a 1, 592 for a 0), written to tape from `pit.output[2]` and read back on port 62h bit 4. The BIOS times the halves with channel 0, which is what found two faults of the shared `i8253`: a latch command kept only the low byte (the high byte read was stale), and a count written to a running mode 2/3 channel restarted it and flipped OUT, so every bit got a spurious edge (the write path rewrites channel 2 after each edge). Both are fixed for every machine; the regression suite passed unchanged. A `.cas` is the PCE format - the record's bytes with the leader as FFh and the sync bit as FEh. The BIOS writes records back to back with no pause, so the decoder recognises the next record by its leader: a run of 2080 ones (32 of the trailer + 2048), longer than any block of FFh bytes can give. A `.cas` that does not start with a leader is a bare file (digitised cassettes are often kept so, `TETRIS.CAS`): the loader wraps it into a header (A5h, the file name as is - the BIOS compares it byte for byte, capitals included) and a data record. The BIOS menu runs a loaded file on Enter only; any other key returns to the menu
- **A far transfer goes through `i8086core::far_jump()`**: the prefetch cycles the BIU began before the jump belong to the old CS and are run to the current clock before CS changes. Setting CS and then calling `flush()` ran them from the new segment - the wrong memory's wait states and a read at a bogus address. `reset()` drops the queue without running them at all
- **`wd1793` has one slot for a delayed register write**, and a 16-bit OUT of the 8088 writes two registers within one instruction, before the devices are clocked: `set_value()` applies a waiting write before it takes the slot, or the first of the two (a command, a sector number) was lost
- **The bits of an i8255 port half are numbered by their place in the whole port**: `~CH[4]` is PC4, `~CH[0]` names nothing and silently drives nothing - which is how the tape first never reached port 62h
- Tests: `boot-poisk*`, `work-poisk-*` (`work-poisk-tape*`: read, write + read back, bare file) and `state-poisk-tape` / `state-poisk-tape-write` / `state-poisk-disk` (a snapshot in the middle of a tape read and of a tape write - a restored recording must set the decoder up again; graphics plus a sector that lives only in the drive buffer). `Poisk-1-cart-ram.ext` stands on `Poisk-1.cfg` itself and repeats the 128 KB edits: an extension on another extension is not packed for the web

### ДВК (`deploy/computers/dvk`)

ДВК-1/2 are the МС1201.01 board (К1801ВМ1, monitor ПЗУ 000), ДВК-3 the МС1201.02 (КМ1801ВМ2, monitor 279 or 055, КСМ, КГД, MX, MY, DW), ДВК-4 the МС1201.04 (КМ1801ВМ3, monitor 134, КЦГД, MX, MY, DW). **Four shipped machines, one per model**: what was a separate variant is a switch or a test machine. A ROM that was a replaceable chip is a `rom` with `image_1`, `image_2`, ... - **The terminal КСМ is a second machine**, not a display controller: its own i8080 (`ksm-cpu`, own mapper and clock domain) runs the real firmware (ksm_04/05) with an 8259, two 8251 and an 8255; `ksm-display` only scans its video RAM. The КСМ firmware needs ~0.35 s after power-on before it takes characters from the line, while the ДВК monitor prints its first prompt at once. On the real machine the start is given by the power panel, modelled by `dvk-panel` (the author's Arduino replica `DVK_Control`): POWER GOOD after `power_good` (500 ms), АИП (`~dclo`) 13 ms later, АСП (`~aclo`) 10 ms after that. Without it the first prompt was lost. Do not put such a delay into the processor. Its two switches are device options (toolbar drop-downs, `COMMAND panel.option(id,v)`): «Пульт» drives ОСТ (`~halt`, a level - the CPU cannot leave the console while it is on) and «Прерывания» the 50 Hz ПРТ square wave, which is the line clock everywhere: `~irq2 = !panel.prt` on ВМ1/ВМ2, and on the МС1201.04 `dvk-lks` with `frequency = 0` counts its rising edges, as the real board takes ПРТ from the bus (netlist: XS1 BA14 -> D7 -> VM3 EVNT); only the FPGA replica has its own 50 Hz. The 055 monitor's `P` is STEP, not proceed: restart with `addrG` `k1801vm1` starts only when both lines are released: ACLO released after DCLO is the power-up, not the interrupt through 024. The tests still press ВК first

- **`ms7004` sends LK201 key codes as they are**; the КСМ firmware turns a code into a character through its table at 0AFD + ~code (the `CMA` there belongs to the table index, not to the line). The МС7004 is ЙЦУКЕН with Latin letters on the same keys (J on the Q key); the host map gives Latin letters to keys with the same Latin label, `use_remap = 0`.
- **The КСМ firmware takes AE (ВР) and AF (СУ) as "down" only, and B3 (all up) clears СУ first and ВР only when СУ is already clear** (0587). So releasing one modifier while the other is held is sent by `ms7004` as B3, B3 and the code of the one still held; a single B3 left ВР latched after Windows' Ctrl+Shift layout switch, and the monitor got lower-case letters it ignores. `work-dvk3-ctrl-shift` reads the firmware's flags (КСМ RAM 20B3/20B4)

Running the КЦГД in the console broke the RTI trace (no trace trap in the console). On ВМ2 (and ВМ3) a T bit set by RTI traps right after it and RTT after one instruction, and a trap instruction (BPT/IOT/EMT/TRAP) is not followed by a trace trap; ВМ1 keeps its old extra delay after RTT (unverified). The ВМ2 PSW is the low byte only (`execute()` masks it; a word loaded whole carried bit 11 into the FIS trap frame), and a bus timeout in the console goes through `halt_sel | 004` with nothing saved - the console program runs on the interrupted program's stack, which the console space may not have. The FODOS factory test disk (`deploy/software/dvk/FODOSTMO.DSK`, test monitor FTMON, chains `VM2MY.CCC` / `VM3.CCC`; `slow-dvk3-fodos-vm2`, `slow-dvk4-fodos-vm3`) found these. FTMON rewrites the vector area with interrupts enabled, so the panel's «Прерывания» switch must be off for it, or a clock tick through the half-written vector 100 halts the machine. `TSKGD1` (КГД), `012101` (КСМ characters) and `TESTMY` (MY: formatting, functional test) pass
- **The MY controller is the whole КМД board**: its own К1801ВМ1 (`kmd-cpu`, 4 MHz, starts at 010000 from the high byte of its 177716) runs firmware 255 with 4 KB RAM and a `bk-fdc` (ВП1-128); `dvk-kmd` is only the link - the host registers 172140/172142, the firmware's view of them at 177100/177102, and the DMA window 40000-77777. The window's address bits 14-21 are the low byte of MYDR: the firmware (subroutine 007550) shifts the buffer address bits 14-15 and the MYCSR bits 8-13 there itself and writes the byte into both halves (two ВП1-095 on the board; MAME takes only bits 0-1). `address_bits = _22` on the ДВК-4 (jumpers S1-S6 carry A16-A21), 16 on the ДВК-3. Host INIT is IRQ2 of the board. The netlist and BOM are in `docs-external/DVK/kmd`. TESTMY's «запись/чтение с меткой» needed `bk-fdc` to keep the deleted data mark (F8) of a written sector - a flat image has no room for it, so it lives per drive as long as the same image stays in. Formatting 80 tracks takes about 280 s of emulated time
- **The DW hard disk (`dvk-dw`, КЗД 3.057.316) is MAME's `dvk_dwhle` registers with three corrections the factory test TESTDW (on the DW disk) forced**: the sector register is 1-based (DW.SYS writes (block + 1) & 15, the 279/134 boot reads sector 1 = block 0; the image is plain blocks, (cyl * 4 + head) * 16 + sector - 1, as `DW_System54.DSK` of Patronov's emulator, shipped as `software/dvk/rt11-dw.dsk`); interrupt requests are edge-triggered - enabling IE with DONE already up gives none (MAME raises one, and TESTDW's interrupt test then enters its read handler before the read), while a reset is an operation of `init_time` (200 ms; 100 ms is too short for the same test, which waits for the interrupt from the end of the reset, and 400 ms still fits the busy timeout of its register test); and the data register without a read/write command is a 256-word ring buffer (the buffer test writes 256 words with no command - MAME sent them to the disk). The full cycle ends with code 015 «операция завершена» in cell 001000 (`slow-dvk3-testdw`). The image is not put into the socket by the configs: 5 MB in every web bundle; on the page the visitor picks an image on their own computer (see the web hard disk point above). `HddImage` (`devices/common/hdd_image.*`) is the image file of every hard disk - `dvk-dw` and `UKNCHDD` (УК-НЦ, СМК/БК): shared open (`_wfsopen` with `_SH_DENYNO`), write protect, write to memory, the snapshot blob; the controllers keep only geometry and registers. `find_file_location()` checks existence with `GetFileAttributesW`/`stat`, not by opening: `dsk_tools::file_exists()` opens a stream, which on Windows fails while another process holds the file for writing - a parallel test run "lost" the image
- **ВМ2 console instruction 000020 reads the board's startup register** (`una_value`, 140001 on ДВК-3: 140000 + mode 001). The 055 monitor decides by its low bits whether to enter the console, boot or run.
- **In the ВМ2 console mode (SEL) only 140000-177777 answer** (monitor ROM, shadow RAM); the monitor reaches user memory with MFPM/MTPM. A timer request latched while in the console is taken right after RUN, so a program started with `G` needs vector 100 set.
- **ROM must not answer writes on МС1201.01** (`strict = 1`): the ROM BASIC sizes memory by writing down from 160000 and stops at the first timeout. Its own code occupies 100-..., so the line clock must stay off (no `~irq2`) - the real board has a front panel switch for it.
- **`dvk-mx` reads and writes a whole track** in FM words from the sync word 000363; a track is rebuilt from the flat sector image (11 x 256 per side) on each read and parsed back on write. The driver ends a write by clearing the WRITE bit and immediately starts a verify read - that clear must store the track. Two STEP writes within 2 ms are one step (MAME).
- **A track the program wrote is read back word for word** (`Drive::written`, keyed track * 2 + side, dropped when another image goes in, carried in a snapshot), and the sectors still go into the flat image. The format belongs to the program: RT-11 MX.SYS ends a track with three words 0101400 + track * 2 + side, the factory test TESTMX with one word track * 2 + side; rebuilt to the RT-11 pattern the test saw a «side error». A write is not stopped by the index (as in MAME): words after it overwrite the start of the same track, and the write ends when the program clears WRITE or stops feeding words (an underrun). TSTMX (TMX V04.03, «КНГМД and drives») feeds 177777 until it sees the index bit after a TR and only then lets go - stopped at the index it never got its TR and hung; with that fixed it passes in full, type 1 (40 tracks, `slow-dvk3-tstmx`) and type 3 (МС5305, 80 tracks, both sides, on a drive with `tracks = _80`). The older TESTMX still does not pass: its `F` (format with verify) writes each cylinder with MXCS bit 12 set and reads it back with bit 12 clear, which with bit 12 as the head select (here and in MAME) reads the other side - meant for a single-sided drive, or the head select is not what the register map says; and its `V`/`Q` (random data, compare) finds the read 3 words off, probably words lost to the 128 us word timing at the start of a read. TTIN (serial interface, under FTMON: `R TTIN`, type `1234JCUK`) and TESTDL (the КТЛК channels at 176560+, run on a second `dl11` with the loopback plug, `tests/files/dvk3-ktlk.ext`) pass - `work-dvk3-ttin`, `work-dvk3-testdl`. `INSTR.TXT` on the FODOS disk lists what every test is for. Also passing: TSTKGD (КГД, full check), TSTDW3 (КВД = DW), SYST2 (system test without a printer, from chain MXPSI3), SPEED (asks to switch the line clock on - only after its question, FTMON has overwritten vector 100: 786/361/85/63 thousand ops/s for ADD R,R / ADD mem,R / MUL / DIV), TSDL6N and TSDL6W (the six-channel КТЛК-6 board МС4622, 176560-176636 / 176500-176556 - six `dl11` with plugs, `tests/files/dvk3-ktlk6.ext`; the upper half needs DW out, its channel 5 takes vector 300). SYST/SYST1 (with a printer), LPIN (printer), DXIN (DX interface) and TOZUDP (extra RAM board) stop on a bus timeout - the machines have none of those boards
- **`dvk-dx` (RX11): the function and unit bits of RXCS are write-only** - the standard bootstrap waits on mask 100247, which includes them.
- **The КМ1801ВМ3 (`1801vm3`) is the same `pdp11core` with a `vm3` flag**; everything of its own is in `pdp11core_vm3.cpp` (MMU, internal registers, traps, halt mode, MFPx/MTPx) and is reached through `if (vm3)` hooks, so the ВМ1/ВМ2 paths are unchanged. The bus functions of the core take 22-bit physical addresses (`uint32_t`); the machine's mapper is physical (`address_bits = _23`: I/O page 17760000-17777777, the halt-mode shadow space from 20000000 = SEL). The MMU and PSW registers live inside the chip and are not in the mapper. The spec is the chip model (github.com/1801BM1/cpu11 `vm3`, forth32 `hdl/vm3/vm3_wb.v`) plus the DEC 11/34 diagnostics in `tests/files/vm3/` (`cpu-vm3-*`; `boot-dvk4-xm` boots RT-11XM from the shipped MY disk), run on the debug machine `vm3-test.cfg` with output read from `tt.text`. Things they pinned down: the PDR W bit is set on any write through the page except a write to SR0; SR0 shows mode and page of every relocated reference until an abort freezes it; SR2 is the address of the last *successfully fetched* instruction; an explicit PSW write overrides the instruction's own condition codes; autoincrements are undone when an instruction aborts, autodecrements stay; checks NR/PL/RO are independent (both bits can be set); opcodes 7-77 are reserved
- **The ВМ3 halt mode has its own stack register (R10)** for implicit stack operations - JSR, RTS, RTI and the entry, which pushes PSW/PC at 100000 (077776/077774 of the shadow space, where the 134 monitor reads them) - while `SP` named in an instruction is the kernel SP. The monitor sets `MOV #17000,SP` for the program it is about to start and then returns with RTS PC; one shared SP threw it into garbage. `pdp11core::stack_reg()` picks the register for push/pop
- **The КМД firmwares are for different variants of the board** (bkbtl-doc wiki «1801re2 ROMs»; dumps in `docs-external/DVK/dvk-rom/`): 255 - RAM on 537РУ8/РУ10, which is our board by the netlist (D22/D23, 4 KB at 020000-027777, stack 30000); 092 - RAM on 537РУ11 (512 bytes, stack 21000); 093 - К1809РУ1 (2 KB, stack 24000); 091 - the original КМД (К1809РУ1 and the ВП1-097 disk controller instead of ВП1-128). 092/093/255 are the same program apart from the RAM; 091 is a different one. 537РУ11 and К1809РУ1 are RAMs with their own МПИ interface, and 177760 is *their* register of start address and configuration: 092/093 write it at start-up (20400, 23000) and trap through vector 4 if nothing answers - unmapped, 092 never does a DMA. The netlist has nothing at 177760 (selects are gates on AD12-15, ВП1-096 D14 is on the host side), so nothing answers it here and only 255 is shipped (all four passed TESTMY and booted RT-11 identically while 177760 was accepted)
- **Monitor 377 is an alternative to 134 for the МС1201.04** (НПП «Кристалл» 1991, author К.Е. Юдин, for МС0507.03/.04 and МС0504; `docs-external/DVK/377.pdf` is its manual): the same ROM layout (6 KB, shadow RAM in the last 2 KB), the switch «ПЗУ монитора» of the ДВК-4. At power-on it runs its tests - HALT mode, RAM (much faster than 134: about 3 s), МMU and interrupts, the hard disk (НЖД = DW: reset, buffer, read of cylinders 0 and 152) - and only when all pass boots automatically: MY0, MY1 (only a disk whose block 0 starts with 240 or 260), then DW. A machine without DW, or with no image in it, stops in the console with «? - Ошибка» every power-on (010000 = not ready, «нет устройства» without the controller); `B` asks «Boot:» and takes a two-letter device name and unit (`MY0`, `DW0`), `Tn` runs test n (table 3 of the manual), the console commands are those of the DEC ODT plus `I`/`J` breakpoints, `F` search, `K`/`U`/`=` address spaces. It draws its banner with VT100 sequences (ESC #3/#4, ESC [7m): the КЦГД shows them, the КСМ prints them raw. The MY probe waits for the board's answer to command 7 with a counted loop of ~65000 passes; the КМД answers in about 0.9 s and the probe still succeeds. `boot-dvk4-377`
- **The 134 monitor runs from a copy**: at power-on it checks itself and the terminal (a `*` sent and expected back - a loopback plug selects the factory endless test), copies the ROM to RAM 0 through the HPAR window and runs the memory test from there in kernel mode with the 22-bit MMU on; that test ends with HALT, and only then the monitor prints `@`, about 10 s after power-on. Boot is `B` plus a device name and unit, no CR (`BMY0`, `BMX0`)
- **The КЦГД is a terminal, not a framebuffer**: its own КМ1801ВМ2 (7.7 MHz, firmware 181 at 100000, start and console vectors from 100000), own MS7004 and a serial line to the ДВК (two ВП1-065 on the board; the netlist shows only transceivers and address jumpers on the host bus). So it replaces the КСМ and the machine still has one display - no second screen was needed. `kcgd` holds the 17-bit 64K-word video memory (lower 16K words are the КЦГД CPU's RAM at 0, the rest through 160000/160002) and the ВП1-033 registers 167770-167777; the mapper gives it absolute addresses with `kcgd[160000]`. `kcgd-display` lays the frame out from the line-address table (word 015574/2, entries read from the end, each shown twice without interlace), 8x2-bit or 4x4-bit pixels by bit 16. The palette register is 6 bits, 2 per DAC output U55/U56/U57 (netlist: D73/D74 -> D72 -> 2-bit resistor DACs); U55 is red, U56 green, U57 blue (confirmed by the replica's author; `rgb` keeps the order configurable), so the firmware's default text value 017 is yellow. A character cell is 10 px (4 chars in 5 words); `display.text` matches glyphs against the 181 font through its KOI-7 tables (the font is not in code order). ROM 182 stores its font elsewhere, `text` does not work with it. The KeyGP ROM (RR1-183/184, graphics commands `ESC M <cmd> <args>`) sits at 120000-157777 with firmware 182: one `kcgd-rom` of 24 KB over 100000-157777 with `partial = 1` (`kcgd182-keygp.rom` is 182+183+184 back to back; the 8 KB variants leave the rest empty, and the range is `routed = 1` so an empty socket does not answer - KC.SAV with 181 counts an answer at 120000 as its error 13). Firmware 182 which jumps to 120000 at start-up (vector 4 brings it back when nothing answers) and lets KeyGP patch its RAM hooks; the command table then sits in КЦГД RAM at 045336 + 2 x code (`work-dvk4-kcgd-gp`). KeyGP checks for 182 (114142 at 100000), so it does nothing with 181. Firmware 182 starts in VT52 mode (`ESC <` switches to ANSI), and `ESC M` graphics work in VT52 only - in ANSI `ESC M` is reverse index. `'` takes one point (x as two 6-bit chars + 040, y as one, origin bottom left) and draws a rectangle from the current point. The language is undocumented here; `docs-external/DVK/circle.sav` (a game written for it) also has a string loop bug at 004164 (`MOV (R1),R2` without autoincrement) The mouse (`kcgd-mouse`) is two 3-bit up/down counters read in 167774 bits 8-11 (netlist: К555ИЕ7 D84/D14, mux D15 onto AD08-11, axis by control bit 2) - no firmware reads it, programs downloaded into the КЦГД do. The factory test `KC.SAV` (FODOS test disk, `work-dvk4-kcgd-factory`) pinned the rest: palette registers are 8 bits and readable at 167773 by index; REQB is bit Q12 of the scan line counter (toggles every 16 lines, ~0.5 ms - MAME's "500 Hz" is wrong); REQA is the latched bit 16 of the last 160002 read XOR control bit 6 at the moment 167770 is read; interrupt A/B requests come on the rising edge of "enabled and raised", including enabling an already raised one; the КЦГД CPU needs `reply_delay` > 8 (12 is set: at 8 the second wait loop of error 44 lasts exactly one frame and passes or fails by the frame's phase) - its RAM is the video DRAM the raster keeps busy; the MS7004 must answer $FD with $01,0,0,0. Every device of class `mouse` is a `HostMouse` (`move()`, `mouse_plugged()`), which is what `Emulator::mice` holds; the БК «Марсианка» `Mouse` is one of them
- **The `*_mc1201.rom` dumps** (031, 054, 279 in `docs-external/DVK/`) are stored with the words in reverse order and inverted data, plus 2 trailing bytes; `deploy/computers/dvk/files/*.rom` hold them decoded (279 matches forth32's copy except their B RK patch).

### Core Classes

- **`Core`** (`emulator/core.h`): Base device class with interface management, memory read/write hooks, message passing
- **`Emulator`** (`emulator/emulator.h`): Main orchestrator (plain C++ class, not QObject) - manages device lifecycle, CPU execution timing, rendering, keyboard input via `key_event(int key, int modifiers, bool press)`
- **`CPU`** (base), **`I8080`**, **`Z80`**, **`6502`**, **`65C02`**, **`k1801vm1`**, **`i8086`** (`i8088` / `i8086`): CPU implementations with instruction execution
- **`MemoryMapper`** (`emulator/devices/common/page_mapper.h`): Routes address space to devices
- **`GenericDisplay`**: Base for display devices; implementations handle video output
- **`InterfaceManager`**: Manages interface connections between devices (wires them together)
- **`ScriptEngine`** (`emulator/script/script_engine.h`): Runs `.ecat` test/automation scripts against the emulator (see Scripting below)

### Scripting

`src/emulator/script/` is a Qt-free script runner driving the emulator from a text file (`docs/SCRIPTING.md` has the full command reference, in Russian). Launch with `eCat3 --script <file.ecat>` (or `--config <file.cfg>`; a positional argument is dispatched by extension) from the `deploy/` working directory.

Scripts load a machine (`MACHINE`), wait, press keys (`KEY`, `TYPE`), take screenshots (`SCREEN`), dump device state to a log (`LOG dev.field`, `LOGDEFS` picks width and base), send device commands (`COMMAND dev.cmd(args)`), snapshot the whole machine (`SAVESTATE`, see "Saved state" above), and `EXIT`. This is the practical way to reproduce a bug or verify a machine without driving the GUI by hand.

Two things surprise people:
- **`WAIT` counts emulated time, not wall-clock.** If the config fails to load or the CPU is stopped, the clock never advances and the script hangs forever. Wrap batch runs in a timeout.
- **The log file is created lazily** next to the script, named `<script>-YYYY-MM-DD-HH-mm-SS.log`; a script that prints nothing leaves no file behind.
- **Relative paths in `COMMAND dev.load("...")` resolve from the script's directory first**, then the config's directory / `files/` / `deploy/software/<machine>`, then the working directory (`deploy/`). Test assets therefore live in `tests/files/` and are loaded as `"../files/x.dsk"` from `tests/scripts/`.
- **On the БК a `KEY` held for 200 ms already autorepeats** in the MK-DOS / ANDOS shells, so a cursor move lands one entry further than asked: hold keys for `_50`, and walk to a known position (several `up` to the top) instead of trusting where the cursor was left
- **`SCREEN` waits for a frame from the render thread**, so whatever follows it runs at an emulated moment that depends on the host. Take screenshots after the measurements, never between a `WAIT` and a timing-sensitive `COMMAND`
- **Load a test machine with `MACHINE` from an `.ecat`, not through an `.ext`'s `@script`**: the embedded script starts after the machine has already run for a while, so its `WAIT`s end at different instructions from run to run (`work-poisk-*.ecat` load `tests/files/poisk-*.ext`)
- **`COMMAND dev.set` writes with `force`**: an i8255 port set this way is latched but not driven onto its lines. Drive a port from guest code when the wiring is what is being tested
- **`TYPE` cannot type every character on every machine**: a key that exists only with Shift in a Rus-mode map entry (`:` on Irisha) comes out wrong. Use `KEY 50,50,shift+colon` instead.

Devices expose themselves to scripts through `get_device_fields()` / `get_field()` (readable state) and `get_device_commands()` / `send_command()` (actions), declared in `ComputerDevice` and overridden down the hierarchy. `AddressableDevice` already provides `value`/`value16`/`size` plus `set`/`set16`/`fill` (`set` and `set16` take a list of values for consecutive addresses, so machine code is one line per instruction), and `CPU` provides `pc`/`registers`/`flags` plus `stop`/`run`/`step`/`breakpoint`/`setreg`, so a new device usually needs nothing to be scriptable.

**GUI record / replay** (toolbar block, menu Emulation > Action recording) uses the same `ScriptEngine`: it owns the command buffer, and `ScriptRecorder` (`emulator/script/script_recorder.h`, Qt-free) appends commands built from GUI events, timed by `Emulator::clock_counter`. A press/release pair becomes `KEY delay,hold,name`; overlapping presses become `KEYDOWN` / `KEYUP`. `format_script_command()` is the serializer; arguments are stored in file syntax (escapes included), so a value built from scratch goes through `escape_script_text()` first. Threading rule: the emulation thread only calls `tick()`, which has a lock-free fast path and takes the engine mutex only when a command actually runs; the GUI edits the buffer (`append`/`truncate`/`seek`) only while the engine is not active. New GUI actions that should be replayable call `e->record_command()` / `e->record_verb()` right after performing the action (see `fdd_open`, the device-option combo lambda, `TapeRecorderWindow`).

### Rendering System

Three rendering backends controlled by compile flags:
- `RENDERER_QT`: Software rendering via Qt painter
- `RENDERER_SDL2`: Hardware-accelerated via SDL2 (preferred for Windows 7)
- `RENDERER_OPENGL` (default for Qt6 debug): OpenGL rendering (best performance)

Selected at build time with `-DRENDERER_OPENGL=1` / `-DRENDERER_SDL2=1` / `-DRENDERER_QT=1`. A windowed build needs exactly one, and configuration stops otherwise. A Debug build that names none gets OpenGL with Qt 6 and SDL2 with Qt 5. OpenGL needs Qt 6.

### Common Tasks

**Add a new CPU type:**
1. Create `emulator/devices/cpu/newcpu.cpp/h` inheriting from `CPU`
2. Implement instruction decode/execute cycle
3. Add to `src/emulator_sources.cmake`, the one core list every build includes (desktop, console, web)
4. Register the factory in `Emulator::register_devices()`. The debugger asks the processor for its disassembler: override `disasm_table()` to name a table in `deploy/data/*.dis`, or `create_disasm()` to return a `DisAsm` subclass when the instruction set does not fit the table format (see `k1801vm1::create_disasm()` and `disasm_pdp11.cpp`)
5. Reference in `.cfg` files via `device_id: newcpu {}`

**Add a new device:**
1. Create `emulator/devices/common/newdevice.cpp/h` (or `specific/` for machine-specific)
2. Inherit from `ComputerDevice` (generic) or `AddressableDevice` (memory-mapped/port-mapped)
3. Declare `Interface` members in the class body; they self-register on construction
4. Implement `get_value(addr)` / `set_value(addr, val, force)` for addressable devices, `clock(counter)` for clocked devices, and `interface_callback(id, new_val, old_val)` for reactive devices
5. Add a `create_xxx(InterfaceManager*, EmulatorConfigDevice*)` factory function in the `.h`, implement it in the `.cpp`
6. Register the factory in `Emulator::register_devices()` in `emulator.cpp`
7. Add source files to `src/emulator_sources.cmake`
8. Optional: override `get_device_fields()` / `get_field()` and `get_device_commands()` / `send_command()` to expose state and actions to scripts
9. Override `save_state()` / `load_state()` for anything a cold start does not reproduce — the base class already carries the device's interfaces and its fractional clock, so most devices need only their own registers. See "Saved state" above for what must not go in and what belongs in `state_restored()` instead

**Reserved device names:** Every config MUST have a device named `"cpu"` and one named `"mapper"`. The emulator also looks up `"display"` and `"keyboard"` by name. These four names are hardcoded in `Emulator`; everything else is found by class (`find_devices_by_class()`): the drives (`fdd`), the tape (`tape`), the audio outputs the volume control reaches (`sound`, set by `GenericSound`). `"cpu"` is the *master* processor — its frequency is the machine's time base (`clock_counter`, script delays, `WAIT`) — and `"mapper"` is the default address space a processor gets. A machine may declare more processors; see Clock domains below.

**Add a new computer configuration:**
1. Create `.cfg` file in `deploy/computers/` subdirectory (e.g., `my_machine/config.cfg`)
2. Define system, CPU, memory, devices, and interface connections
3. Place ROM/disk images in same directory
4. Create matching `.md` file with user-facing description
5. No code recompilation needed

**Test changes:**
- Most behavior testing is via `.cfg` file modifications

Emulated time makes every run byte-identical, so a screenshot is a valid reference. See `tests/README.md`; a machine or device change that alters behaviour means re-recording the affected references in the same commit
- **The same scripts through MCP**: `python tests/run_mcp_tests.py --exe <build with ENABLE_MCP>` replays every test (no development build enables MCP by default; `src/cmake-build-mcp` is a headless one configured with `-DENABLE_GUI=OFF -DENABLE_HEADLESS=ON -DENABLE_MCP=ON`) against `<exe> --mcp` (`ecat_machine` plus one `ecat_run`) and diffs the answer against the same `expected/*.txt`, which is the only check of the `ScriptSink` path. A live session runs the machine between loading it and the first command, so anything sampled from absolute emulated time (`ay.level`, a generator phase) will not repeat: such a script declares `# @nomcp <reason>` in its header and is skipped
- **Any stderr output fails every test**: the runner treats a non-empty stderr as a problem, so the core must not print diagnostics. Real discrepancies are listed per test in `tests/results/report.txt`. On Windows without `python` on PATH use `py tests/run_tests.py`

The flip side: `--no-sound` returns from `GenericSound::load_config()` before `init_sound()`, so a headless-only run never enters the audio setup path at all — a fault there shows up only when the suite runs the windowed build
- **`--update -k X` re-records every artifact of X**, including screenshots that already passed within their `@pixels` tolerance (an animation phase): restore those with `git checkout` so only the intended reference changes
- **Under `-j 8` a few tests fail now and then on host load alone** (`state-unior`, `state-uknc-sound`, `boot-2cpu` have): rerun a failure with `-k` before looking for a cause
- **Keep test assets tiny**: every `"../results/…"` name in a script becomes a compared artifact, so do not save whole disk images from a test. Verify a write by reading it back on the machine (`DIR`, `TYPE`) plus a counter field such as `fdc.writes`. Synthetic images go in `tests/files/` next to the Python that generates them (an image shorter than the geometry is zero-padded on load)
- **Tests run on the shipped defaults, not on the developer's ini**: `apply_saved_device_options()` reads `[DeviceOptions]` from `deploy/ecat.ini`, where the GUI remembers a monochrome БК display or a plugged mouse, so `KeepIni` in `tests/run_tests.py` (also used by `run_mcp_tests.py`) swaps in a copy of `deploy/.ecat.ini` for the run and puts the developer's file back afterwards. A script started by hand still sees the developer's ini, which is why the mouse test plugs its socket explicitly
- **The runner prefers a windowed build over the headless one**: `tests/run_tests.py` scans
  `src/cmake-build-*/eCat3.exe` first and only falls back to `eCat3-headless`, and it prints the
  executable it picked. Rebuilding one directory and recording references with another silently bakes
  the old behaviour into `expected/`; pass `--exe` when in doubt
- **The wrapper also survives the emulator dying**: before, it exited with it, and the server stayed gone for the rest of the client session - no client restarts it by itself. Now a hung request gets an error, the next tool call starts the emulator again, and every start, restart and exit code (a crash is `0xC0000005`) goes to `%TEMP%/ecat3-mcp-reload.log`, since the client hides the wrapper's stderr. A copy of the build is taken before the old process is stopped, waiting for the linker to finish, so a call in the middle of a build does not leave the server empty
- **The MCP server runs behind `.build/mcp_reload.py`**, and that is not decoration: an `eCat3.exe --mcp`
  started directly outlives every rebuild, so it holds the exe open (`cannot open output file eCat3.exe:
  Permission denied`) and keeps answering from the core it was launched with - plausible answers from a
  stale build. The wrapper runs the emulator from a temporary copy and restarts it whenever the built exe
  gets newer, so a rebuild is picked up by the next tool call; it says so in the answer, and the emulated
  machine has to be loaded again. `ECAT3_MCP_NO_RELOAD=1` keeps only the copy. See `docs/MCP.md`

The distributed defaults are `deploy/.ecat.ini`, which the release scripts package as `ecat.ini`. A missing `ecat.ini` is made a copy of `.ecat.ini` by both frontends and by `tests/run_tests.py` - without its `[TapeFiles]` no tape image loads, which is how a fresh checkout would otherwise break every tape test. A new default setting therefore goes into `.ecat.ini`

### Debugging Tips

- **`globals.h` is generated**: Produced by `configure_file(globals.h.in ...)` at CMake configure time into the build directory, one per build directory. Do NOT edit it; edit `globals.h.in` or CMake variables instead. It used to be written into `src/`, where every build directory overwrote the others' copy; the configure step deletes a `src/globals.h` left from then, since it would be found first.
- **`LOG cpu.history(_40)` answers "how did it get here"** on the 1801 processors: the last 256 executed addresses, oldest first. Combined with `COMMAND cpu.breakpoint(addr)` at the crash address it finds a wild jump in one run; that is how the УК-НЦ plane index bug (176640 halved into a processor address, corrupting one word of a loaded program) was traced
- **A halted CPU still runs the script engine**: `Emulator::timer_proc()` calls `script->tick()` on the zero-cycle path too, so `LOG`, `COMMAND` and the other instant verbs work while `cpu.stop()` holds the processor. The delays cannot - they are counted in emulated time and that has stopped, which is what an MCP session reports as a stall instead of hanging forever.
- **A renderer's `get_screenshot()` must return raw RGBA**, `sx*sy*4` bytes: `Emulator::store_screenshot()` encodes the PNG itself and drops a buffer of any other size (with a line in `cerr`). The contract is written next to the declaration in `renderer.h`; `WasmRenderer` used to return an encoded PNG, which is why it is written down at all. Nothing in the web frontend requests a screenshot yet - there is no C API for scripts there - so `SCREEN` in the browser is correct but unreachable.
- **A tape write can leave the emulated keyboard in the other alphabet** (known bug, Орион-128): `scan-keyboard`
  takes its Rus/Lat register from `~ruslat_led`, and the Орион monitor writes the whole of port C - data bits
  included - while saving to tape, so the indicator line ends up data dependent while the monitor's own flag
  (`$F3E5`) does not move. `RUS_REMAP` then presses the key from the other half of the layout: `I` arrives as
  `$5B` and the monitor answers `?`, which looks exactly like a tape read failure. `LOG keyboard.rus` against
  the machine's own flag separates them; two presses of РУС/ЛАТ resynchronise. Радио-86РК, Апогей and
  Микроша are immune - their ROM re-asserts the indicator from its own variable on every keyboard poll. Left
  as is on purpose: the indicator is the only signal of the register, and the remap is what lets a ЙЦУКЕН
  host keyboard drive a ЯВЕРТЬ machine
- **The indicator line is taken into the register at a scan write, never the moment it moves**: the
  Радио-86РК and Апогей ROMs zero the whole of port C on every keyboard poll and set PC3 back from their flag
  a few instructions later (Апогей `$FE7F-$FE89`). Following `~ruslat_led` instantly made the drawing's РУС
  lamp flicker and could remap a host key typed inside that 20 us dip. `ScanKeyboard::interface_callback()`
  latches the line and applies a change of it on the next write to the scan lines, which the ROM does before
  the dip and after the restore
- **`COMMAND sound.record("f.wav")` … `sound.record()` captures what goes to the audio device**, also under `--no-sound` (44100 Hz); the file lands next to the script. numpy/matplotlib are not installed system-wide: make a venv in the scratchpad for spectrograms
- **A `.ecats` snapshot carries its own `@config`**: a fix to a machine's `.cfg` (a new device, a mapper line) does not reach a snapshot taken before it. To test a user's snapshot against the fix, patch the `@config` text inside a copy of the zip
- **The СМК-512 BIOS maps drive numbers differently from the КНГМД**: 0-1 are the floppies, 2 and up the logical disks of the hard disk, while the КНГМД driver folds the drive number to 0-3. A program asking for a drive the СМК does not have gets BIOS error 13 (in cell 052) after the ~10 s wait for an empty IDE channel - `andos330.img` used to keep its shell's right panel on E: for exactly this reason, see `disk-bk0011m-smk-shell`. The BIOS keeps its partition table copy and variables in board RAM segment 7 (176000-176777, 176770 = number of logical disks)
- **Hard disk images of the БК are stored as on the drive, so the CPU sees them inverted**: search an image for text only after inverting its bytes. A `*.hdi` starts with a 512-byte IDENTIFY header before sector 0 (`UKNCHDD::m_data_offset`); without it every sector reads one off and the BIOS finds no partition table
- **To bisect a regression, build an old commit in a `git worktree`**: the submodule `src/libs/dsk_tools` comes up empty there, copy its contents in from the main tree before configuring (`ENABLE_GUI=OFF ENABLE_HEADLESS=ON`), and run it from the worktree's own `deploy/` after copying `.ecat.ini` to `ecat.ini`
- **Measuring the cost of a core change**: every build runs in real time and spins between slices, so wall time and process CPU time say nothing. Accumulate `steady_clock` time around `timer_proc()` in the emulation loop (a temporary insert, dumped to a file at exit), run the same fixed script twice before and after, and compare; the spread between two runs is about 5%. When comparing screenshots across runs at different CPU speeds, remember the program is at a different moment in each
- **No compile-time logging**: the old `LOGGER` / `LOG_*` macros and the `Logger` class are gone. To trace a device, expose its state through `get_device_fields()` / `get_field()` and read it from an `.ecat` script (`LOG dev.field`), like `bk-fdc` does with its `trace` field
- **PDF documents in `docs-external/`**: the Read tool cannot render them here (no poppler); `/mingw64/bin/pdftotext` from Git Bash or `pypdf` extracts the text layer
- **The address label of `LOG dev.value(from,to)` follows the LOGDEFS base**: after `LOGDEFS _8,_16` on a БК the label `$0740` is hex (octal 003500), not an octal address
- **Debug Windows**: GUI provides disassembler, memory dump, port inspector, CPU state viewer
- **Breakpoints**: Debug menu supports execution breakpoints and step modes
- **Scripts beat GUI automation**: `LOG mapper.map` prints the memory and port map in the order ranges are matched (with `[off]` on ranges disabled by `cancelinit`) — usually the fastest way to see that a window or page is wired to the wrong device. `LOG cpu.registers`, `LOG ram0.value(from,to)` and `SCREEN` cover most of the rest

## Important Implementation Details

### Interface System

Interfaces are declared as `Interface` member variables in device classes. The `Interface` constructor auto-registers with `InterfaceManager`:
```cpp
Interface(ComputerDevice *device, InterfaceManager *im,
          unsigned int size, const std::string &name, unsigned int mode,
          unsigned int callback_id = 0)
```
The `callback_id` is the key reactive mechanism: when a connected interface changes value, `device->interface_callback(callback_id, new_value, old_value)` fires. A `callback_id` of 0 means no callback.

Interface wiring happens in `ComputerDevice::load_config()`, not constructors. Config parameters prefixed with `~` are parsed as connections. The `!` prefix inverts the signal. Bit-range syntax `[lo-hi]` handles width differences via mask/shift.

Propagation is **synchronous**: calling `interface.change(value)` immediately cascades through all linked interfaces and triggers callbacks. No event queue.

Config example:
```
memory_mapper: page-mapper {
  ~address = cpu.address
  ~data_read = cpu.data_read
}
ram1: ram {
  size = 64k
  ~address[0-15] = memory_mapper.address[0-15]
  ~data = memory_mapper.data
}
```

### Two-Phase Device Initialization

1. **Constructor**: Creates `Interface` members (auto-registered), sets defaults. Must NOT reference other devices (they may not exist yet).
2. **`load_config(SystemData *sd)`**: Base class processes `~` interface connections. Subclasses load ROM images, resolve cross-device references by name, call `init_sound()`, etc.

### Key Constants and Sentinel Values

- **`_FFFF`** (`(unsigned int)(-1)` from `utils.h`): Represents "all bits set / no device responded / high-impedance". Returned by `MemoryMapper::read()` on miss; initial value of all interfaces; broadcast by `MODE_OFF` interfaces.
- **Fixed-size limits**: `MAX_DEVICES = 100`, `MAX_INTERFACES = 200`, `MAX_LINKS = 100` per interface.

### CPU Execution Model

Emulation runs in a dedicated high-priority thread (not QTimer). `Emulator::run()` spawns two raw threads: `emulationThread` (TIME_CRITICAL priority on Windows, SCHED_FIFO on POSIX) and `renderThread` (50fps target). The emulation loop polls wall-clock time with microsecond resolution, converts elapsed time to cycles of the master processor, and calls `cpu->execute()` which returns cycle count. `DeviceManager::clock(domain, counter)` then clocks the devices of that domain whose `clock()` does something — the per-domain `clocked_devices` lists built by `load_devices_config()` from the `m_clocked` flag every such class sets in its constructor. Processors are not in those lists: each is clocked by its own `execute()`.

**Clock domains.** `Emulator` keeps one `ClockDomain` per processor: the CPU, a `scale` and a position `norm`. `scale` is `LCM(all frequencies) / this frequency`, computed once in `run()`, so positions of different processors are comparable as whole numbers — 8 MHz and 6.25 MHz give scales 25 and 32, the true 32:25 interleave of the УК-НЦ. Each pass `timer_proc()` runs whichever domain is furthest behind, adds `cycles * scale` to it and clocks that domain's devices; what a domain overshoots the slice by is carried into the next one. With a single processor the LCM is its own clock, every scale is 1, and the arithmetic is exactly the old `local_counter` loop — which is why the whole regression suite has to pass unchanged after touching this. A device joins a domain through `clock_source` (`ComputerDevice::load_config`), which also sets its `m_system_clock`, so anything converting real units into cycles uses the frequency of its own side of the machine. `clock_counter` — emulated time for scripts, `WAIT` and recordings — counts the master only. `deploy/computers/bk/2cpu-test.cfg` + `tests/scripts/boot-2cpu.ecat` is the test that the ratio really holds.

Two properties of that loop are deliberate and easy to "fix" into a regression:
- **The loop spins.** Between slices it calls `yield()` rather than sleeping, so the thread holds a core even while the CPU is stopped. A `sleep_for` needs `timeBeginPeriod()` on Windows (the default timer granularity is ~15 ms, and 15 ms chunks of emulated time cost audio quality), which is what the removed `Core/TimerResolution` and `Core/TimerDelay` settings were once for. The regression suite cannot see the difference — it measures emulated time, not smoothness — so this is a change to make by ear, not by test.
- **The catch-up is not capped.** The whole interval since the previous slice is replayed, however long. A ceiling makes emulated time fall behind the wall clock whenever the host is busy, which breaks a parallel test run (`-j4`) in a way that looks like random screenshot and timeout failures. What a 32-bit counter used to break — a slice longer than 2^32 cycles never ending — is fixed by the domain positions being 64-bit, not by a cap.

### Memory Access

CPU holds a direct pointer `mm` to `MemoryMapper` (set in `CPU::load_config()`). All memory/port access goes through this pointer, **not** through the interface system:
- `read_mem(addr)` → `mm->read(addr)` → `MemoryMapper::map()` finds matching `AddressableDevice` → `device->get_value(addr)`
- `write_mem(addr, val)` → `mm->write(addr, val)` → `device->set_value(addr, val, false)`
- Port I/O: `read_port()`/`write_port()` → `mm->read_port()`/`mm->write_port()` (same dispatch via separate port map)

`MemoryMapper::map()` does linear scan of ranges checking: config mask match, address in range, address mask filter, and read/write mode. Returns `_FFFF` (all bits set) when no range matches. The four emulation entry points go through a page cache first, see below; everything else (the debugger, `mmwindow`, scripts) keeps using the scan.

**Word access**: CPUs with a 16-bit bus (the К1801ВМ1 family) use `mm->read_word()` / `write_word()`, which map once and call `AddressableDevice::get_value_word()` / `set_value_word()`. The default implementation composes the word from two little-endian byte accesses, so byte-oriented devices need no changes; `Port` and `MemoryMapper` override it to stay atomic. A `port` with `size > 8` is a true two-byte register: byte accesses pick a lane by address bit 0, word accesses see the whole thing.

### Display Rendering

Display devices accumulate pixel data into buffer. Rendering happens on the render thread (typically 50fps). Multiple render backends supported via interface abstraction.

## Configuration File Format (Quick Reference)

See `docs/CONFIG.md` for complete spec. Key points:
- `device_id: device_type { ... }` declares device
- `~interface_name = other_device.interface_name` connects devices
- `parameter = value` sets device parameters
- Hex prefix: `$` (e.g., `$FF`), Octal: `&` (e.g., `&177714`), Binary: `#` (e.g., `#1010`), Multiplier: `k` (e.g., `64k`). The same prefixes `format_number()` writes, so a value from a `LOG` line can be typed back in. Octal is what every К1801ВМ1 (БК) document uses; note that the `#` of a PDP-11 listing means an immediate operand, not binary
- **`radix` in the `system` section sets the base of every unprefixed number of that machine** (`radix = 8` in every BK config), and `_` marks the decimals — `clock = _4000000` next to `start_address = 140000`. It is ambient state: `set_default_radix()` (`utils.cpp`) is called by `Emulator::load_config()` from `EmulatorConfigDevice::radix`, and by the script verb `RADIX`. `parse_numeric_value(s)` therefore reads it everywhere; pass `10` explicitly for a number that is **not** the machine's — ini settings, tape format strings, the base of `RADIX` itself, and interface bit ranges in `convert_range()`. Converting a machine to a non-decimal radix means marking every count, size, frequency and delay in its configs **and its scripts** with `_`; the regression suite is what catches a missed one
- **The arguments of a script verb are read in the machine's radix too**, which is easiest to forget when typing commands by hand into an MCP session rather than into a `.ecat` file. On a БК `LOGDEFS 16,8` fails outright (`Invalid numeric value: 8` — an octal number has no digit 8), and `WAIT 1000` silently waits 512 ms; write `LOGDEFS _16,_8` and `WAIT _1000`. The base of `LOGDEFS` is itself such a number, so the octal output of a БК is asked for with `_8`

## Non-Obvious Design Patterns

- **A device is clocked in the order it is declared, and for a device that reads another's fast-moving state that order is part of the wiring**: the slice is one instruction (a dozen ticks), and anything moving faster than that — the УК-НЦ tone grid steps every 12.5 ticks — cannot be sampled at the slice boundary, it has to be integrated over the slice. `UKNCSound` does that from the timer's step log, so it is declared *after* `pp-timer`: declared before, it would average the previous instruction's slice and weight it by this one's, which is audible in the pauses of a melody. There is no mechanism that enforces this; the config says why.
- **`DeviceManager::clock(domain, counter)` skips processors by class, not by index**: devices are stored in declaration order, and a CPU is recognised by `device_class == "cpu"` (set in `CPU::CPU`). Clocking a processor here would double-count the cycles its own `execute()` already returned. Slots 0 and 1 used to be reserved for the names `cpu` and `mapper`, which is what made a second processor impossible.
- **`clock` parameter has dual meaning**: For a processor it's the absolute frequency in Hz. For all other devices, `clock = 1/2` sets a multiplier/divider ratio relative to that device's clock domain. Both constructors read the parameter, so `CPU::CPU` resets `clock_miltiplier`/`clock_divider` back to 1 after the base class has taken the frequency for a multiplier.
- **An ВВ55 mode word resets the output registers**: a control word with bit 7 set clears ports A, B and C and drives the output ones to 0 (8255A datasheet, "Mode Definition Format"); a bit set/reset word (bit 7 clear) does not. It is the only thing the Агат-840 boot ROM does to put the controller into a known state, so without it a warm restart out of a program that left drive B selected steps forever waiting for a track 00 that drive cannot report. Школьница's «Конец работы» is exactly that case; `work-agat-9-restart` is the test
- **The on-screen keyboard presses machine keys, not host keys**: `Emulator::key_event_id(id, press)` goes straight to `Keyboard::key_event_id()` and skips `rus_translate()`, because the drawing shows the machine's own layout — pressing Й on an Орион picture is already `EmuKey::Key_J`, and the ordinary `key_event()` would remap it a second time into О. The names come from the machine's native key table (`keys = <file>`, `picture = <file>.svg`), all start with `key_` so they never collide with a host key name, and `KEYDOWN`/`KEYUP` accept them. That table is what expresses things the host `.map` cannot: on the БК `key_1` sends $31 or $21 depending on the register latch, while `bk.map` has `!/S` and no `1/S` at all
- **`MainWindow::e` is null once `closeEvent()` has run**: the emulator is deleted there, and the window still receives events afterwards - `ActivationChange` (which releases the host keys), the release of the key that closed it, a paint. Before the pointer was cleared, a click on the close button of the active window crashed the process with 0xC0000005 whenever the freed memory had been reused, which is rare enough to look random. A new window event handler that touches `e` checks it for null first. Under MCP the emulator is not deleted at all: `McpSession` holds the same pointer (its destructor runs after the window's and clears the script sink through it, and the stdin reader thread may be mid-request), so `closeEvent()` only stops it and the process exit frees it. Deleting it there crashed an MCP session closed after a long run, once the freed memory had been reused
- **A window changes a device only through `e->invoke()`**: a device is not locked, it belongs to the emulation thread. `Emulator::invoke(fn)` runs `fn` there, between two time slices, and returns when it has run; with no emulation thread (nothing loaded, the machine stopped) and on that thread itself it runs `fn` at once, so a script verb and the reset in `run()` go straight through. `Emulator::reset()` goes through it by itself; the drive menu, the option boxes, the debugger (mode, breakpoints, PC, a byte typed into the dump) and the tape window call it explicitly - before that a disk swapped under a spinning drive replaced the buffer the controller was indexing, and a reset from the menu cleared the memory the processor was executing. Three things to keep in mind: `fn` must not wait for the calling thread, which is waiting for `fn`; what it captures by reference lives on the caller's stack, which is fine precisely because the call is synchronous; and reads for display (registers, the tape counter, the drive led) still go direct - a stale value there is a wrong number on the screen for one refresh, not a fault. The debugger reads memory with `CPU::peek_mem()` (the mapper's `get_direct()`), never `read_mem()`: that one is a bus cycle, with the strobes, the read-to-clear registers, the page cache fill and - on a 1801 - the timeout flag the instruction being executed is about to test. Left outside the queue: the hard disk (its own mutex), host keys (next point) and the other device calls of `wasm_main.cpp` (options, tape). Waiting on the browser's main thread works: the page's Reset and Power (`wasm_reset` -> `Emulator::reset()`) go through the queue and return in under a millisecond
- **Host key events arrive on the GUI thread**: `Emulator::key_event()` and `key_event_id()` call straight into the keyboard device from the window, while the machine runs on the emulation thread. A keyboard that only updates its own key matrix, which the machine polls, gets away with it; one that writes a register and drives an interrupt line from `key_down()` races the processor taking or clearing that same request. `UKNCKeyboard` therefore only queues codes in `key_down()` and hands them to the machine from `clock()`. Scripts and MCP press keys on the emulation thread, so they cannot show such a race - but do not blame every lost key on it: the УК-НЦ menu that skipped every fifth arrow was an interrupt fault, see the next point
- **An interrupt request that is a one-shot event must be cleared by the acknowledge, not by the level**: a 1801 processor reports taking a vectored interrupt on `~iako` (the vector, for an instant). The УК-НЦ channels latch a request on the transition to ready and drop it there. Computed as "ready and enabled", the free transmitter of channel 0 was offered again after every other interrupt, and its ROM handler (175540) steals a character from the keyboard buffer when the ЗАГРУЗКА menu is waiting for input - the menu got the arrow code without its ESC and ignored it. The regression is `work-uknc-menu`
- **РУС/ЛАТ flips on the press, never on the release**: `ScanKeyboard::key_down()` toggles `rus_mode`, `key_up()` only releases the line. Toggling on both edges cancels itself out and leaves the register wherever the indicator line (`~ruslat_led`) happened to point - which the Орион configs used to paper over with an inverted `~ruslat_led`. All three now wire it straight, like РК86 and Микроша, and the register follows the monitor's own flag ($F3E5)
- **An interface line has no wired-AND: two writers overwrite each other**, so a second interrupt source on a line cannot simply be linked to it. The Агат ЯЗС (`agat-yazs`) takes the rest of the machine's IRQ on `~irq_in` and drives `cpu.~irq` with both (`Agat-9-yazs.ext`); a new open-collector source does the same
- **Port access strobe**: `Port::get_value()`/`set_value()` toggle `i_access` (0→1 pulse) on every access. Devices connected to `port_name.access` receive this as a trigger. Used for keyboard reset, sound toggle, etc.
- **A register whose read does something must override `get_direct()`**: the dump window, `LOG dev.value` and `MemoryMapper::get_direct()` (which the debugger's dump goes through) read with it, and the default forwards to `get_value()`. Without an override, looking at a channel data register takes the byte, a timer read reloads the counter. `value16` still reads the way the processor does (`get_value_word`), side effects included
- **`PortAddress` stores address, not data**: `PortAddress::set_value(addr, val)` drives `i_data` with the *address*, not the value. Models Apple II / Agat soft-switches where the accessed address encodes the command.
- **`force` parameter**: `set_value(addr, val, force=true)` updates internal state without driving bus interfaces. Used to initialize registers without triggering connected devices.
- **ROM has `auto_output = true`, RAM does not**: ROM responds to address bus changes by outputting data on `i_data` automatically (combinatorial lookup). RAM requires explicit `get_value()` calls through the mapper.
- **Sound uses `AudioDriver` abstraction**: `GenericSound` uses a pluggable `AudioDriver` (`emulator/audio/audio_driver.h`). Default backend is **miniaudio** (`audio_driver_miniaudio`); SDL2 audio is optional via `USE_SDL_AUDIO` CMake flag. Sound devices inherit from `GenericSound` and override `calc_sound_value()`.
- **`cancelinit`**: MemoryMapper feature where range index 0 (marked `[*]` in config) is active only after reset. Flips off when CPU reads an address matching the cancelinit mask. Models Agat boot-ROM-only-at-reset behavior.
- **`portstomemory = 1`**: Routes port I/O to the memory address map instead of the port map. Used by Agat-9 (6502 has no separate I/O space).
- **The mapper resolves a whole 512-byte page at once, and the config value is part of the tag**: `MemoryMapper::find_page()` / `fill_page()` (`core.h`, `core.cpp`) answer `read`/`write`/`read_word`/`write_word` in O(1) when, of the ranges matching the current config, at most one intersects the page — and that one covers it entirely, filters no addresses of its own (`address_mask`) and does not continue a read (`or_read`) or a write (`through`). Anything else marks the page `uncached` and it goes the old way, which is what the I/O page of every 1801 machine does. Because the config value sits in the tag, **a configuration change invalidates nothing** — that matters, since `interface_callback` fires on every write to the config line, not only on a real change. Anything that ever changes `ranges[]` or `first_range` must call `invalidate_pages()`; today that is `load_config`, `reset()` and the `cancelinit` flip. 512 bytes is not arbitrary: it is the largest page that keeps the УК-НЦ ROM window (ending at 176777) whole and leaves 177000-177777 in one page
- **`Interface::mask` is set by the constructor now**, not only by `set_size()`. An interface whose size never changed used to carry whatever was on the stack; nothing read it until a saved state needed the width of a line, and then the same machine wrote two different files on two runs.
- **`parse_numeric_value()` parses unsigned**: it used `strtol`, which stops at `LONG_MAX` — 0x7FFFFFFF where `long` is 32 bits — so everything above 2^31 came back as that one wrong number. A bus line nobody drives carries `_FFFF`, and one driven in part carries most of it, so a saved state writes such values routinely.
- **What the guest may do and a device does not model is counted, not fatal**: `ComputerDevice::note_unsupported(what)` bumps the `unsupported` field and keeps the text in `unsupported_last`, and the device carries on as close to the chip as it can (the ВТ57 answers a missing register with nothing, the ВВ55 treats port A in mode 1/2 as mode 0, the ВГ93 answers Read Address/Track with not-ready). `DeviceManager::error()`, which stops the machine, is for faults of the emulator itself - a drive asked for a byte outside its sector. A real machine never freezes because a program touched a register, so neither should the emulator; the counter keeps the inaccuracy visible to a script or an MCP client
- **Device lookup is O(N)**: `DeviceManager::get_device_by_name()` does linear scan. Use `required=false` for optional devices to get `nullptr` instead of exception.
- **Bus timeout is a feature, not an error**: `k1801vm1` aborts the current instruction and traps through vector 004 when an address matches no range. The БК0011М ROM probes for installed memory blocks exactly this way, and without the trap it never starts БЕЙСИК. `MemoryMapper::responds()` answers whether anything is mapped.
- **`-N` entries in `get_registers()` / `get_flags()`**: pairs whose name starts with a dash carry no value — they are blank separators between register groups, drawn (skipped) by `KeyValueArea::paintEvent` and filtered out by the script engine's `pairs_to_string`. Anything else consuming those lists must skip them too.
- **One core source list**: `src/emulator_sources.cmake` defines `ECAT_CORE_SOURCES`, included by `src/CMakeLists.txt` (as `EMULATOR_SOURCES`, shared by the windowed and the console targets) and by `src/wasm/CMakeLists.txt`. A core file goes there and nowhere else; `GUI_SOURCES` is for files that need Qt. A source of one build's library (SDL audio) stays in the list and compiles to nothing without its define.
- **Only `dsk_tools_core` of the `dsk_tools` submodule is built**: helpers, `Result`, the Agat track decoders (`include/dsk_tools/core.h`). The submodule is added `EXCLUDE_FROM_ALL`, so its loaders, file systems and viewers (some 75 files) are never compiled; a file of eCat3 includes `dsk_tools/core.h`, and `dsk_tools/dsk_tools.h` does not even compile here (its headers are not on the include path). Something more from the library means moving it into the core there, not linking the full `dsk_tools`
- **`Emulator`'s constructor takes work, *data*, software, ini** - not the order the members are declared in. Swapping the middle two is silent until a machine whose images live under `software/` reports "Disk image file not found".
- **A machine may carry several disk controllers of different types**: `Irisha-kngmd.cfg` has `fdc : wd1793` (5.25", drives A:/B:) and `fdc2 : gmd70` at ports 50-51 (8", drives E:/F:). Nothing is special-cased by name: the GUI finds drives by class `fdd`, the scripts by device name (`fdd2.track`). Only `cpu`, `mapper`, `display` and `keyboard` are reserved names (and `bios` and `mapper` in the loaders of `files.cpp`). A controller takes its drives with `FDC::load_drives(min, max, list)` (defined in `fdd.cpp`), which checks the count against the controller's selects and that each name is an `fdd`: the five controllers used to parse `drives` each on their own, and only one of them checked anything.
- **A bus master stops the CPU with `cpu->hold(cycles)`**: `CPU::hold()` (`core.h`) banks cycles that `execute()` hands straight back to `Emulator::timer_proc()` instead of running an instruction, so emulated time and every clocked device move on while the processor stands still — HOLD/HLDA, and no change to the emulation loop. `i8275` is the only user: it charges four system clocks per ВТ57 cycle, 2340 of them a frame, which is the 26% of a Радио-86РК the screen refresh really costs. `cpu.hold` reports the running total to scripts. Not to be confused with the wd1793 trick below, which does not spend emulated time at all.
- **Wait states are modelled by running the device forward, not by stalling the CPU**: `wd1793` `sync = <address mask>` marks a data-register copy whose access (Irisha KNGMD port 37) advances the controller state machine until DRQ/INTRQ before returning. Use the same trick for any device whose READY line holds the CPU.
- **`VideoRenderer::fill()` invalidates `render_pixels` under the OpenGL back end**: it reaches `QImage::fill()`, which detaches the implicitly shared image the widget still holds, so the renderer carries on with a fresh buffer while the pointer `GenericDisplay::set_renderer()` captured keeps addressing the copy the widget is about to free. `I8275Display` blacks the screen out by writing `render_pixels` itself for that reason. The symptom is heap corruption reported in an unrelated thread, minutes later — and only in the windowed MCP build, because there the window (and the surface) is created when a machine is asked for, while `--script` builds it up front.
- **`I8275::clock()` must jump between events, not step per character clock**: it is driven at the character clock (1.33 MHz on a Радио-86РК, and the loop body is entered ~7 times per emulated instruction), so stepping one tick at a time costs a quarter of the whole emulator. Only two things happen inside a character row — the next DMA transfer and the end of the row — so the beam advances straight to the nearer of them; `m_dma_delay` is the full period until the next transfer, counted down by `clock()`, and `dma_tick()` is called only when one is due. Getting that period off by one silently changes the burst pacing and every reference screenshot with it.
- **The ВГ75 frame is drawn from a snapshot, never from live registers**: `I8275` runs on the emulation thread and may be reprogrammed at any moment, so `I8275Display` copies the row bytes plus the geometry, font bank, cursor and blink phase when the row is fetched, and the render thread lays the frame out from that alone. Reading `chars_per_row()` / `char_height()` while drawing means one row drawn with the width of one raster and the height of another.
- **`fdd` `layout` picks the track order by file extension** (`cpm:sides|dsk:cylinders`); `save` to an extension with the other order reshuffles tracks on the way out, so the drive doubles as an image converter. Only the sector (`logical`) path honours it; MFM/whole-track paths index `track_indexes[track*sides+side]` directly.
- **Input devices sharing one port go through a `connector`**: interface links are last-writer-wins, so a joystick and a mouse on the same `~data` lines are both `PluggableDevice`s and the `connector` (`devices = joystick|mouse`, `default = none`, `COMMAND up.plug(name|none)`) plugs one. An unplugged device must drive 0 when it leaves, or the port keeps its last value. On the БК the socket is empty by default: a joystick always on the host arrows made programs that poll 0177714 (the TDR demo) run the cursor into the edge
- **A `routed = 1` range asks its device, address by address** (`AddressableDevice::route()`): answer, pass the address on to the ranges after it as if the range were not there, hold the bus with no reply, answer a write and pass it on (like `through`), or answer a read OR-ed with the ranges after it (like `or_read`). `route()` must be side-effect free - `map()`, `map_read()` (which then skips its read-modify-write memo), `responds()`, `fill_page()`, `peek_read_device()` and the debugger all ask it. The page cache asks it once per 512-byte page (at both ends, both ways) and keeps an ANSWER / TIMEOUT / PASS-both-ways answer, so the device must answer uniformly within a page except where it answers THROUGH or OR (those pages stay uncached), and must call `MemoryMapper::routing_changed()` whenever its answers change - the СМК does on a mode change. `map()` reports the route through its optional last argument, so the read and write loops do not ask twice. The СМК-512 of the БК (`smk512`) is the user: one range over 100000-177777 placed before the machine's own memory, which by its mode covers, switches off or leaves alone. Its spec is the gid АльтПро test v4.77F (tables `CODS`/`CODSR11`), run by `tests/scripts/smk-altpro-*.ecat`; the replica's RAM beats ROM and machine RAM on a read but is OR-ed with the I/O registers (the test polls 177716 in mode All, where its own sync word lies underneath), and the machine starts at 166400 because in SYS the ROM covers 177716 too
- **The К1801ВМ1 console mode is external, and the БК's vector 4 on СТОП/HALT is a consequence of it**: entry is RMW 177716 |= 010, PSW to 177676, PC to 177674, new PC/PSW from 160002 (`pdp11core::vm1_console_entry`); START/STEP read them back. On a plain БК nothing answers 177676, the bus timeout becomes the ordinary trap through 4 - `halt_vector`/`halt_sel` do not apply to `1801vm1`. A timeout inside such an entry counts in `cpu.timeouts` (the БК0010 monitor executes a HALT at 120000 on start-up). PSW bits 10/11 come only from a console vector: RTI/RTT clear them (and drop `halt_mode`: a console handler may leave that way instead of START), MTPS keeps them, and while set a timeout goes to 160002 and nIRQ1 waits. `work-bk-smk-halt` is the test, with the СМК-512 Hlt modes providing the console memory
- **The БК 2xAY board is its own entry of the sound socket**, beside the single `ay`: `ts-ay1` (`chip = 1`, `title = 2xAY TurboSound`) and `ts-ay2` (`chip = 2`, `pair = ts-ay1`) sit on 177714 with `through = 1`, and each decodes the select word itself - TurboSound 0377/0376, GryphonSound bits 15/14, the protocol of the bk-catalog emulator. Not folded into `ay`: a word select with a zero high byte (after the port inversion both Gryphon bits) would send a single-AY program to both chips. `ts-ay2` joins the mix only once written. It is last in `devices = ay|covox|ts-ay1` so the indices saved in `[DeviceOptions]` do not shift. A device's `title` overrides its `plug_title()` in any `connector`, so a board name never goes into device code. `work-bk-ay-turbosound` is the test
- **A write reaches only the first matching range, unless it is `through = 1`**: `@memory[177714-177715] = ay {mode = w, through = 1}` followed by `port-ppi-out {mode = w}` delivers the write to both. Reads are unaffected; `LOG mapper.map` marks such ranges with `through`
- **The machine mouse measures a step on the screen widget, not with `get_scale()`**: auto scale (`scale=0`, the shipped default) returns 0 there. The pointer is put back to the middle only when it strays past a quarter of the widget: doing it on every event loops under a fractional Windows scale. Capture lives in `MainWindow::eventFilter`, speed is `[Mouse] speed` in the Settings menu
- **`MOUSE dx,dy[,buttons]` hands its steps out over time**: wait with `WAITFOR mouse.pending == 0`. A recorded movement is written as `_12` / `-_12`, because a БК reads unprefixed numbers as octal
- **Some files are committed with CRLF** (`git ls-files --eol` shows `i/crlf`: `i8255.cpp`, `i8257.*`, `6502.*`, `i8080.*`, `z80.*`, `globals.h.in`). A script that rewrites such a file with LF turns the diff into the whole file; preserve the existing line endings.

## Language and Compiler Constraints

- **C++11 baseline** (`CMAKE_CXX_STANDARD 11`): The emulator core targets C++11 for MinGW 4.9.2 (Windows XP) compatibility. Modern compilers (MSVC, MinGW 13+) build with C++17 features enabled selectively (e.g., `USE_MINI_INI` requires `<filesystem>`).
- **Threading**: `thread_compat.h` provides `EmuThread` and `compat_mutex` — use these instead of raw `std::thread`/`std::mutex`. On MinGW < 5, these map to QThread/QMutex; otherwise to std equivalents. CMake options `FORCE_QT_THREADING` / `FORCE_STD_THREADING` override auto-detection.
- **Qt-free core boundary**: Code under `src/emulator/` must not include Qt headers directly. The only exception is `thread_compat.h`, which uses Qt threading behind `#if USE_QT_THREADING`. Qt-dependent utilities live in `src/qt_utils.h/cpp` (outside the core).
- **Keyboard codes**: `EmuKey` namespace in `keyboard.h` defines key constants with values matching `Qt::Key`, so Qt frontends pass `event->key()` directly. Non-Qt frontends (Wasm, SDL) use the same `EmuKey::` constants.
