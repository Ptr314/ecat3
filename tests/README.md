# Проверка машин сценариями

Набор сценариев __.ecat__ по всем машинам эмулятора и раннер, который
прогоняет их и сравнивает полученное с эталонами. Смысл в том, чтобы после
правки в ядре одной командой убедиться, что ни одна из двух с лишним десятков
конфигураций не перестала запускаться, печатать и считать.

~~~
python tests/run_tests.py               весь набор, кроме медленных тестов
python tests/run_tests.py --all         вместе с медленными
python tests/run_tests.py -k bk         только тесты, в имени которых есть bk
python tests/run_tests.py -j 4          в четыре эмулятора одновременно
python tests/run_tests.py --list        список тестов с описаниями
python tests/run_tests.py --update      записать полученное как новые эталоны
~~~

Раннер завершается с ненулевым кодом, если хоть один тест разошелся с
эталоном, так что его можно ставить в сборочный конвейер.

## Что лежит в каталоге

| Каталог | Содержимое |
|---|---|
| `scripts/` | сценарии, по файлу на тест |
| `files/` | небольшие образы и данные, которые сценарии загружают в машину (рядом лежат скрипты, которыми они сделаны) |
| `expected/` | эталоны: логи, снимки экрана, файлы, снятые с ленты |
| `results/` | результат последнего прогона (в git не входит) |
| `run_tests.py` | раннер |

Имя теста &ndash; это имя файла сценария; первое слово в имени задает группу:

| Группа | О чем |
|---|---|
| `boot-*` | машина доходит до приглашения: карта памяти и портов, разрешение и сам экран. По одному тесту на каждую `.cfg`, включая отладочные |
| `work-*` | работа на машине: набор с клавиатуры, директивы монитора, вычисления в Бейсике и Фокале, переключение режимов экрана, тест из ПЗУ |
| `file-*` | загрузка программ через меню «Файл» и запуск |
| `disk-*` | дисководы и контроллеры |
| `slow-*` | то, что идет десятками секунд: лента, тесты процессоров и памяти. По умолчанию пропускаются, включаются ключом `--all` |

## Как это работает

Раннер запускает эмулятор с ключом `--script` и рабочим каталогом `deploy/`.
Рабочий `deploy/ecat.ini` он сохраняет и возвращает на место: эмулятор
переписывает его при каждом выходе, а прогон запускает эмулятор полсотни раз.
Все, что сценарий оставляет после себя, попадает в `results/` и сравнивается
с одноименными файлами в `expected/`:

* __лог сценария__ (`LOG`, `PRINT`) &ndash; построчно, с показом расхождений;
* __снимки экрана__ (`SCREEN`) &ndash; попиксельно; при расхождении рядом
  кладется `<тест>.diff.png` с эталоном, полученным и разностью;
* __файлы__, записанные командами `tape.save`, `fdd.save`, `ram.save`.

Сценарий сам объявляет, что он пишет: раннер вытаскивает из его текста все
имена вида `"../results/…"`. Поэтому новый тест не требует правки раннера
&ndash; достаточно положить файл в `scripts/`.

Задержки в сценариях отмеряются по тактам процессора, а не по системным часам
(см. [SCRIPTING.md](../SCRIPTING.md)), поэтому результат почти не зависит от
загрузки хост-машины: логи, снимки и снятые с ленты файлы повторяются от
прогона к прогону и не меняются при `-j 4`. Обратная сторона &ndash; сценарий,
у которого машина не запустилась, встает навсегда: время не идет. На такой
случай у каждого теста есть предел времени; его можно задать строкой
`# @timeout <секунд>` в шапке сценария, по умолчанию 90.

## Что нельзя проверять

Повторяемость не абсолютная, и об это стоит споткнуться один раз, а не в
каждом новом тесте.

* __Регистры процессора работающей машины.__ Устройства тактуются порциями,
  длина которых зависит от того, сколько времени прошло на хосте, так что
  момент снимка плавает на доли миллисекунды эмулируемого времени. Машина,
  стоящая в цикле опроса клавиатуры, оказывается в разных точках этого цикла,
  и `LOG cpu.registers` дает каждый раз новое. Поэтому в тестах выводится то,
  что от момента снимка не зависит: карта памяти (`mapper.map`), состояние
  устройств (`fdd0.track`, `tape.size`, `display.resolution`), содержимое
  памяти и экран. Регистры уместны там, где программа уже остановилась
  &ndash; например, в `slow-agat-6502-functional`, где тест заканчивается
  «ловушкой» на известном адресе.
* __Мигающие элементы на экране.__ Курсор и выделенная строка меняются целиком
  и попадают в снимок в случайной фазе. Поэтому снимки сравниваются с допуском
  в 0,2% точек (около двух знакомест); настоящая разница на порядок больше.
  Отдельному тесту допуск задается строкой `# @pixels <точек>`.
* __Конфигурации с `fill = random`.__ У `agat/6502-test.cfg` ОЗУ заполняется
  случайными числами, так что без подготовки случаен и экран, и все состояние
  машины. В тестах память сначала заливается командой `fill`.

## Когда тест не сошелся

Разбирается это глазами: раннер печатает расхождение лога и путь к картинке с
разностью экранов. Дальше два случая.

* __Ошибка в эмуляторе__ &ndash; чинить эмулятор.
* __Поведение изменилось намеренно__ (поправили карту памяти, палитру,
  формат вывода регистров) &ndash; посмотреть на разницу и обновить эталон:

~~~
python tests/run_tests.py --update -k boot-bk-0011m
~~~

Эталоны &ndash; часть репозитория, и коммит с обновленными эталонами должен
объяснять, почему они изменились.

## Чего в наборе нет

Функционального теста 6502 Клауса Дорманна (`src/tests/6502/`), хотя запустить
его сценарием несложно. Единственная подходящая конфигурация,
`agat/6502-test.cfg`, для этого не годится сразу по трем причинам: в ней стоит
ядро 65C02, а тест написан под НМОП-6502; ОЗУ заполняется случайными числами;
и линии `~irq`/`~nmi` подтянуты к активному уровню незаписанным портом, так что
прерывание приходит в случайный момент. Результат от прогона к прогону разный,
и эталон из него не сделать. Нужна отдельная отладочная конфигурация: 6502,
`fill = 0`, неактивные линии прерываний.

## Как добавить тест

1. Положить сценарий в `scripts/` с именем `<группа>-<машина>-<о чем>.ecat`.
2. Первой строкой комментария написать, что тест проверяет: эту строку
   показывает `--list`.
3. Снимки экрана и файлы писать в `../results/<имя>`.
4. Прогнать с `--update`, посмотреть на полученный лог и снимок глазами,
   и только потом коммитить эталон.

Полезное правило: чем меньше в сценарии слепых `WAIT`, тем он надежнее. Там,
где есть за чем следить, лучше `WAITFOR` &ndash; например, `WAITFOR fdd0.loaded == 1`
вместо задержки после подключения образа.

## Эмулятор

Раннер сам находит самую свежую сборку (`src/cmake-build-*`, `build*`,
`.build/build/*`), а нужные для запуска каталоги Qt и MinGW берет из
`CMakeCache.txt` рядом с исполняемым файлом. Если сборка лежит где-то еще:

~~~
python tests/run_tests.py --exe путь/к/eCat3.exe
set ECAT3_EXE=путь\к\eCat3.exe
~~~

Отдельный сценарий можно запустить и руками &ndash; из каталога `deploy`:

~~~
eCat3 --script ../tests/scripts/boot-bk-0011m.ecat
~~~
